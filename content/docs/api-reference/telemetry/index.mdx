Telemetry is stored as one row per reading: a timestamp, a metric name, a value
and a unit. Metric names are always `group.field` (`imu.accel_x`, `gps.lat`,
`system.cpu_temp`), and that string is the interop contract between the stored
history and the live feed.

<Callout title="The live feed is not here">
  These endpoints read what has been STORED. The device publishes at 1 Hz to
  `xorgate/devices/{deviceId}/telemetry` over MQTT, and a client that wants live
  values subscribes to that topic directly over MQTT-over-WSS after calling
  [`POST /live/access`](/api-reference/live/grant-live-access). No endpoint in
  this API streams. The usual pattern is to seed a chart from
  `/telemetry/recent` and append live samples on top.
</Callout>

## Which endpoint to use

`/telemetry/latest` is the cheap "what is it doing now" read: one row per metric,
last-writer-wins, and the authoritative source of a metric's unit. It reflects
the last reading ingested, so on an offline device it keeps returning stale
values rather than nothing. Check the timestamps.

`/telemetry/recent` returns the newest N rows with NO time window, which is what
makes it the right call for seeding a chart. It cannot come back empty just
because the device last reported weeks ago. Default 500 rows, maximum 5000, and
out-of-range values are a `400` rather than being clamped.

`/telemetry` is the range query. Both `from` and `to` are required and the range
may not exceed 31 days. Passing `interval` (seconds) downsamples server-side by
averaging into buckets. This endpoint does not paginate: it caps at 5000 raw
rows or 10,000 buckets and sets `truncated: true` when it hits the cap, which is
your only signal that data was left behind. Narrow the range or pass a coarser
`interval`.

`/telemetry/readings` is the paginated history table, and the only one of the
four that returns a `page` block. It paginates over DISTINCT timestamps so a
page boundary never splits a sample.

`/telemetry/sessions` is different in kind: it does not return readings at all.
It lists what the device **recorded**, one row per telemetry session, with the
counters and the `insights` block (distance, duration, max speed, stops, GPS
quality) computed when the session's overview artifact was built. It is the read
for a sessions table or a "kilometres this month" roll-up, and it never touches
object storage. To play a session's telemetry, ask the
[replay manifest](/api-reference/media-sessions/get-replay-manifest) for its
window: the manifest's `telemetry` block carries the presigned overview and raw
segments. The artifact format and the insight rules are on
[Telemetry sessions and artifacts](/platform-concepts/telemetry-sessions).

## Two caps worth knowing on /telemetry/readings

The `metric` filter accepts at most 20 names anywhere it appears, and each must
match `group.field` or the request is a `400`.

`page.total` is bounded at 10,000 distinct timestamps. When more match,
`page.totalIsCapped` is `true` and only the first 10,000 in the requested order
are addressable; `page.coveredFrom` and `page.coveredTo` describe exactly that
slice. This is not a display quirk, it is a hard boundary: an offset past the cap
returns an empty page rather than an error. To reach older data, narrow `from`
and `to` instead of paging deeper.

## Two response shapes

`/telemetry/readings` defaults to `shape=table`: an ordered `columns` list with
stable units, and one `rows` entry per timestamp whose `v` array is POSITIONAL
against `columns`, with trailing nulls never trimmed. It is roughly ten times
smaller on the wire than the alternative (this API does not compress) and its
column set does not vary between pages.

`shape=flat` returns the `readings: [{ts, metric, value, unit}]` rows instead,
the same raw contract as `/telemetry` and `/telemetry/recent`. Use it when you
want one parser for all four endpoints.

Under `shape=table`, `columnSource` tells you where the columns came from:
`request` (your `metric` filter), `model` (the device model's `ioCapabilities`),
or `data` (the model declares nothing usable, so columns were discovered from
this page and may change between pages). `data` with empty `columns` means the
model declares nothing AND this page has no rows.
