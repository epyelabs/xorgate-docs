<Callout title="Live data does not flow through this API">
  Neither live video frames nor live telemetry samples ever traverse
  `xorgate-core-service`. A client connects to the streaming plane directly:
  WebRTC for video, MQTT over WebSocket for telemetry, using credentials it
  mints itself. The endpoints in this section only hand out the metadata and the
  authorization needed to do that.
</Callout>

## Live video

`GET /devices/{id}/video-channels` returns channel METADATA and no credentials:
one entry per provisioned video stream, each with a `streamKey` (`cam0`,
`cam1`), a `channelName` of the form `${deviceId}-${streamKey}`, a `channelRef`
and a region. Treat `channelRef` as opaque: it is a handle you pass back, not a
string to parse. An empty array means the device is not provisioned yet, which is a
`200` rather than a `404`.

From there the client obtains scoped credentials from
[`POST /auth/live-credentials`](/docs/api-reference/auth/create-live-credentials)
and joins those channels as a viewer while the device publishes. Getting that
lifecycle right (signaling, ICE, credential refresh, reconnection) is real work,
and it is what the Frontend SDK will package.

## Live telemetry

`POST /live/access` is the **first-party dashboard's** path onto the live plane,
not a third party's. It resolves the caller's Cognito identity from the bearer
token and authorizes that identity to connect to the realtime broker and
subscribe to `xorgate/devices/{deviceId}/telemetry`. It is idempotent, so calling
it on every page load is fine and is the normal pattern.

A third-party integration uses
[`POST /auth/live-credentials`](/docs/api-reference/auth/create-live-credentials)
instead: it needs no Cognito identity, accepts any of the three credentials, and
comes back scoped to the calling credential's organization or workspace.

Use the `identityId` it returns as the prefix of your client id. Connect is
scoped to `client/<identityId>*`, so any other client id is refused. Append
something random after the identity id: one identity holds several concurrent
connections, and two browser tabs of the same user resolve to the same identity
id.

[`DELETE /live/access`](/docs/api-reference/live/revoke-live-access) is the
counterpart. It withdraws the authorization from the caller's identity, and
removing someone's last organization membership does the same thing
automatically.

The payload on that topic uses the same `group.field` metric names as the
[stored telemetry](/docs/api-reference/telemetry) endpoints, which is what lets
a chart seeded from `/telemetry/recent` append live samples without translating
anything.

<Callout type="warn" title="What the first-party grant still allows">
  Subscribing is org-blind: the grant authorizes the telemetry topic space
  broadly rather than per organization, so any authenticated caller can
  subscribe to any device's topic. That is acceptable for first-party use and is
  NOT safe to hand to a third party, which is exactly why
  `POST /auth/live-credentials` exists and returns a credential scoped to one
  organization or one workspace. Narrowing this first-party grant the same way is
  tracked as platform-readiness work.

Connecting is not org-blind. It is scoped to the caller's own Cognito identity,
so a browser can neither connect as a device nor as another user. Publishing
was already narrow: browsers may publish only to the workflow-simulator ingest
topics.

</Callout>
