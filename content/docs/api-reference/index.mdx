This section is the reference for `xorgate-core-service`. One page per endpoint,
generated from the service's own OpenAPI document, so each page carries the real
parameters, schemas, response codes, code samples, and a playground that calls
the API from your browser. Each resource also has an overview page covering the
things a schema cannot say.

The base URL for the development deployment is <ApiBaseUrl />.

## Versioning

Every endpoint is served under **`/v1`**, so the full URL for
`POST /auth/session-tokens` on the development deployment is:

```
https://api-dev.xorgate.io/v1/auth/session-tokens
```

The version is part of the PATH, not of the host. Keep your base URL a bare
origin and let the version live with the route, so that pointing a client at a
different deployment cannot silently drop it. The SDKs do the same: you pass
`baseUrl` as an origin and the SDK appends `/v1` itself.

Reference pages below show the full path including `/v1`, because they are
generated from the OpenAPI document. Prose elsewhere on this site writes paths
without it (`POST /auth/session-tokens`), relative to the versioned base URL.
Both mean the same URL.

There is no unversioned surface. A request without the prefix is a `404`. Two
routes also changed name at the cut: `GET /devices/{id}/kvs-channels` became
[`GET /v1/devices/{id}/video-channels`](/api-reference/live/get-device-video-channels)
and `POST /iot/attach-policy` became
[`POST /v1/live/access`](/api-reference/live/grant-live-access). The old
names are gone rather than redirected.

## Things that are true everywhere

<Callout title="Always send X-Organization-Id">
  Org-scoped endpoints resolve the active organization from the
  `X-Organization-Id` header, falling back to your sole membership when you have
  exactly one. If you belong to more than one organization and omit the header,
  every one of those endpoints answers `400 ORGANIZATION_REQUIRED`. Read the
  organization ids from [`GET /me`](/api-reference/users/get-me) and send the
  header on every request.
</Callout>

**Authentication** is one of three credentials in `Authorization: Bearer <…>`,
told apart by prefix: a Cognito ID token (not an access token) for a person, an
`xg_` [API key](/api-reference/api-keys) for a program, or an `xgs_`
[session token](/api-reference/auth) for a browser or mobile app. Most
endpoints take any of them. See
[Authentication](/getting-started/authentication) for which to reach for.

**Responses are always a named object**, never a bare array: `{devices, page}`,
`{device}`, `{organizations}`. Fields are camelCase throughout. Three envelope
keys are snake_case (`api_keys`, `api_key`/`plaintext_key`, and
`device_model`/`device_models`) because they mirror their Postgres table names.
That is a wart we chose to keep rather than break clients over, and the SDKs
will normalize it.

**Errors are uniform**: `{"error": {"code", "message", "details?"}}`. Match on
`code`, never on `message`. A resource in another organization returns `404`
rather than `403`, so an unauthorized read is indistinguishable from a missing
one by design.

**Deletes return `204`** with an empty body. Device commands return `202`,
meaning the instruction reached the message broker, not that the device carried
it out.

**Only three endpoints paginate**: `GET /devices`,
`GET /devices/{id}/sessions`, and `GET /devices/{id}/telemetry/readings`. They
share one dialect (`limit`, `offset`, `order`, `sort`, and where relevant
`status`, `from`, `to`) and return a `page` block. An over-large `limit` is
clamped silently rather than rejected, so read `page.limit` back. Every other
list endpoint returns its whole collection with no `page` block at all.

## What is not in here

Live telemetry and live video do not flow through this API. The client
subscribes over MQTT-over-WebSocket for the 1 Hz telemetry feed, and connects
over WebRTC for live video, using credentials it
mints itself. This API only hands out the metadata and the authorization needed
to do that; see [Live](/api-reference/live).

Two routes are excluded on purpose and do not appear here: `GET /get/{code}`,
which renders the device install script, and
`POST /device-registrations/{code}/claim`, which returns private key material.
Both are internal to the installer. See
[Device Registrations](/api-reference/device-registrations) for how they
fit into onboarding.

The Workflows and AI surface is undocumented while it is still moving.
