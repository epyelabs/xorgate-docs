---
title: "Overview"
description: "The platform-wide hardware catalog, and why io_capabilities drives so much."
---

A device model describes a hardware configuration: a name, a SKU, and an
`ioCapabilities` document. Unlike everything else in this reference, the catalog
is PLATFORM-wide rather than per organization. These endpoints take no
`X-Organization-Id` header, every authenticated caller sees the same rows, and
writes require the platform-admin role (`user.role === "admin"` from
[`GET /me`](/api-reference/users/get-me)), which is separate from any
membership role.

`ioCapabilities` is the field that matters. It is a structured JSON document
(`{ schemaVersion, media: { video[], audio[] }, sensors, comm, system }`) and it
drives two things elsewhere in the platform. Its declared video and audio stream
keys (`cam0`, `cam1`, `audio0`) become the video channels created when a
device is provisioned, and its declared sensors become the default column set of
the [telemetry history table](/api-reference/telemetry/get-device-telemetry-readings).
A model that declares nothing usable is not an error, but devices built from it
fall back to discovering columns from whatever data a page happens to contain.

<Callout type="warn" title="ioCapabilities is not validated on write">
  `POST` and `PUT` accept any JSON object here. The schema shown on those pages
  is generated from the same definition the provisioning code parses with, but
  that parse happens later, when the device is
  [provisioned](/api-reference/devices/provision-device), and it is forgiving in
  the worst way: a document that fails it yields no video stream keys, so the
  device is provisioned with ZERO video channels and live video simply never
  works, with no error anywhere along the way. Validate the document against the
  schema yourself before writing it.
</Callout>

Two more consequences worth planning around. Editing `ioCapabilities` does not
retro-provision anything: devices already provisioned from that model keep the
channels they were given. And device onboarding by registration code picks the
model automatically (the most recently created one), so a deployment is expected
to have a small, curated catalog rather than a large one.

The envelope keys are `device_models` and `device_model` in snake_case, mirroring
the table name, with camelCase contents. See
[the reference overview](/api-reference) for why that stays.
