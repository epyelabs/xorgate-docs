There is **no API Gateway authorizer** in front of xorgate-core-service. Every
route is reachable at the gateway and each handler enforces its own auth. A route
described as unauthenticated is simply one whose handler does not check.

## Two credentials, one header

The API accepts two kinds of bearer credential, and tells them apart by the
credential itself rather than by a separate header:

| Credential           | Prefix | Who sends it                          | Carries a user |
| -------------------- | ------ | ------------------------------------- | -------------- |
| Cognito **ID** token | a JWT  | a signed-in browser or mobile session | yes            |
| API key              | `xg_`  | a server-to-server integration        | no             |

A third prefix, `xgs_`, is reserved for short-lived session tokens. Nothing
mints one yet and sending one returns `401 SESSION_TOKEN_UNSUPPORTED`.

route is reachable at the gateway and each handler enforces its own auth. A route
described as unauthenticated is simply one whose handler does not check.

## Cognito ID tokens

A Cognito ID token (not an access token) on the `Authorization` header, plus the
tenancy headers from [Tenancy model](/docs/getting-started/tenancy):

```http
GET /devices HTTP/1.1
Host: h357muxy3k.execute-api.us-east-1.amazonaws.com
Authorization: Bearer <cognito-id-token>
X-Organization-Id: 8f1c1e2a-....
```

The token is verified against the platform user pool. On the first request from a
new identity, a `users` row is created from the token's `sub`, `email` and
`name`, so there is no separate registration step.

## API keys

For server-to-server integrations, an ID token is the wrong shape: it is
short-lived and tied to an interactive login. Mint a key instead:

```http
POST /api-keys
Content-Type: application/json
Authorization: Bearer <cognito-id-token>
X-Organization-Id: 8f1c1e2a-....

{ "name": "alocate-backend", "scope": "cloud", "role": "member" }
```

```json
{
  "api_key": {
    "id": "...",
    "name": "alocate-backend",
    "scope": "cloud",
    "role": "member",
    "keyPrefix": "xg_9c1f0",
    "expiresAt": null,
    "...": "..."
  },
  "plaintext_key": "xg_9c1f...."
}
```

The key is returned **exactly once**, at creation. Only its SHA-256 hash is
stored, so a lost key has to be replaced rather than recovered. Minting or
deleting a key requires the `owner` or `admin` role.

Then send it in the same header a token goes in:

```http
GET /devices HTTP/1.1
Authorization: Bearer xg_9c1f....
```

Three things follow from a key having no user behind it.

**It is bound to one organization.** The organization comes from the key row, so
`X-Organization-Id` is never required. Sending a _different_ organization is a
`403 FORBIDDEN` rather than a silently ignored header: a consumer that thinks it
is switching tenants and is not has a bug worth hearing about.

**It acts with a role.** Every key carries one, defaulting to `member`, and it
runs through the same role gates a membership role does. A `member` key can read
everything and write devices, workspaces and device registrations, which is what
a data-plane integration needs. It cannot touch memberships, API keys or
organization settings. A key is also never a _platform_ admin, so device-model
writes are closed to every key regardless of its role. See the
[method index](/docs/backend-sdk/resources) for the per-operation gates.

You cannot mint a key more privileged than you are: an `admin` minting an
`owner` key gets a `403`.

**Four operations refuse it**, because they describe or act on a person, and
answer `401 USER_CREDENTIAL_REQUIRED`: `GET /me`, `GET /organizations`,
`POST /organizations`, and the two live-access operations.

### Rotation, expiry and revocation

A key can be given an `expiresAt` at mint time (ISO-8601, must be in the
future); omit it for a key that never expires. Past its expiry a key gets
`401 API_KEY_EXPIRED`.

`DELETE /api-keys/{id}` is a hard delete, not a revocation: the row goes and the
key thereafter reads as unknown (`401 INVALID_API_KEY`). Rotation is therefore
mint-then-delete, with both keys live in between.

`lastUsedAt` advances as a key is used, but treat it as a liveness hint for
finding unused keys rather than an audit trail: the write is throttled to at most
once per minute per serving process and is deliberately fire-and-forget, so it
never delays or fails a request.

<Callout type="info" title="One key spans everything its organization can see">

A key is organization-scoped, not workspace-scoped, so a consumer that maps its
own customers onto workspaces has one key covering all of them. Keep keys on
your server, give each integration its own so one can be replaced without
disturbing the others, and set an expiry on anything long-lived.

</Callout>

### Programmatic onboarding, and the one thing you cannot do

`POST /organizations` needs a user, so a key cannot create an organization. A
consumer onboarding its own customers maps them onto **workspaces** inside its
one organization, which a default `member` key can create. Organizations for a
new consumer are provisioned out of band.

## The live planes

Live telemetry and live video do not go through the REST API, and so they do not
use the same credential.

- **Live telemetry** is MQTT over a SigV4-signed WebSocket to AWS IoT Core. The
  browser gets temporary AWS credentials from a Cognito Identity Pool (federated
  from the same user pool), calls `POST /iot/attach-policy` once to attach its IoT
  policy, then subscribes to `xorgate/devices/<deviceId>/telemetry`.
- **Live video** is KVS WebRTC. `GET /devices/{id}/kvs-channels` returns channel
  metadata only. The browser mints its own credentials the same way and joins the
  channel as a viewer, with media flowing peer to peer from the device.

<Callout type="warn" title="Live-plane READ scope is not organization-scoped">

What the IoT and KVS browser policies let you read is currently broad but
authenticated: any authenticated user can subscribe to any device's telemetry
topic. This is a known cross-tenant gap and has to be closed before third
parties touch the live plane. It is tracked on the platform-readiness backlog.

Connecting to the broker is organization-blind but not identity-blind: it is
scoped to the caller's own Cognito identity, so the MQTT client id must start
with the `identityId` that `POST /iot/attach-policy` returns.
[`DELETE /live/access`](/docs/api-reference/live/revoke-live-access) revokes what
that call granted.

</Callout>

An API key has no live-plane path. Both live planes are entered with AWS
credentials from the Cognito Identity Pool, which needs a Cognito identity, and
a key does not have one: the two live-access operations refuse keys with
`401 USER_CREDENTIAL_REQUIRED`. So an application that authenticates its own
users, rather than federating them into xorgate's Cognito, can use the whole
REST surface with a key but cannot yet open a live stream. Telemetry history and
recorded media go through REST and work regardless.

## CORS

Browser callers are gated by a **fixed origin allowlist** in the API stack, not by
a wildcard. Allowed request headers are exactly `Authorization`, `Content-Type`,
`X-Request-ID`, `X-Organization-Id` and `X-Workspace-Id`. A new browser origin
(including this documentation site, whose API playground calls the API directly)
has to be added to that allowlist before it can call the API.

## Unauthenticated routes

Two routes are deliberately open, both part of the device install flow:
`GET /get/{code}` renders the install script, and
`POST /device-registrations/{code}/claim` exchanges a registration code for a
device identity. The short-lived registration code is the bearer secret in both
cases.

The claim route returns **private key material** for the device's X.509
certificate. It is meant to be called once, by the installer, on the device
itself. Do not build against it.
