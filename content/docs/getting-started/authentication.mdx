There is **no API Gateway authorizer** in front of xorgate-core-service. Every
route is reachable at the gateway and each handler enforces its own auth. A route
described as unauthenticated is simply one whose handler does not check.

## Three credentials, one header

The API accepts three kinds of bearer credential, and tells them apart by the
credential itself rather than by a separate header:

| Credential           | Prefix | Who sends it                          | Carries a user |
| -------------------- | ------ | ------------------------------------- | -------------- |
| Cognito **ID** token | a JWT  | a signed-in browser or mobile session | yes            |
| API key              | `xg_`  | a server-to-server integration        | no             |
| Session token        | `xgs_` | a third party's browser or mobile app | no             |

Which one you want follows from where the credential will live. Code you
control on a server holds a key. Code you ship to someone else's device holds a
session token, because it is short-lived, narrower than the key, and revocable.
A person signing in to xorgate's own dashboard holds an ID token.

## Cognito ID tokens

A Cognito ID token (not an access token) on the `Authorization` header, plus the
tenancy headers from [Tenancy model](/docs/getting-started/tenancy):

```http
GET /devices HTTP/1.1
Host: h357muxy3k.execute-api.us-east-1.amazonaws.com
Authorization: Bearer <cognito-id-token>
X-Organization-Id: 8f1c1e2a-....
```

The token is verified against the platform user pool. On the first request from a
new identity, a `users` row is created from the token's `sub`, `email` and
`name`, so there is no separate registration step.

## API keys

For server-to-server integrations, an ID token is the wrong shape: it is
short-lived and tied to an interactive login. Mint a key instead:

```http
POST /api-keys
Content-Type: application/json
Authorization: Bearer <cognito-id-token>
X-Organization-Id: 8f1c1e2a-....

{ "name": "alocate-backend", "scope": "cloud", "role": "member" }
```

```json
{
  "api_key": {
    "id": "...",
    "name": "alocate-backend",
    "scope": "cloud",
    "role": "member",
    "keyPrefix": "xg_9c1f0",
    "expiresAt": null,
    "...": "..."
  },
  "plaintext_key": "xg_9c1f...."
}
```

The key is returned **exactly once**, at creation. Only its SHA-256 hash is
stored, so a lost key has to be replaced rather than recovered. Minting or
deleting a key requires the `owner` or `admin` role.

Then send it in the same header a token goes in:

```http
GET /devices HTTP/1.1
Authorization: Bearer xg_9c1f....
```

Three things follow from a key having no user behind it.

**It is bound to one organization.** The organization comes from the key row, so
`X-Organization-Id` is never required. Sending a _different_ organization is a
`403 FORBIDDEN` rather than a silently ignored header: a consumer that thinks it
is switching tenants and is not has a bug worth hearing about.

**It acts with a role.** Every key carries one, defaulting to `member`, and it
runs through the same role gates a membership role does. A `member` key can read
everything and write devices, workspaces and device registrations, which is what
a data-plane integration needs. It cannot touch memberships, API keys or
organization settings. A key is also never a _platform_ admin, so device-model
writes are closed to every key regardless of its role. See the
[method index](/docs/backend-sdk/resources) for the per-operation gates.

You cannot mint a key more privileged than you are: an `admin` minting an
`owner` key gets a `403`.

**Five operations refuse it**, because they describe or act on a person, and
answer `401 USER_CREDENTIAL_REQUIRED`: `GET /me`, `GET /organizations`,
`POST /organizations`, and the two live-access operations.

<Callout type="warn" title="A key must never reach a browser">

A key is organization-wide and does not expire unless you gave it an
`expiresAt`, so a copy in a JavaScript bundle or a mobile binary is a published
key. Ship a session token instead; the next section is how.

</Callout>

### Rotation, expiry and revocation

A key can be given an `expiresAt` at mint time (ISO-8601, must be in the
future); omit it for a key that never expires. Past its expiry a key gets
`401 API_KEY_EXPIRED`.

`DELETE /api-keys/{id}` is a hard delete, not a revocation: the row goes and the
key thereafter reads as unknown (`401 INVALID_API_KEY`). Rotation is therefore
mint-then-delete, with both keys live in between.

`lastUsedAt` advances as a key is used, but treat it as a liveness hint for
finding unused keys rather than an audit trail: the write is throttled to at most
once per minute per serving process and is deliberately fire-and-forget, so it
never delays or fails a request.

<Callout type="info" title="One key spans everything its organization can see">

A key is organization-scoped, not workspace-scoped, so a consumer that maps its
own customers onto workspaces has one key covering all of them. Keep keys on
your server, give each integration its own so one can be replaced without
disturbing the others, and set an expiry on anything long-lived.

</Callout>

### Programmatic onboarding, and the one thing you cannot do

`POST /organizations` needs a user, so a key cannot create an organization. A
consumer onboarding its own customers maps them onto **workspaces** inside its
one organization, which a default `member` key can create. Organizations for a
new consumer are provisioned out of band.

## Session tokens

A session token is what your application hands to code running on someone
else's device. Your server exchanges its key for one, per end user, after making
its own authorization decision:

```http
POST /auth/session-tokens
Content-Type: application/json
Authorization: Bearer xg_9c1f....

{ "workspaceId": "3f9a...", "ttlSeconds": 900 }
```

```json
{
  "id": "0f2c....",
  "token": "xgs_7d3b....",
  "expiresAt": "2026-08-13T12:15:00Z",
  "workspaceId": "3f9a....",
  "role": "member",
  "live": {
    "region": "us-east-1",
    "realtimeEndpoint": "a1b2c3d4e5f6g7-ats.iot.us-east-1.amazonaws.com"
  }
}
```

Then the client sends it in the same header everything else uses:

```http
GET /devices HTTP/1.1
Authorization: Bearer xgs_7d3b....
```

Both fields in the body are optional. Omit `workspaceId` and the token sees the
whole organization, exactly as the key does; omit `ttlSeconds` and it lives 15
minutes, with an hour the maximum. An out-of-range TTL is rejected rather than
clamped, because a lifetime you believe you got and did not shows up as
mysterious 401s much later.

xorgate never learns who your end user is. You authorize the person, xorgate
authorizes the key, and `workspaceId` is how you state the first decision in
terms the second can enforce.

**Only a key can mint one.** An ID token gets `401 API_KEY_REQUIRED` (a
signed-in session already authenticates this API directly), and a session token
cannot mint another one, or a leaked token would renew itself forever and the
expiry would mean nothing.

**A token is never more privileged than its key.** It inherits the key's `role`,
and the role in force on any request is the _lower_ of the token's and the key's
current role. Downgrading a key downgrades its live tokens rather than leaving
them privileged until they expire.

**It has no user either**, so the same operations that refuse a key refuse a
token, with the same `401 USER_CREDENTIAL_REQUIRED`.

### Workspace scoping is an enforced boundary

For a person or a key, every workspace in the organization is visible and
`X-Workspace-Id` merely narrows a list. For a session token minted with a
`workspaceId` it is a boundary:

- Devices, and everything reached through a device id, are confined to that
  workspace. Another workspace's device reads as `404`.
- `GET /workspaces` returns exactly one row, its own.
- An `X-Workspace-Id` naming a different workspace is `403 WORKSPACE_MISMATCH`,
  not a silently empty result.
- `POST /device-registrations` needs no `X-Workspace-Id`: the token supplies it.
- Organization-wide operations, meaning memberships, API keys, organization
  settings and workspace writes, are `403 WORKSPACE_SCOPED` **whatever role the
  token carries**. The limit is tenancy, not privilege.
- `GET /device-models` is still allowed. The hardware catalog is platform-wide
  and has no tenant to separate.

That is what lets a consumer running its own multi-tenancy give each of its
customers a credential that provably cannot reach another's.

### Revoking a session token

There is no per-token revoke endpoint. The maximum lifetime is an hour, and
tracking token ids in order to revoke them would be more machinery than that
window justifies.

The emergency stop is one level up: `DELETE /api-keys/{id}` destroys every
session token minted from that key, immediately. Mint the replacement key first
if the integration also has to keep working.

## The live planes

Live telemetry and live video do not go through the REST API, and so they do not
use the same credential.

- **Live telemetry** is MQTT over a SigV4-signed WebSocket to AWS IoT Core. The
  browser gets temporary AWS credentials from a Cognito Identity Pool (federated
  from the same user pool), calls `POST /iot/attach-policy` once to attach its IoT
  policy, then subscribes to `xorgate/devices/<deviceId>/telemetry`.
- **Live video** is KVS WebRTC. `GET /devices/{id}/kvs-channels` returns channel
  metadata only. The browser mints its own credentials the same way and joins the
  channel as a viewer, with media flowing peer to peer from the device.

<Callout type="info" title="Live-plane read scope is per-tenant">

A credential from
[`POST /auth/live-credentials`](/docs/api-reference/auth/create-live-credentials)
reaches its own scope's live plane and nothing else. Vended for a workspace, it
receives that workspace's devices' telemetry and can view that workspace's
devices' video; a sibling workspace's device is refused rather than filtered,
by the credential itself.

The xorgate dashboard is the exception, and deliberately so: it signs in as a
person, federates that person into an identity pool, and what it may read there
is still broad-but-authenticated. Narrowing the first-party path onto the same
per-tenant mechanism is a separate change and is not done yet. Connecting is
identity-scoped either way, so an MQTT client id must start with the
`identityId` that `POST /iot/attach-policy` returns.
[`DELETE /live/access`](/docs/api-reference/live/revoke-live-access) revokes what
that call granted.

</Callout>

An API key and a session token both have a live plane, and it is the same one.
Call
[`POST /auth/live-credentials`](/docs/api-reference/auth/create-live-credentials)
with either, and hand what comes back to the SDK. This is the endpoint that lets
an application authenticating its OWN users open a live stream, which is the
thing that used to be impossible: the browser holds a session token and vends
for itself, or your server holds the API key, vends per customer, and the
browser never touches xorgate at all.

The two live-access operations still refuse both credentials with
`401 USER_CREDENTIAL_REQUIRED`, and that is correct rather than a leftover: they
attach and detach an IoT policy on a **Cognito identity**, which neither
credential has. They are the dashboard's own path, not part of a third-party
integration.

<Callout type="info" title="Two things arrive with the token, and only one is a credential">

`POST /auth/session-tokens` returns `live: { region, realtimeEndpoint }` so a
client never has to hardcode where the live plane is. Those are addresses, not
authorization. What opens a stream is the separate exchange above — which the
SDK performs for you, so in practice you supply the token and nothing else.

</Callout>

## CORS

Browser callers are gated by a **fixed origin allowlist** in the API stack, not by
a wildcard. Allowed request headers are exactly `Authorization`, `Content-Type`,
`X-Request-ID`, `X-Organization-Id` and `X-Workspace-Id`. A new browser origin
(including this documentation site, whose API playground calls the API directly)
has to be added to that allowlist before it can call the API.

## Unauthenticated routes

Two routes are deliberately open, both part of the device install flow:
`GET /get/{code}` renders the install script, and
`POST /device-registrations/{code}/claim` exchanges a registration code for a
device identity. The short-lived registration code is the bearer secret in both
cases.

The claim route returns **private key material** for the device's X.509
certificate. It is meant to be called once, by the installer, on the device
itself. Do not build against it.
