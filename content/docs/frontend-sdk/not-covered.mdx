title: "What this SDK does not cover"
description: "Runtime limits, deliberate omissions, and the platform gaps a frontend consumer will hit — in either package."
---

Everything here is a known limit, not an oversight. Reading it before you design
around this package is cheaper than discovering it afterwards.

## Runtime limits

### React Native is a different package

<Callout type="info" title="This page used to say React Native was not supported. It is.">

All three planes run on a phone, through
[`@xorgate/react-native`](/frontend-sdk/react-native): live telemetry, live
video into `react-native-webrtc`'s `RTCView`, and replay over `expo-video`.

The old reason given here was that mqtt.js needs a `WebSocket` it recognises.
That turned out to be false — **mqtt.js 5 runs on React Native's global
`WebSocket` unmodified**, and no substitute client was needed. What was
genuinely missing was smaller and more specific: Hermes has no `crypto` global,
which one package entry point installs, and the AWS tree needs four Metro
resolver rules. Both are documented and both are four lines of setup.

</Callout>

What remains true is that **`@xorgate/react` itself** is the browser package and
will not run there: its `useLiveVideo`, `LiveVideo`, `useReplayPlayer` and
`ReplayVideo` need `HTMLVideoElement`, `window` or Media Source Extensions.
Those four names are shadowed by native implementations in the React Native
package, and everything else — the data hooks, the telemetry feed, the KVS
session itself, the clock, the lanes, the timeline and telemetry math — is
shared code reached through the provider's `platform` slot, not a second
implementation.

One thing is not yet verified there: a **physical phone over a cellular
network**. Everything published was measured on the iOS simulator against a
production device over Wi-Fi, so carrier-NAT TURN relay selection and iOS's real
background socket suspension are open. See
[live video on React Native](/frontend-sdk/react-native-live-video).

### Server rendering renders a shell

The provider renders on the server without error. Every REST hook returns
`{ data: undefined, isLoading: true }` there, so a page renders its loading
state and hydration fills it in. That is the whole extent of the support.

The live and replay hooks touch browser APIs on mount, so put them below a
client boundary. Under Next.js, mark the component that mounts the provider
`"use client"`.

There is no server-side data fetching helper, no `dehydrate`/`hydrate` pair and
no streaming integration. If you want data on the server, call `@xorgate/sdk`
there directly and pass the result down as props; that is what it is for.

### No Suspense, no `use()`

The hooks return state, they do not throw promises. Suspense boundaries around
them do nothing. If you want Suspense, drive `@xorgate/sdk` through a library
that provides it.

### There is no HLS, on any platform

Recorded segments are 60-second fMP4 files in S3, and stitching them is the
client's job. There is no HLS, no DASH, no plain URL you can hand to another
player, and no transcoding service to ask for one.

That constraint shapes both players rather than blocking either. In the browser
the segments are appended into one `SourceBuffer` through Media Source
Extensions. On React Native, where there is no MSE and a native player plays a
file, each lane runs [two players and flips between
them](/frontend-sdk/react-native-replay) at a segment boundary.

## Deliberate omissions

### No styling, and no copy

Two components ship, `LiveVideo` and `ReplayVideo`, and each is a hook plus a
bare `<video>` element. There is no grid, no scrubber component, no status
badge, no gap overlay, no error card.

The same rule applies to words. `useLiveBlock` returns
`{ blocked, reason, detail, elapsedMs, parked }` and no human-readable copy at
all, even though xorgate-web has three carefully written paragraphs for the
three known reasons. Copy is product voice; an SDK that ships it makes every
consumer sound like xorgate.

### No query cache

No deduplication across components, no background revalidation beyond
`refetchIntervalMs`, no optimistic updates, no mutation helpers. The data hooks
are thin wrappers over `@xorgate/sdk` calls.

Bring your own library and drive it from `useXorgate()`. That is a first-class
way to use this package, not a workaround.

### No writes

The hooks are read-only. There is no `useUpdateDevice` or `usePatchConfig`,
because a mutation hook without a cache to invalidate is just a `useState`
around a promise. Do writes imperatively:

```tsx
const xg = useXorgate()
await xg.devices.patchConfig(deviceId, { gnssAntBias: true })
await refetch()
```

### No workflows, no AI

The workflow templates, instances, runs, catalog, model registry and simulation
surfaces are out of scope for the whole SDK effort, in both packages. The
definition format, the node catalog and the engine itself, which the platform
runs on, are documented under [Workflows](/workflows).

## Platform gaps you will hit

These are limits of the platform, not of the SDK. They are recorded on the
plan's backlog; they are listed here so you can design around them today.

### The live plane is a tenant boundary for vended credentials, and not for the dashboard

<Callout type="info" title="What a vended credential can watch">

Credentials from
[`POST /auth/live-credentials`](/api-reference/auth/create-live-credentials)
reach exactly one scope. Vended for a workspace, they receive that workspace's
devices' telemetry and can view that workspace's devices' video, and a sibling
workspace's device is refused rather than filtered. That is the boundary a
consumer running its own multi-tenancy needs, and the SDK obtains and refreshes
those credentials for you.

The exception is the xorgate dashboard's own path, which signs a **person** into
an identity pool and is still broad-but-authenticated: a signed-in xorgate user
can watch any device. It does not affect a consumer integration, which never
uses that path, and the REST API was never affected — every endpoint there
enforces membership.

</Callout>

### No webhooks, so polling is the only option

Nothing pushes over the REST plane. Device state, config acknowledgement,
registration claims and new recording sessions are all discovered by polling.
`refetchIntervalMs` is the tool; be gentle with it, especially against
`useRecordingRuns`, which is the slowest endpoint in the API.

Live telemetry **is** push, and it carries more than metrics: the `recording`
and `media` blocks tell you whether the device is uploading, whether video is
recording and whether live streaming is parked. Where a device is online, that
feed is a better source than any poll.

### No batch telemetry read

There is one `telemetry/latest` per device. A fleet map is N requests, so a
workspace dashboard is N+1 and a thousand-device fleet is not servable this way.
For a fleet view, poll a bounded page of devices rather than the whole fleet.

### `telemetry/latest` has no staleness signal

It returns the last reading it ever ingested, forever. Compare `reading.ts`
against now yourself, on every consumer, or ship a map that lies about where an
asset is.

### Config writes have no optimistic concurrency

`PATCH /devices/{id}/config` replaces each namespace whole with no `If-Match` on
`configRev`. Two browser tabs editing the same device silently clobber each
other, and the loser never learns. Read, merge and write is a mitigation, not a
fix.

### The development API is slow when cold

First call after an idle period runs 1 to 2.5 s. Warm calls are 200 to 420 ms,
except `GET /devices/{id}/sessions`, which is about 1,090 ms even warm. The
cause is Lambda cold starts against a database sitting at its minimum capacity,
not the SDK. Do not set `timeoutMs` below about 3,000, and do not write a test
that assumes a fast first request.
