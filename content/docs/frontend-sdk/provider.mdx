---

`XorgateProvider` carries four things: where the API is, what AWS resources the
live plane uses, how to authenticate, and which tenant you are acting as.
Everything below it reads them from context.

```tsx
import { XorgateProvider } from "@xorgate/react"

;<XorgateProvider
  config={{
    baseUrl: import.meta.env.VITE_API_BASE_URL,
    region: import.meta.env.VITE_AWS_REGION,
    identityPoolId: import.meta.env.VITE_COGNITO_IDENTITY_POOL_ID,
    userPoolId: import.meta.env.VITE_COGNITO_USER_POOL_ID,
    realtimeEndpoint: import.meta.env.VITE_IOT_ENDPOINT,
  }}
  auth={{ getIdToken }}
  organizationId={organizationId}
  workspaceId={workspaceId}
>
  <App />
</XorgateProvider>
```

Reading `import.meta.env` in your own application code is fine. The rule is that
the **SDK** never does it: the values arrive as props, so one build of the
package serves your development and production environments, and a test can
point a hook at a fake without a bundler.

Nothing is required; `config` may be omitted entirely. The four AWS fields are
what the **first-party** live plane needs, and leaving them out is a supported
configuration rather than a mistake: in `{ getIdToken }` mode every live hook
then reports `status: "unavailable"` with
`unavailableReason: "not-configured"` instead of failing at runtime. In the two
third-party modes the live coordinates arrive with the credential, so those
fields stay unset. REST and replay work without any of them.

`realtimeEndpoint` is the one value that is not in any console page you would think
to look at. Get it with `aws iot describe-endpoint --endpoint-type iot:Data-ATS`,
or read it off `iot.dataEndpoint` in a `POST /devices/{id}/provision` response.

## `auth`

Three modes. They differ in which planes they can reach, which is the single
most important thing to understand about this SDK.

### `{ getIdToken }`, Cognito

```tsx
auth={{ getIdToken: async () => (await auth.currentSession()).getIdToken() }}
```

The first-party mode, for applications whose users sign in to xorgate itself.
It returns a Cognito **ID** token, not an access token: the API verifies
`tokenUse: "id"`, and the Identity Pool federates on the ID token as well. This
is the one mode that needs the four AWS fields in `config`.

It is called on every REST request and before every live reconnect. The SDK does
not cache it, because your Cognito library already does and only that library
knows when it expires. Returning `null` means "not signed in yet": REST hooks
stay `isLoading`, live hooks stay `connecting`, and nothing throws.

### `{ apiKey }`, REST only

```tsx
auth={{ apiKey: process.env.XORGATE_API_KEY }}
```

Sent as `Authorization: Bearer xg_…`, matching
[the backend SDK](/backend-sdk/authentication). Two warnings, both real:

<Callout type="warn" title="An API key in a browser bundle is a published key">
  This mode exists for React rendered on a server you control, or behind a proxy
  that injects the header. It is not for a public single-page app. Nothing in
  the platform can scope a key to an origin, so a leaked key is a
  full-organization credential.
</Callout>

<Callout
  type="warn"
  title="Reach the live plane from your server, not from this mode"
>
  An API key can obtain live credentials — that is what the [live-credentials
  endpoint](/api-reference/auth/create-live-credentials) is for — but doing it
  from a browser means the key was in the browser, which is the problem above
  rather than a solution to it. Vend on your server and pass the result in
  through `getLiveCredentials`, or use `getSessionToken` and let the SDK vend
  for itself.
</Callout>

A key also cannot reach the four person-scoped operations (`GET /me`,
`GET`/`POST /organizations`, and the two live-access operations), which answer
`401 USER_CREDENTIAL_REQUIRED`.

### `{ getSessionToken }`, the third-party mode

```tsx
auth={{ getSessionToken: () => myBackend.getXorgateSessionToken() }}
```

**The mode to reach for by default in a third-party application.** Your server
exchanges its API key for a short-lived `xgs_` token and hands it to your client;
the client supplies it here, and the SDK does everything else. REST is
authenticated with it directly, the live-plane coordinates arrive with it, and
the SDK exchanges it for live credentials on your behalf. Your `config` collapses
to `{ baseUrl }`.

What the token may see is decided when your server mints it: the key's
organization, never more than the key's role, an expiry of at most an hour, and
optionally **one workspace**. A workspace-scoped token is confined to that
workspace as a boundary rather than a filter, on the REST plane and on both live
planes alike. That is how a consumer running its own multi-tenancy gives each of
its customers a credential that cannot reach the others.

It is called on every REST request and before every live reconnect, exactly like
`getIdToken`, and the SDK does not cache it: hold the token until shortly before
`expiresAt` and then fetch another from your own endpoint. Returning `null`
behaves like a signed-out first-party session.

### `{ getLiveCredentials }`, the escape hatch

```tsx
auth={{
  getSessionToken: undefined,
  getLiveCredentials: () => myBackend.mintXorgateLiveCredentials(),
}}
```

For a consumer whose own backend vends live credentials and whose browser
therefore touches no xorgate endpoint at all. This is Project Alocate's shape:
it manages its own users, talks to xorgate server-to-server with an API key, and
its server calls
[`POST /auth/live-credentials`](/api-reference/auth/create-live-credentials)
with the workspace that end user is allowed to see.

Almost nobody needs it — `{ getSessionToken }` is the supported path and does the
vending for you — and it earns its place because a fully proxied consumer wants
one fewer endpoint reachable from its browser, not because the SDK cannot do the
exchange.

Whatever `POST /auth/live-credentials` returned is what this function should
return, unread: the fields are dictated by the signing algorithm rather than
chosen, which is exactly why they are not something to build against.

Nothing in `useLiveTelemetry`, `useLiveVideo` or `useReplayPlayer` mentions an
auth mode; they ask an internal resolver for credentials. That is what lets this
slot exist without touching a single hook contract.

`getLiveCredentials` is called on connect and again on the roughly 50 minute
refresh cycle, so an implementation should cache and only mint when its own copy
is near expiry.

## Tenancy

```tsx
organizationId={organizationId}   // string | null, required prop
workspaceId={workspaceId}         // optional
```

`organizationId` is **nullable on purpose**, which is a deliberate divergence
from the backend SDK, where it is a required string. A browser renders before
the user has picked an organization, and a brand-new user has none at all.
Making the prop required but the value nullable forces you to think about that
state instead of discovering it as a 400.

While it is null:

- `useMe()` and `useOrganizations()` still work. They are two of the three
  operations that need no active organization, which is how you populate an
  organization switcher in the first place.
- Every org-scoped hook resolves to
  `error.code === "ORGANIZATION_REQUIRED"` **without making a request**. No
  wasted round trip, no confusing 400 in the network tab.

`workspaceId` is a filter on `useDevices()` and a required field on device
registration. It is sent on nothing else. Note that an out-of-organization
workspace id yields an **empty page**, not an error, so an empty device list
never distinguishes "no devices" from "wrong workspace".

Changing either prop refetches the REST hooks. It does not disturb the live
sockets, which are keyed by device.

## The three credential flows

This is the part worth reading twice. The three planes authenticate in three
different ways, and they fail independently.

| Plane          | Credential                                    | How                                                                                                     |
| -------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| REST           | `Authorization: Bearer <id token or xg_ key>` | Sent by `@xorgate/sdk` on every request, plus the tenancy headers.                                      |
| Live telemetry | SigV4 over WebSocket                          | ID token to Identity Pool credentials, then a hand-rolled presigned WSS URL, after `POST /live/access`. |
| Live video     | SigV4                                         | ID token to Identity Pool credentials, then the signaling client and a WebRTC viewer session.           |

<Steps>

<Step>

**REST** is the simple one. The token or key goes in `Authorization`,
`X-Organization-Id` goes on every request, `X-Workspace-Id` goes on the two
places it means something.

</Step>

<Step>

**Live telemetry** in FIRST-PARTY mode needs an extra step nothing else does.
AWS IoT authorizes Cognito identities through an **attached IoT policy**, not
through the IAM role on the credentials. So before the first connect, the SDK
calls `POST /live/access`, which attaches the browser policy to the **caller's
own** Cognito identity.

The two vended-credential modes skip the attach entirely: their authorization
is the inline session policy on the credentials, which allows connecting only
with an `xgl-`-prefixed client id and subscribing only to the credential's own
tenant-scoped telemetry topic. The SDK obeys both rules for you; they are worth
knowing because violating either by hand surfaces as a bare
`Connection refused: Not authorized` with nothing distinguishing the cause.

That is why `@xorgate/sdk` has no method for it and this package does: an
endpoint that acts on the identity of whoever calls it is meaningless from a
server. It is idempotent, so calling it on every page load is fine, and the SDK
does exactly that rather than trying to remember.

Its response carries the `identityId`, which the SDK then uses as the prefix of
the MQTT client id: connect is scoped to `client/<identityId>*`, so any other
client id is refused. The SDK appends a random suffix, because a single page
opens several connections and two tabs of the same user share one identity id.

Then it mints Identity Pool credentials and builds a presigned WSS URL by hand.
Two quirks make that hand-rolled rather than a call into
`@aws-sdk/signature-v4`, and both survive into the SDK:

- IoT signs a GET with **only** the `host` header against service
  `iotdevicegateway`, and `X-Amz-Security-Token` must be appended to the query
  string **after** signing. The device gateway rejects the handshake if the
  session token is inside the signed canonical query, which is the opposite of
  what most AWS services want.
- mqtt.js rebuilds the WebSocket URL from host and path and **drops the query
  string**, which would strip every SigV4 parameter and earn a 403. The
  connection passes `transformWsUrl: () => url` to force the full presigned URL
  through.

</Step>

<Step>

**Live video** is the easy one by comparison. The video plane authorizes with
plain IAM and SigV4, so there is no separate grant step. The SDK mints the same
Identity Pool credentials, resolves the channel's viewer endpoints, fetches the
ICE server configuration, and runs a WebRTC viewer session.

</Step>

</Steps>

## The live plane is not a tenant boundary yet

<Callout type="warn" title="Live READ scope is org-blind">

In FIRST-PARTY mode, what the browser may subscribe to and what it may view are
both scoped to "any authenticated user", not to the devices in your
organization. **Any signed-in user of this platform can
subscribe to any device's live telemetry topic and open a viewer on any device's
video channel.**

The REST API is not affected. Every REST endpoint enforces organization
membership; this is specific to the two live planes, which bypass the API
entirely and talk to AWS directly.

The consequence for you: live video and live telemetry are safe inside a single
trusted organization, which is what xorgate-web is, and are **not** ready for
third parties. Fixing it is Phase 6 P2 of the platform-readiness work, and it is
the same work item as credential vending, because both need per-identity policy
scoping.

Two things that used to be listed here are done. MQTT **connect** is scoped to
the caller's own Cognito identity, so a browser can no longer connect as a
device and displace it on the broker, nor collide with another user. And live
access can be taken away: [`DELETE /live/access`](/api-reference/live/revoke-live-access)
detaches the policy, and losing your last organization membership detaches it
automatically.

</Callout>

`useLivePlane()` tells you whether the live plane is reachable at all, so a page
can render one honest banner instead of three broken tiles.

```tsx
import { useLivePlane } from "@xorgate/react"

function LiveBanner() {
  const { available, reason } = useLivePlane()
  if (available) return null
  return <p role="status">Live view is unavailable ({reason}).</p>
}
```

`reason` is one of `"no-live-credentials"` (the auth mode cannot produce AWS
credentials), `"not-configured"` (the provider is missing one of the four AWS
fields), or `"not-provisioned"` (reported per device, not by this hook, when the
device has no realtime identity or no video channels).

## `platform`, the host runtime

Everything in this package that touches the host runtime goes through one
optional `platform` prop, and **every slot defaults to the browser**, so a web
app never passes it. It exists so React Native can supply its own runtime
without forking the session, feed and replay logic.

<TypeTable
  type={{
    createWebRtcPlatform: {

    },
    mqttConnect: {
      type: 'TelemetryFeedDeps["connect"]',

    },

Each slot is resolved at its point of use rather than materialised into a
default object on the provider, which is what keeps a page that mounts no video
from pulling the WebRTC, AWS and mqtt code into its entry chunk.
`browserPlatform()`, `browserSubscribeWake()` and `browserRandomId()` are
exported if you want to wrap one.

<Callout
  type="info"
  title="On React Native, the provider fills this in for you"
>
  [`XorgateNativeProvider`](/frontend-sdk/react-native) is `XorgateProvider`
  with all four slots already native. Building an adapter for some other host?
  The seams are `useLiveVideoSession`, `useReplayPlayerCore` + `attachLane`, the
  `ReplayEngine` interface, and `createWebRtcPlatform(overrides)` — the browser
  hooks are thin wrappers over the same cores.
</Callout>

## Escape hatches

`useXorgate()` returns the underlying `@xorgate/sdk` client. Use it for anything
the hooks do not model, for imperative calls in event handlers, and as the
`queryFn` if you would rather drive fetching with react-query or SWR.

```tsx
import { useXorgate } from "@xorgate/react"

function RebootButton({ deviceId }: { deviceId: string }) {
  const xg = useXorgate()
  return <button onClick={() => xg.devices.reboot(deviceId)}>Reboot</button>
}
```

`useLiveCredentials()` returns the credentials the live hooks resolved, so a
consumer can drive an AWS client of its own with the same session instead of
building a parallel credential path.
