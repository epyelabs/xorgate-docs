<Callout title="What a key can and cannot do">
  A key authenticates the organization-scoped REST surface at its own `role`
  (default `member`). It cannot reach the four person-scoped operations and
  cannot write the device-model catalog, but it CAN vend live-plane credentials
  for a workspace. `scope` is validated on write and still never enforced. See
  [Authentication](/backend-sdk/authentication).
</Callout>

## `create(input)`

```ts
const { apiKey, plaintextKey } = await xg.apiKeys.create({
  name: "alocate-backend",
  scope: "cloud",
  role: "member", // the default; caps at your own role
  expiresAt: "2027-01-01T00:00:00Z", // optional, omit for never
})

await secrets.put("XORGATE_API_KEY", plaintextKey)
console.log(apiKey.id, apiKey.createdAt)
```

<Callout type="warn" title="plaintextKey is shown exactly once">
  Only the SHA-256 is stored. There is no endpoint that returns a key again, so
  a lost key is replaced, never recovered. Write it to your secret store in the
  same function that creates it, and never log the return value of `create()`
  whole.
</Callout>

Owner or admin.

## `list(params?)`

Newest first by default, metadata only; the hashed key is never returned.
Paginated with the [shared list dialect](/backend-sdk/pagination);
`listAll()` is the guaranteed-complete form.

```ts
for (const key of await xg.apiKeys.list()) {
  console.log(key.name, key.scope, key.createdAt, key.lastUsedAt)
}
```

`lastUsedAt` is a real signal. Every request a key authenticates stamps it, and
it has been observed advancing within seconds of a key's first use. The write is
throttled and fire-and-forget, so treat it as a liveness **hint** for finding
keys nobody holds any more, not as an audit trail: a key used a minute ago may
still read as used five minutes ago.

(This paragraph used to say the column was always null. That stopped being true
when API keys became verifiable, and it was corrected once the SDK's integration
suite watched it advance against production.)

## `delete(id)`

```ts
await xg.apiKeys.delete(apiKey.id)
```

A hard delete, not a revocation: the row is removed and `revokedAt` is never set
by this call. `ApiKey.revokedAt` exists in the schema and stays null.

It also destroys **every session token minted from this key**, immediately. That
cascade is the only way to kill a live session token, which makes this the
emergency stop for a leaked client credential. It also means the order matters:
mint the replacement key first if the integration has to keep working.

Rotation is therefore manual and ordered: mint the new key, deploy it
everywhere, confirm, then delete the old one. There is no grace period and no
overlap window the platform manages for you.

Owner or admin.

## The snake_case envelope

This is the one resource where the SDK's normalization is worth stating
explicitly, because you will see the difference the moment you compare against a
raw `curl`.

| Wire                                              | SDK                        |
| ------------------------------------------------- | -------------------------- |
| `{ "api_keys": [...] }`                           | `ApiKey[]`                 |
| `{ "api_key": {...}, "plaintext_key": "xg_..." }` | `{ apiKey, plaintextKey }` |

The envelope keys mirror their Postgres table name. They stay that way on the
wire deliberately, and the
[API reference](/api-reference/api-keys) documents them truthfully. The SDK
is the layer that translates, so a database naming detail does not reach your
code. `device_model` / `device_models` is the same story, on
[Device models](/backend-sdk/resources/device-models).

Everything **inside** those envelopes is already camelCase on the wire. Only the
envelope keys differ.
