The largest resource module. It covers the device row, its configuration, the
commands you can send it, and its AWS IoT identity.

## Listing

```ts
list(params?: ListDevicesParams): Promise<Page<Device>>
iterate(params?): AsyncIterableIterator<Device>
listAll(params?): Promise<Device[]>
```

This is one of the three paginated endpoints, so `list()` returns
`{ items, page }` rather than an array. See
[Pagination](/backend-sdk/pagination).

```ts
const page = await xg.devices.list({ status: "online", sort: "lastSeenAt" })
console.log(`${page.items.length} of ${page.page.total}`)

for await (const device of xg.devices.iterate({ workspaceId: yardId })) {
  console.log(device.serial, device.status, device.lastSeenAt)
}
```

## `get`, `create`, `update`, `delete`

```ts
get(id: string): Promise<Device>
create(input: CreateDeviceInput): Promise<Device>
update(id: string, input: UpdateDeviceInput): Promise<Device>
delete(id: string): Promise<void>
```

### `create(input)`

```ts
const device = await xg.devices.create({
  workspaceId: yardId, // in the BODY, not the header
  deviceModelId: model.id,
  serial: "XG-0042", // unique within the workspace
})
```

This creates the **row only**. The device has no IoT identity until
`provision()`, and no agent until someone installs one. For onboarding real
hardware, use the
[registration code flow](/backend-sdk/resources/device-registrations)
instead, which does all three in one pass.

### `update(id, input)`

`UpdateDeviceInput` has one field: `name`. That is deliberate.

```ts
await xg.devices.update(device.id, { name: "Excavator 12" })
```

`status` and `lastSeenAt` are machine-managed by telemetry ingest, the MQTT
last-will and the offline sweeper. The API rejects writing them with a `400`, so
the SDK does not offer them. Configuration moved to `patchConfig()` and
`patchUiPrefs()`; the API still accepts a handful of deprecated per-namespace
fields on this route for a transition window, and the SDK does not expose those
either.

### `delete(id)`

`owner` or `admin`. Final and thorough: it cascades the device's rows (identity,
video channel rows, media and telemetry sessions, workflow attachments and runs,
webhook routes) and tears down the AWS side (the IoT thing and its X.509
certificate, the KVS signaling channels, the uploaded media and telemetry
objects, the FK-less telemetry history). There is no soft delete and no restore.

<Callout title="To keep the device and drop only its history, purge instead">
  `delete()` is a decommissioning: the device has to be re-enrolled afterwards.
  [`purges`](#purge-data) removes what the device recorded and leaves it
  enrolled and running.
</Callout>

## Configuration

Device configuration is one namespaced document. Writing it bumps a revision and
publishes the whole document as a retained MQTT message; the device applies
anything newer than its last-applied revision.

```ts
getConfig(id: string): Promise<DeviceConfigView>
patchConfig(id: string, patch: DeviceConfigPatch): Promise<Device>
mergeConfig(id: string, patch: DeviceConfigPatch): Promise<Device>
patchUiPrefs(id: string, patch: DeviceUiPrefsPatch): Promise<Device>
```

### `getConfig(id)`

There is no `GET /devices/{id}/config` route. This is a convenience view over a
full device read, so it costs exactly one `get()` and you can use `get()`
instead if you want the rest of the device anyway.

```ts
const cfg = await xg.devices.getConfig(deviceId)

cfg.config // the desired document
cfg.configRev // monotonic revision
cfg.reportedConfig // what the device says is in force, or null
cfg.pending // configRev > reportedConfig.rev, on an online device
```

`pending` is computed by the SDK, because there is no `pending` state on the
wire and every consumer was deriving it the same way.

`reportedConfig` is `null` until the device has reported at least once. Its
`effective` block holds post-clamp values actually in force, and its `status`
block carries a per-namespace `applied` / `adjusted` / `rejected` verdict.
Several keys inside `effective` are **reported-only** and can never be written:
`agent.mode`, `sim`, `uplink`, `apn`, `cameras`. A device cannot be told its own
ICCID.

### `patchConfig(id, patch)`

```ts
const device = await xg.devices.patchConfig(deviceId, {
  recording: {
    video: { enabled: true, preset: "1080p15-2mbps", segmentSeconds: 60 },
  },
  timeSync: { offlineSources: true },
})

console.log(device.configRev) // bumped
```

The namespaces are `gnssAntBias`, `imuMount`, `recording`, `lteRecovery`,
`timeSync`, `cellular`, `cameraMount`, `simulation`, `obd` and `cameraSensors`.
The last three are accepted only for the devices they apply to; the
[configuration reference](/device-sdk/configuration-reference#layer-2-cloud-managed-settings)
describes each.

<Callout type="warn" title="Each namespace is replaced WHOLE. This has broken real hardware.">

A present namespace is validated and replaced entirely, because the device
replaces namespaces the same way. Writing only the `recording.video` block when
`recording.telemetry` was already configured **drops** the telemetry block.

This is not hypothetical. Bringing production up, a single
`patchConfig(id, { recording: { telemetry: { enabled: true } } })` erased the rest
of that device's `recording` namespace, including a per-camera flag that was
suppressing a camera which does not work on that unit. The device went from zero
errors to a start/fail loop every sixty seconds, and the only way back was to
re-send the whole namespace from a backup. The request looked like a merge. It
was not.

Read the current value, merge, then write:

```ts
const { config } = await xg.devices.getConfig(deviceId)
await xg.devices.patchConfig(deviceId, {
  recording: { ...config.recording, video: { ...config.recording?.video, enabled: true } },
})
```

Or let `mergeConfig()` below do exactly that for you, which is what you almost
always want.

</Callout>

Pass `null` to revert a namespace to the device's own defaults:

```ts
await xg.devices.patchConfig(deviceId, { cellular: null })
```

An empty object is **not** an erase; it is a `400`. `null` is the erase.

Two failure modes worth handling separately:

- `CONFIG_PUBLISH_FAILED` (502) means the write **succeeded** and delivery
  failed. Do not retry. See [Errors](/backend-sdk/errors).
- A device whose `reportedConfig.effective` has no `apn` block predates the APN
  rollback machinery. Writing the `cellular` namespace to it has no safety net,
  so a bad APN takes the device off the network. Check for the block first.

### `mergeConfig(id, patch)`

Read-modify-write. It fetches the device, deep-merges your patch into the current
config, and sends each **touched namespace back whole**, so the smallest possible
expression of "turn X on" stops being the most dangerous one.

```ts
// Enables telemetry recording and changes NOTHING else in `recording`.
await xg.devices.mergeConfig(deviceId, {
  recording: { telemetry: { enabled: true } },
})
```

Semantics worth knowing:

- `null` **at the namespace level** still means "revert this namespace to the
  device defaults", and is passed through unmerged, exactly as in
  `patchConfig()`.
- `null` **below** a namespace deletes that one key from the merged result. It is
  the only way to remove a single setting without rewriting its siblings.
- Arrays replace rather than concatenate. Every array in the config contract is a
  complete list rather than an accumulator.
- It costs one extra `GET`.

<Callout type="warn" title="Safer, not atomic">
  The API has no `If-Match` on `configRev`, so two writers racing on the same
  device still clobber each other and the loser is never told. `mergeConfig()`
  removes the self-inflicted case, where your own partial write erases your own
  earlier one. It cannot remove the concurrent case, and nothing in the API can
  today.
</Callout>

### Watching a config change land

A config change has no [webhook](/platform-concepts/webhooks), so this is a poll. The pattern:

```ts
await xg.devices.patchConfig(deviceId, { gnssAntBias: true })

for (let i = 0; i < 20; i++) {
  const cfg = await xg.devices.getConfig(deviceId)
  if (!cfg.pending) break
  await new Promise((r) => setTimeout(r, 3_000))
}
```

An offline device never converges, because it is not listening. The retained
message waits for it and is applied on reconnect.

### Camera sensors

{/* TODO(sdk-version): confirm the `@xorgate/sdk` release number below once the release that carries the camera types is published. */}

Which image sensor sits on each camera port is the `cameraSensors` namespace.
It is typed from `@xorgate/sdk` 0.18.0, together with the device's per-port
answer in `reportedConfig.effective.cameras`. It needs a device on the Rust
agent, 0.2.0 or newer; for any other device the write throws `BAD_REQUEST` with
a message that says why.

```ts
// Replaced whole: send every port that should stay managed. A port left out
// goes back to unmanaged; `{ sensor: "none" }` declares it empty.
await xg.devices.patchConfig(deviceId, {
  cameraSensors: {
    cameras: {
      cam0: { sensor: "imx708" },
      cam1: { sensor: "imx290", options: { clockFrequency: 74250000 } },
    },
  },
})

// Takes effect at the next boot. The device says what is really on each port.
const device = await xg.devices.get(deviceId)
const cameras = device.reportedConfig?.effective.cameras ?? {}
for (const [port, camera] of Object.entries(cameras)) {
  console.log(port, camera.verdict, camera.detail)
}
if (Object.values(cameras).some((c) => c.verdict === "reboot-required")) {
  await xg.devices.reboot(deviceId)
}

// Back to unmanaged on every port.
await xg.devices.patchConfig(deviceId, { cameraSensors: null })
```

The device's report follows the write by a few seconds, so in real code wait
for it before reading the verdicts, as in
[Watching a config change land](#watching-a-config-change-land). The sensors,
their options, and what each verdict means are on
[Cameras](/device-sdk/cameras) and
[Camera status](/device-sdk/camera-status).

### `patchUiPrefs(id, patch)`

Cloud-only presentation preferences: `activeStreamsViewType` and `imuView`.
Nothing here reaches the device, nothing is published, and `configRev` is not
bumped. `null` resets a preference to its default.

```ts
await xg.devices.patchUiPrefs(deviceId, { activeStreamsViewType: "map" })
```

## Transfer

```ts
transfer(id: string, input: TransferDeviceInput): Promise<TransferResult>
previewTransfer(id: string, input: TransferDeviceInput): Promise<TransferPreview>
transferMany(ids: readonly string[], input: TransferDeviceInput): Promise<BulkTransferItem[]>
```

`owner` or `admin`. A device has no organization of its own — it points at a
workspace, and the organization is derived — so moving a device between
workspaces and moving it between organizations are the **same call**.

/>

### `previewTransfer(id, input)` first

The dry run behind a confirmation. It writes nothing, and **blockers are
returned rather than thrown**, so a dialog can explain a refusal without
provoking it.

```ts
const preview = await xg.devices.previewTransfer(deviceId, { workspaceId: dest })

if (preview.blockers.length > 0) {
  for (const b of preview.blockers) console.log(b.code, b.message)
  return
}
for (const a of preview.workflowAttachments) {
  console.log("will be detached:", a.templateName)
}
```

Blocker codes are `SAME_WORKSPACE`, `SERIAL_COLLISION` and
`TRANSFER_IN_PROGRESS` — the same conditions `transfer()` would throw as a `400`
or `409`. Everything else on the preview is context to render: counts of running
workflow runs, open recording sessions, and session tokens that will lose the
device.

`carriesHistory` is **always literally `true`**. Render it; do not branch on it.
It is there so a confirmation can state out loud that all telemetry history and
all recorded footage travel with the device, which across organizations is a
data-disclosure event and is the question anyone receiving a device actually
asks.

### `transfer(id, input)`

```ts
const { device, transfer } = await xg.devices.transfer(deviceId, {
  workspaceId: dest,
})
```

<Callout title="Never gate this on `device.status`">
  Nothing on the device changes during a transfer: certificates and identity are
  untouched, and the tenancy is never written to disk. An offline device has its
  new tenancy staged in the cloud and adopts it on its next connect. **Offline
  is a normal success**, reported through `transfer.warnings`, not an error.
</Callout>

A `200` is not uniformly clean. Two fields carry the nuance:

- **`adoption`** has three values, not two. `"pending"` right after a transfer
  is **normal** — the ownership change is already complete and authoritative in
  the cloud. `"confirmed"` means the device has reported publishing under the
  new tenancy. `"unknown"` means it has never reported a telemetry scope at all,
  which is an agent older than `v0.0.6`, not a failure to converge.
- **`scopeAttributes: "failed"`** is a degraded success. The device moved and
  was told its new topic, but the broker was not told to allow it, so it falls
  back to the still-ingested legacy telemetry plane. A workspace-scoped vended
  credential sees nothing until any settings save re-asserts the attributes.

<Callout
  type="warn"
  title="`reportedConfig.rev` is not evidence, and neither is a device that is still publishing"
>
  A scope change deliberately does not bump the config revision, so the reported
  rev reads the same before and after. And AWS IoT resolves the policy's tenancy
  variables at **connect** time, so an established session keeps its old
  resolution and a botched transfer can look clean for hours before stranding on
  the next reconnect. `adoption` is the only honest signal.
</Callout>

`transfer.kvsChannelsRetagged` is not a per-device count. It counts video-channel
rows re-tagged across **both** workspaces the transfer touched, including other
devices' channels repaired on the way past, so it can legitimately exceed the
preview's `kvsChannels`. Do not render it as "N of this device's cameras moved".

### `transferMany(ids, input)` is a client-side loop

```ts
const results = await xg.devices.transferMany([a, b, c], { workspaceId: dest })
for (const item of results) {
  if (item.ok) console.log(item.deviceId, "moved")
  else console.log(item.deviceId, "failed:", item.error?.code)
}
```

There is no bulk route, and this does not pretend otherwise. It runs
**sequentially on purpose**: each transfer publishes a retained MQTT message and
writes AWS IoT thing attributes, and a parallel fan-out is a good way to find the
account's control-plane limits during an operation whose design depends on two
writes staying adjacent.

It does not stop at the first failure and it is **not atomic**. A partial result
is the honest outcome, and there is nothing to roll back: a failed transfer has
already rolled itself back. Same-organization only in practice — a
cross-organization move is a handover, done one device at a time.

### Failures

`SAME_WORKSPACE` is a `400`. `SERIAL_COLLISION`, `TRANSFER_IN_PROGRESS` and
`CONCURRENT_MODIFICATION` are `409`s. `TRANSFER_FAILED` is a `502` meaning the
sequence was **rolled back and nothing changed**, so it is safe to retry — the
one write on this API that is.

A device or workspace outside the caller's reach is `404`, never `403`, because
confirming another tenant's workspace exists is itself a leak. Do not render it
as a permissions message; you do not know that it is one.

A workspace-scoped session token is refused with `403`: a transfer spans two
workspaces and such a token is confined to one by construction.

### Handing a device to an organization you are not in

Use [transfer offers](/backend-sdk/resources/transfer-offers). Background and
the full picture of what moves is in
[Device ownership and transfer](/platform-concepts/device-ownership); if your
app also renders the live plane, read
[Scope and transfers](/frontend-sdk/device-scope) before you ship.

## Purge data

```ts
purges.preview(deviceId: string): Promise<DevicePurgePreview>
purges.create(deviceId: string, params: DevicePurgeCreateParams): Promise<DevicePurge>
purges.get(deviceId: string, purgeId: string): Promise<DevicePurge>
purges.list(deviceId: string, params?: ListDevicePurgesParams): Promise<DevicePurge[]>
```

`owner` or `admin`, organization-wide. The companion of a transfer: a transfer
moves every reading and every recorded second with the device and purges
nothing, and `delete()` takes the device along with its history.
`xg.devices.purges` wipes the history and **keeps the device enrolled**: its
row, identity and certificate, live video channels, configuration, webhook
routes and latest-value cache stay, and the agent keeps running.

What goes is chosen per scope, and the scopes combine in one request:

<TypeTable
  type={{
    workflows: {
      type: "scope",
      description:
        "Every attached workflow is detached; every production run of this device (including runs of workflows detached earlier) goes with its steps, events and S3 artifacts. Runs still executing are stopped. The organization's templates and their simulation runs are untouched.",
    },
    telemetry: {
      type: "scope",
      description:
        "Recorded telemetry sessions, their segments and overview artifacts, the ingest log, and every stored reading. The latest-value view the roster reads stays.",
    },
    media: {
      type: "scope",
      description:
        "Recorded video sessions, their segments and thumbnails. Live channels stay.",
    },
  }}
/>

Everything older than the moment of the request (the purge's `cutoff`) is
removed; what the device uploads afterwards is kept. There is no undo.

<Callout type="warn" title="A recording in progress is cut">
  An open telemetry or video session that started before the cutoff is deleted,
  and the segments the device uploads afterwards re-create it as a partial
  session. Stop recording before you purge.
</Callout>

### `purges.preview(deviceId)` first

What a purge would remove, as of now, for the confirmation dialog. It writes
nothing. Stored readings come back as a **time span** rather than a count,
because counting them is the expensive part of the purge itself.

```ts
const preview = await xg.devices.purges.preview(deviceId)
console.log(
  `${preview.workflows.attachments} workflows, ${preview.workflows.runs} runs, ` +
    `${preview.telemetry.sessions} telemetry sessions ` +
    `(readings ${preview.telemetry.readingsFrom} to ${preview.telemetry.readingsTo}), ` +
    `${preview.media.sessions} video sessions`,
)
```

`readingsFrom` and `readingsTo` are `null` when the device has no stored
readings.

### `purges.create(deviceId, { scopes })`, then poll

The API answers `202` with the purge row in `status: "queued"` and a worker does
the deleting in resumable chunks. Nothing has been removed when `create()`
returns. Poll `get()` every few seconds until `status` is `succeeded` or
`failed`.

```ts
let purge = await xg.devices.purges.create(deviceId, {
  scopes: ["workflows", "telemetry", "media"],
})

while (purge.status === "queued" || purge.status === "running") {
  await new Promise((r) => setTimeout(r, 2_500))
  purge = await xg.devices.purges.get(deviceId, purge.id)
}

if (purge.status === "failed") throw new Error(`purge failed: ${purge.error}`)
console.log(purge.counts.runs, purge.counts.readings, purge.counts.mediaSessions)
```

### Failures

One purge per device at a time, and none while a cross-organization transfer
offer for the device is open, because the handover detaches attachments itself.

```ts
try {
  await xg.devices.purges.create(deviceId, { scopes: ["telemetry"] })
} catch (e) {
  if (!isXorgateError(e)) throw e
  switch (e.code) {
    case "PURGE_IN_PROGRESS":
      // `e.details.purgeId` names the one still running; poll it instead.
      break
    case "TRANSFER_PENDING":
      // Cancel or resolve the transfer offer first.
      break
    case "PURGE_DISPATCH_FAILED":
      // Recorded but never queued. Nothing was deleted. Safe to retry.
      break
    case "WORKSPACE_SCOPED":
      // A workspace-scoped session token cannot purge; use an org-wide credential.
      break
    default:
      throw e
  }
}
```

`PURGE_IN_PROGRESS` and `TRANSFER_PENDING` are `409`s. `PURGE_DISPATCH_FAILED`
is a `502` that means the purge row was recorded but never queued: the row is
marked `failed`, nothing was deleted, and the call is safe to retry. An empty or
unknown scope is a `400`, a device outside your reach a `404`, and a
workspace-scoped session token a `403 WORKSPACE_SCOPED` whatever its role.

### `purges.list(deviceId, { limit? })`

The audit trail: who purged what, and when. Newest first, at most 20 (`limit`
defaults to 10), and **not paginated**: it returns an array.

```ts
const [latest] = await xg.devices.purges.list(deviceId, { limit: 1 })
if (latest) console.log(latest.status, latest.scopes, latest.requestedBy, latest.finishedAt)
```

## Commands

```ts
reboot(id): Promise<CommandAccepted>
powerOff(id): Promise<CommandAccepted>
refreshState(id): Promise<CommandAccepted>
updateAgent(id): Promise<CommandAccepted>
```

<Callout type="warn" title="202 means delivered to the broker, not done">

All four resolve when the command reaches the MQTT broker. None of them tells
you the device carried it out. Commands are **not retained**, so the device must
be online: an offline device is a `409 CONFLICT` and there is nothing to pick up
later.

Each carries a `requestId` the device refuses to execute twice, and an
`expiresAt` (epoch ms) after which it refuses the command outright.

</Callout>

```ts
const ack = await xg.devices.reboot(deviceId)
console.log(ack.command, ack.requestId, new Date(ack.expiresAt))
```

How to observe each outcome, since the ack cannot tell you:

| Method         | Role        | Observe by                                                                                                    |
| -------------- | ----------- | ------------------------------------------------------------------------------------------------------------- |
| `reboot`       | owner/admin | `status` goes `offline` then `online`. Expires 60 s after issue.                                              |
| `powerOff`     | owner/admin | `status` goes `offline` and stays. **Not remotely recoverable**: someone has to physically power it on.       |
| `refreshState` | member      | `reportedAt` advances. Rate-limited on the device to roughly one per 30 s; a re-probe takes up to about 45 s. |
| `updateAgent`  | owner/admin | `agentVersion` changes. Unchanged after the device returns online means the install failed and rolled back.   |

`updateAgent()` installs the latest published build. There is no version
parameter. The device drops offline for a minute or two. Pressing it twice is
harmless: an already-running one-shot coalesces.

### `latestAgentBuild()`

```ts
latestAgentBuild(): Promise<AgentBuild | null>
```

Fleet-wide, not per device: the build a device update would install for this
stage. `null` means CI has published no manifest yet, which is "latest unknown"
rather than an error, and the SDK returns null rather than throwing on the
underlying 404.

```ts
const latest = await xg.devices.latestAgentBuild()
const device = await xg.devices.get(deviceId)

const upToDate = latest !== null && device.agentVersion === latest.version
```

<Callout type="warn" title="Compare by string equality only">
  Build versions are CI short shas on dev and release tags on prod. Shas do not
  order, and a sha and a tag are not comparable. Never use `<` or a semver
  compare here.
</Callout>

## Identity and provisioning

```ts
identity(id: string): Promise<DeviceIdentity | null>
provision(id: string): Promise<DeviceProvisioning>
videoChannels(id: string): Promise<VideoChannel[]>
```

### `identity(id)`

Non-secret fields of the X.509 identity: thing name, certificate id, policy,
role alias, status. Returns `null` when the device exists but is not
provisioned, so a clean "not provisioned" state does not need error handling.

```ts
const identity = await xg.devices.identity(deviceId)
if (identity === null) {
  // Never provisioned.
}
```

It reads the database and does not call AWS IoT, so a certificate revoked out of
band still reads `active` here.

### `provision(id)`

Mints an AWS IoT thing and X.509 certificate, attaches the device policy, and
creates one video channel per declared video stream.

<Callout type="warn" title="The credential bundle is returned exactly once">

`certificatePem` and `privateKey` are shown only in this response and the
private key is never stored server-side. Persist them on the device
immediately. A second call for an already-provisioned device is a `409`, and
certificate rotation does not exist yet, so a lost key means deleting and
re-creating the device.

Never log a `DeviceProvisioning` whole.

</Callout>

```ts
const bundle = await xg.devices.provision(deviceId)

bundle.iot.dataEndpoint // MQTT over mTLS, port 8883
bundle.iot.credentialEndpoint // role-alias credential provider
bundle.kvs.channels // one per declared video stream
bundle.mqtt.telemetryTopic // xorgate/devices/{id}/telemetry
```

If `kvs.channels` comes back empty for a model that declares cameras, its
`ioCapabilities` failed the provisioning parse. That is the failure the
[device-model validation](/backend-sdk/resources/device-models) exists to
prevent, and this response is the first place it becomes visible.

Owner or admin.

### `videoChannels(id)`

Channel metadata only, one entry per provisioned video stream, no credentials.
An empty array means the device is not provisioned, which is a `200` rather than
a `404`.

This is what a **browser** needs to join a live stream as a viewer, and the
viewer itself is not part of this SDK. See
[What this SDK does not cover](/backend-sdk/not-covered).

Maps to the [Devices endpoints](/api-reference/devices) and
[Live](/api-reference/live).
