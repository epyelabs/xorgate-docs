## Which endpoints paginate

Since the platform's API-productization release: **every list endpoint**, and
they share one dialect. The paginated collections are devices, media sessions
(and runs), telemetry readings, organizations, memberships, workspaces, device
models and API keys.

Two deliberate exceptions return their whole (small, bounded) collection with
no `page` block: a device's video channels and a session's segments. Neither
has an `iterate()`, which is the SDK's way of saying so.

<Callout title="Older SDK versions keep working">
  Versions before 0.2.0 fetched the five newly paginated collections in one
  request and did not send `limit`. The server's default page (100 rows) covers
  every realistic tenant today, and the SDK tolerates a response with or
  without a `page` block in both directions. Upgrade to 0.2.0 for
  guaranteed-complete `listAll()` past 100 rows.
</Callout>

## Three ways to read a collection

Every collection, paginated or not, offers the same three:

```ts
// 1. One page.
const page = await xg.devices.list({ status: "online", limit: 50 })
page.items // Device[]
page.page // PageMeta

const workspaces = await xg.workspaces.list({ limit: 50 }) // Workspace[]

// 2. Iterate. Fetches pages lazily as you consume them.
for await (const device of xg.devices.iterate({ status: "online" })) {
  console.log(device.serial)
}

// 3. Drain into memory. Convenience over iterate(); the same requests.
const all = await xg.devices.listAll({ status: "online" })
```

The return type of `list()` differs between the two shapes, for historical
reasons that are now load-bearing:

- The original three (devices, sessions, readings): `Promise<Page<T>>`, an
  object with `items` and `page`.
- The five that gained pagination later (organizations, memberships,
  workspaces, device models, API keys): still `Promise<T[]>` — one request's
  items, up to `limit` (default 100). Changing their return type would have
  broken every existing consumer for collections that rarely exceed a handful
  of rows.

<Callout title="iterate() is the portable choice">
  `iterate()` and `listAll()` have identical signatures on both shapes, walk
  the server's `page` blocks, and are the guaranteed-complete forms. Reach for
  `list()` when one page is genuinely what you want.
</Callout>

## The list dialect

The paginated endpoints accept the same parameters.

<TypeTable
  type={{
    limit: {
      type: "number",
      description:
        "Page size. The maximum is 500 everywhere the shared dialect applies; a value above it is a 400, never a silent clamp.",
      default: "100",
    },
    offset: {
      type: "number",
      description:
        "Rows to skip. An offset past the end is an empty page, not an error.",
      default: "0",
    },
    order: { type: '"asc" | "desc"', default: '"desc"' },
    sort: {
      type: "string",
      description:
        "Sort column. Per-endpoint enum; anything else is a 400. See each method.",
    },
    from: {
      type: "string | Date",
      description: "Range start, inclusive. ISO-8601 when a string.",
    },
    to: { type: "string | Date", description: "Range end, exclusive." },
  }}
/>

One outlier: `xg.telemetry.recent()` is not a paginated endpoint, but it takes
a `limit` with the same reject-not-clamp behaviour and a higher maximum, 5000.

The SDK passes your value through and does not pre-clamp, so the platform's
answer is the one you see. (Before API productization the paginated endpoints
clamped silently; they now answer 400, so a too-large `pageSize` fails loudly
instead of quietly shortening pages.)

## `PageMeta`

```ts
interface PageMeta {
  limit: number // echoes the request
  offset: number
  order: "asc" | "desc"
  total: number // exact match count under the same filters
  totalIsCapped?: boolean // telemetry readings only
  coveredFrom?: string // telemetry readings only
  coveredTo?: string // telemetry readings only
}
```

`total` is the exact count of matching rows under the same filters, on every
endpoint except one.

### The telemetry readings cap

`xg.telemetry.readings()` is the exception, because an exact count over the
telemetry table times out. Its `page.total` is **bounded at 10,000 distinct
timestamps**. When more match:

- `page.totalIsCapped` is `true`,
- only the first 10,000 in the requested `order` are addressable, newest first
  by default,
- `page.coveredFrom` and `page.coveredTo` give the ISO span of that addressable
  slice.

To reach beyond it, narrow `from` and `to`. An `offset` past the cap returns an
empty page rather than an error, so a naive loop terminates quietly having read
part of the data.

## Observing pages while iterating

`iterate()` yields items, which means the `page` block is invisible. That
matters exactly once: when you need to know that a cap was hit. Pass `onPage`.

```ts
let capped = false

for await (const reading of xg.telemetry.iterateReadings(deviceId, {
  from: yesterday,
  to: now,
  metric: ["gps.lat", "gps.lon"],
  onPage: (page) => {
    capped ||= page.totalIsCapped === true
  },
})) {
  track.push(reading)
}

if (capped) {
  // More than 10,000 samples matched. Narrow the window and run again.
}
```

`onPage` is called once per underlying HTTP request, before that page's items
are yielded. It is also the honest way to build a progress indicator, since
`page.total` is only knowable after the first request.

## Cost and safety

`iterate()` and `listAll()` make one request per page, sequentially. They do not
parallelize, because `offset` pagination over a table that is still being
written gives inconsistent results when pages are fetched out of order, and
because the platform throttles at the gateway (a parallel fan-out is a good way
to meet the 429).

- Use `pageSize` to trade requests against payload size:
  `xg.devices.iterate({ pageSize: 500 })`. Above 500 the platform answers a
  400.
- Pass a `signal` to stop early. Abandoning a `for await` loop with `break` also
  stops it: the iterator is lazy and issues no further requests.
- `listAll()` holds the entire collection in memory. For device counts in the
  thousands, or for telemetry, prefer `iterate()`.
