The platform has two kinds of collection, and the SDK does not pretend
otherwise.

## Which endpoints paginate

Exactly three, and they share one dialect:

| SDK method                 | Endpoint                                                                                              | Page unit                            |
| -------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------ |
| `xg.devices.list()`        | [`GET /devices`](/docs/api-reference/devices/list-devices)                                            | devices                              |
| `xg.media.sessions.list()` | [`GET /devices/{id}/sessions`](/docs/api-reference/media-sessions/list-media-sessions)                | sessions, or runs under `listRuns()` |
| `xg.telemetry.readings()`  | [`GET /devices/{id}/telemetry/readings`](/docs/api-reference/telemetry/get-device-telemetry-readings) | distinct timestamps                  |

Everything else returns its whole collection with **no `page` block at all**:
organizations, memberships, workspaces, device models, API keys, KVS channels and
a session's segments.

That is a property of the API, not a simplification here. Adding pagination to
the unpaginated list endpoints is on the platform-readiness backlog, and the
iterator below is designed so that change costs you nothing.

## Three ways to read a collection

Every collection, paginated or not, offers the same three:

```ts
// 1. One page (or the whole thing, when the endpoint does not paginate).
const page = await xg.devices.list({ status: "online", limit: 50 })
page.items // Device[]
page.page // PageMeta

const workspaces = await xg.workspaces.list() // Workspace[], no page block

// 2. Iterate. Fetches pages lazily as you consume them.
for await (const device of xg.devices.iterate({ status: "online" })) {
  console.log(device.serial)
}

// 3. Drain into memory. Convenience over iterate(); the same requests.
const all = await xg.devices.listAll({ status: "online" })
```

The return type of `list()` differs between the two kinds, and that is
deliberate:

- Paginated: `Promise<Page<T>>`, an object with `items` and `page`.
- Unpaginated: `Promise<T[]>`.

TypeScript catches the difference at compile time, which is the point. Making
both return `T[]` would let `await xg.devices.list()` quietly hand back the first
100 of 4,000 devices, and that is a bug you find in production.

<Callout title="iterate() is the portable choice">
  `iterate()` and `listAll()` have identical signatures on both kinds. Code
  written against them keeps working unchanged when the platform paginates the
  remaining endpoints, because the SDK is the only thing that has to learn about
  the new `page` block. Reach for `list()` when you genuinely want one page.
</Callout>

## The list dialect

The paginated endpoints accept the same parameters.

<TypeTable
  type={{
    limit: {
      type: "number",
      description:
        "Page size. Values above the endpoint maximum are silently CLAMPED, not rejected, so read page.limit back.",
      default: "100",
    },
    offset: {
      type: "number",
      description:
        "Rows to skip. An offset past the end is an empty page, not an error.",
      default: "0",
    },
    order: { type: '"asc" | "desc"', default: '"desc"' },
    sort: {
      type: "string",
      description:
        "Sort column. Per-endpoint enum; anything else is a 400. See each method.",
    },
    from: {
      type: "string | Date",
      description: "Range start, inclusive. ISO-8601 when a string.",
    },
    to: { type: "string | Date", description: "Range end, exclusive." },
  }}
/>

Two exceptions worth knowing, because they behave the opposite way:

- `xg.telemetry.readings()` **rejects** an out-of-range `limit` with a 400
  instead of clamping it. Its maximum is 500.
- `xg.telemetry.recent()` is not a paginated endpoint at all, but it takes a
  `limit` that also rejects rather than clamps. Its maximum is 5000.

The SDK passes your value through and does not pre-clamp, so the platform's
answer is the one you see.

## `PageMeta`

```ts
interface PageMeta {
  limit: number // the REQUEST value after clamping
  offset: number
  order: "asc" | "desc"
  total: number // exact match count under the same filters
  totalIsCapped?: boolean // telemetry readings only
  coveredFrom?: string // telemetry readings only
  coveredTo?: string // telemetry readings only
}
```

`limit` and `offset` echo the request after clamping, not what you asked for.
`total` is the exact count of matching rows under the same filters, on every
endpoint except one.

### The telemetry readings cap

`xg.telemetry.readings()` is the exception, because an exact count over the
telemetry table times out. Its `page.total` is **bounded at 10,000 distinct
timestamps**. When more match:

- `page.totalIsCapped` is `true`,
- only the first 10,000 in the requested `order` are addressable, newest first
  by default,
- `page.coveredFrom` and `page.coveredTo` give the ISO span of that addressable
  slice.

To reach beyond it, narrow `from` and `to`. An `offset` past the cap returns an
empty page rather than an error, so a naive loop terminates quietly having read
part of the data.

## Observing pages while iterating

`iterate()` yields items, which means the `page` block is invisible. That
matters exactly once: when you need to know that a cap was hit. Pass `onPage`.

```ts
let capped = false

for await (const reading of xg.telemetry.iterateReadings(deviceId, {
  from: yesterday,
  to: now,
  metric: ["gps.lat", "gps.lon"],
  onPage: (page) => {
    capped ||= page.totalIsCapped === true
  },
})) {
  track.push(reading)
}

if (capped) {
  // More than 10,000 samples matched. Narrow the window and run again.
}
```

`onPage` is called once per underlying HTTP request, before that page's items
are yielded. It is also the honest way to build a progress indicator, since
`page.total` is only knowable after the first request.

## Cost and safety

`iterate()` and `listAll()` make one request per page, sequentially. They do not
parallelize, because `offset` pagination over a table that is still being
written gives inconsistent results when pages are fetched out of order, and
because the platform has no rate limiting yet and a parallel fan-out is a good
way to discover that.

- Use `pageSize` to trade requests against payload size:
  `xg.devices.iterate({ pageSize: 500 })`.
- Pass a `signal` to stop early. Abandoning a `for await` loop with `break` also
  stops it: the iterator is lazy and issues no further requests.
- `listAll()` holds the entire collection in memory. For device counts in the
  thousands, or for telemetry, prefer `iterate()`.
