Every type here is exported from the package root and is shared with
`@xorgate/react`, so a value read on the server and a value read in the browser
have the same type. Where the SDK's type differs from the wire, the reason is
noted.

```ts
import type { Device, MetricName, ReplayManifest } from "@xorgate/sdk"
```

## Naming and normalization

Three rules cover every difference between these types and the raw API.

1. **Envelopes are unwrapped.** `{ devices, page }` becomes `Page<Device>`,
   `{ device }` becomes `Device`, `{ api_keys }` becomes `ApiKey[]`.
2. **Everything is camelCase.** The snake_case envelope keys (`api_keys`,
   `api_key` / `plaintext_key`, `device_model` / `device_models`) and the
   snake_case timestamps on `Organization` (`created_at`, `updated_at`) are
   normalized. Nothing else on the wire is snake_case. The normalization accepts
   **both** spellings, so the day the platform normalizes its own casing is a
   no-op here rather than the day every timestamp becomes `undefined`.
3. **Timestamps stay strings.** ISO-8601, exactly as returned, not `Date`
   objects. Parsing is lossy in one direction and opinionated in the other, and
   a string round-trips into JSON without a serializer. The one exception is the
   replay manifest, whose timestamps are epoch **milliseconds** upstream and stay
   numbers.

Parameters that take a time accept `string | Date`, so you are not forced to
format on the way in.

## Metrics

```ts
type MetricName = `${string}.${string}`

interface TelemetryReading {
  ts: string
  metric: MetricName
  value: number | null
  unit: string | null
}

interface LatestReading {
  metric: MetricName
  value: number | null
  unit: string | null
  ts: string
}

type LatestByMetric = Record<MetricName, LatestReading>
```

`group.field` is the platform's metric addressing scheme, and `LatestByMetric` is
its interop shape. Live MQTT telemetry, the REST latest endpoint and replayed
telemetry all produce it, which is what lets one renderer handle all three. If
you build any abstraction over telemetry, build it on these two.

## Tenancy

```ts
interface User {
  id: string // Cognito sub
  email: string
  name: string | null
  tier: "free" | "pro" | "team"
  role: "user" | "admin" // PLATFORM role
  createdAt: string | null // null through GET /me; see below
}

interface Organization {
  id: string
  name: string
  slug: string
  createdAt: string
  updatedAt: string
}

interface Membership {
  id: string
  userId: string
  organizationId: string
  role: "owner" | "admin" | "member" | "viewer"
  createdAt: string
}

interface MembershipWithUser extends Membership {
  user: Pick<User, "id" | "email" | "name"> | null
}

interface Workspace {
  id: string
  organizationId: string
  name: string
  slug: string
  description: string | null
  createdAt: string
  updatedAt: string
}
```

`User.role` is the **platform** role and gates device-model catalog writes only.
`Membership.role` is per organization and gates everything else. They are
unrelated, and confusing them is the most common cause of a surprising `403`.

`User.createdAt` is nullable because of one endpoint. `GET /me` builds its `user`
block from the request's own credential rather than serializing the row, so it
carries no timestamp at all. Typing it `string` would have been a lie in the only
place the type is observable.

## Device

```ts
interface Device {
  id: string // also the IoT thing name and MQTT client id
  workspaceId: string
  deviceModelId: string
  serial: string
  name: string | null
  agentVersion: string | null
  status: "provisioned" | "online" | "offline" | "decommissioned"
  lastSeenAt: string | null
  config: DeviceConfig
  configRev: number
  configUpdatedAt: string | null
  uiPrefs: DeviceUiPrefs
  reportedConfig: DeviceReportedConfig | null
  reportedAt: string | null
  createdAt: string
  updatedAt: string
}
```

`id` is load-bearing well beyond this type: it is the AWS IoT thing name, the
MQTT client id, and a path segment in every one of the device's MQTT topics and
S3 keys.

`status` and `lastSeenAt` are machine-managed, which is why they do not appear in
`UpdateDeviceInput`.

<Callout title="The deprecated fields are not in this type">
  The API still returns `firmwareVersion`, `gnssAntBias`,
  `activeStreamsViewType`, `imuMount`, `imuView`, `recordingConfig`,
  `lteRecoveryConfig` and `timeSyncConfig` at the top level of a device, all
  marked deprecated and all duplicating something in `config` or `uiPrefs`. The
  SDK omits them, so there is exactly one place to read each value. Use
  `xg.request()` if you need a deprecated field during a migration.
</Callout>

## Device configuration

```ts
interface DeviceConfig {
  gnssAntBias?: boolean
  imuMount?: ImuMountConfig
  recording?: RecordingConfig
  lteRecovery?: LteRecoveryConfig
  timeSync?: TimeSyncConfig
  cellular?: CellularConfig
}

type DeviceConfigPatch = {
  [K in keyof DeviceConfig]?: DeviceConfig[K] | null
}
```

A namespace is either configured or absent on read. It is never
present-but-null, because the API strips cleared namespaces before returning
them. Writing `null` is what clears one, which is why `DeviceConfigPatch` widens
each value and `DeviceConfig` does not.

<Callout title="These types are generated, not hand-written">
  The namespace shapes come from `config-contract.json`, the cross-package
  artifact the web frontend already imports and the device agent contract-tests
  against. Generating them keeps the SDK from becoming a fourth hand-maintained
  copy of a contract that drifts. The [config
  endpoint](/api-reference/devices/patch-device-config) documents their bounds
  and enums, generated from that same artifact.
</Callout>

```ts
interface DeviceUiPrefs {
  activeStreamsViewType?: "card" | "map"
  imuView?: { azimuthDeg: number; elevationDeg: number }
}
```

Cloud-only. Nothing here reaches the device.

```ts
interface DeviceReportedConfig {
  v: number
  deviceId: string
  ts: string
  rev: number // last desired revision applied; 0 = never received one
  origin: "cloud" | "local" | "boot"
  effective: Record<string, unknown>
  status: Record<
    string,
    { state: "applied" | "adjusted" | "rejected"; at: string; detail?: string; reason?: string }
  >
  changed?: string[] | null // only on an origin: "local" report
}
```

`effective` is typed loosely on purpose: it mixes config namespaces with
**reported-only** blocks that are not config at all (`agent.mode`, `sim`,
`uplink`, `apn`), and an absent block means unknown rather than absent hardware.
Typing it strictly would assert a shape the device does not promise.

There is no `pending` state on the wire. `devices.getConfig()` computes it as
`configRev > reportedConfig.rev` on an online device.

## Device model and capabilities

```ts
interface DeviceModel {
  id: string
  name: string
  sku: string
  ioCapabilities: IoCapabilities | null
  firmwareChannel: string | null
  createdAt: string
  updatedAt: string
}

interface IoCapabilities {
  schemaVersion: 1
  media?: { video?: VideoCapability[]; audio?: AudioCapability[] }
  sensors?: { imu?: ImuCapability }
  comm?: { module?: string; gps?: FieldList; signal?: FieldList }
  system?: FieldList
}
```

`ioCapabilities` is typed strictly here even though the API accepts any JSON
object, because provisioning parses it strictly and a document that fails that
parse costs you every camera. See
[Device models](/backend-sdk/resources/device-models).

## Media

```ts
interface MediaSession {
  id: string // device-minted UUIDv7, sorts by start time
  deviceId: string
  streamKey: string
  startedAt: string
  endedAt: string | null
  status: "open" | "closed" // advisory
  timeSource: "ntp" | "gps" | "nitz" | "rtc" | "unsynced" | null
  lastSegmentAt: string | null
  codec: string | null
  width: number | null
  height: number | null
  fps: number | null
  bitrateKbps: number | null
  source: string | null
  createdAt: string
  segmentCount?: number // list endpoint only
  totalBytes?: number // list endpoint only
  totalDurationMs?: number // list endpoint only
}
```

The three rollups are optional because they are computed by the list endpoint. A
session obtained through `xg.media.segments()` does not carry them, and typing
them as required would make that a lie.

```ts
interface ReplayManifest {

```

[Media](/backend-sdk/resources/media).

## Transfer

```ts
type TransferAdoption = "confirmed" | "pending" | "unknown"
type ScopeAttributeResult = "unchanged" | "written" | "failed"
type TransferBlockerCode = "SAME_WORKSPACE" | "SERIAL_COLLISION" | "TRANSFER_IN_PROGRESS"
type TransferOfferStatus = "pending" | "accepted" | "declined" | "cancelled" | "expired"

interface TransferTenancy {
  workspaceId: string
  organizationId: string
}

interface TransferSummary {
  id: string // the transfer record
  deviceId: string
  from: TransferTenancy
  to: TransferTenancy
  crossOrg: boolean
  detachedWorkflowAttachments: string[] // template NAMES; [] same-org
  kvsChannelsRetagged: number
  scopeAttributes: ScopeAttributeResult
  adoption: TransferAdoption
  warnings: string[]
}

interface TransferPreview {
  deviceId: string
  deviceName: string | null
  serial: string | null
  from: TransferTenancy & { workspaceName: string; organizationName: string }
  to: TransferTenancy & { workspaceName: string; organizationName: string }
  crossOrg: boolean
  workflowAttachments: TransferWorkflowAttachment[]
  runningWorkflowRuns: number
  openMediaSessions: number
  staleSessionTokens: number
  kvsChannels: number
  carriesHistory: true // literal true, ALWAYS
  blockers: TransferBlocker[]
  warnings: string[]
}
```

`carriesHistory` is typed as the literal `true`, not `boolean`, because it is
never anything else. It is there to be rendered — all telemetry history and all
recorded footage travel with a device and nothing is purged — not to be branched
on.

`TransferAdoption` has three members on purpose. `"unknown"` means the device has
never reported a telemetry scope at all, which is a different claim from
`"pending"`, and collapsing the two would be a lie. See
[Device ownership and transfer](/platform-concepts/device-ownership).

```ts
// the SENDER's view
interface TransferOffer {
  id: string
  code: string
  status: TransferOfferStatus
  direction: "outgoing" | "incoming"
  deviceId: string
  deviceName: string | null
  from: { organizationId: string; workspaceId: string }
  acceptedBy: { organizationId: string; workspaceId: string | null } | null
  transferId: string | null
  expiresAt: string
  resolvedAt: string | null
  createdAt: string
}

// the RECIPIENT's view. A DIFFERENT, SMALLER type.
interface TransferOfferPreview {
  code: string
  status: TransferOfferStatus
  expiresAt: string
  createdAt: string
  device: { name: string | null; model: { id: string; name: string; sku: string } } | null
  from: { organizationName: string }
}
```

<Callout type="warn" title="The two offer types are not interchangeable">
  `TransferOfferPreview` is a deliberate allowlist, not a subset that happens to
  be short. It carries **no `deviceId`, no `serial`, no `workspaceId`, no
  `organizationId`**, no configuration and no telemetry, because whoever holds
  the code is an organization not yet entitled to the device. Both the API and
  this SDK have tests asserting those absences.
</Callout>

The remaining envelope types are `TransferResult` (`{ device, transfer }`),
`AcceptedTransferOffer` (`{ device, transfer, offer }`), `CreatedTransferOffer`
(`{ offer, willDetachWorkflowAttachments, reused }`), `BulkTransferItem`,
`TransferDeviceInput`, `TransferWorkflowAttachment`, `TransferBlocker` and
`ListTransferOffersParams`.

## Sharing types with the frontend SDK

`@xorgate/react` re-exports every type on this page rather than declaring its
own, so a `Device` fetched server-side and a `Device` held in a hook are the same
type and can cross the boundary without an adapter.

```ts
// server
import type { Device } from "@xorgate/sdk"
// browser
import type { Device } from "@xorgate/react"
```

The frontend SDK adds types the backend one does not have, for the live planes:
connection state, viewer state, replay clock. Those have no server-side meaning
and are not here.
