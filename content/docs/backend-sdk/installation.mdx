
</Tab>

<Tab value="bun">

```bash

```

The package targets Node 20 or newer and any runtime with a global `fetch`,
which covers Cloudflare Workers, Vercel Edge, Deno and Bun. It ships ESM and
CJS, has zero runtime dependencies, and bundles its own TypeScript types. The
zero-dependency claim is checked on the packed tarball rather than on
`package.json`, because an empty `dependencies` block is not the same thing as
an artifact that imports nothing.

## Create a client

```ts
import { createClient } from "@xorgate/sdk"

const xg = createClient({
  auth: { apiKey: process.env.XORGATE_API_KEY! },
  organizationId: process.env.XORGATE_ORG_ID!,
  workspaceId: process.env.XORGATE_WORKSPACE_ID, // optional
})
```

`baseUrl` defaults to `https://api.xorgate.io`, the production deployment, so a
normal integration never sets it.

<Callout title="baseUrl is a bare ORIGIN, and the SDK owns the version segment">

The SDK appends `/v1` itself. That is why the option is an origin rather than a
full base path: pointing it at another deployment or at a proxy cannot silently
drop the version and land you on a deprecated unversioned alias. A `baseUrl` that
already ends in `/v1` is refused at construction with `INVALID_CONFIG` rather
than being doubled up.

</Callout>

### Why `organizationId` is required

Almost every endpoint resolves an active organization, from `X-Organization-Id`
if present and otherwise from your sole membership. A caller who belongs to more
than one organization and omits the header gets a hard
`400 ORGANIZATION_REQUIRED`, not a sensible default. Making the field optional
would produce a client that works in development, where the test account has one
organization, and fails in production the moment a second one exists.

See [Tenancy model](/docs/getting-started/tenancy) for the full resolution order.

### The bootstrap problem

Three operations do not need an active organization, and a brand-new user has
none, so they cannot be reached through a client that requires one:
[`GET /me`](/docs/api-reference/users/get-me),
[`GET /organizations`](/docs/api-reference/organizations/list-organizations) and
[`POST /organizations`](/docs/api-reference/organizations/create-organization).

`createBootstrapClient` is the narrow client for exactly those three:

```ts
import { createBootstrapClient } from "@xorgate/sdk"

const boot = createBootstrapClient({
  auth: { getToken: () => session.idToken },
})

const me = await boot.me()

const org =
  me.organizations[0] ??
  (await boot.createOrganization({ name: "Acme Fleet", slug: "acme-fleet" }))

const xg = boot.forOrganization(org.id)
```

It has four methods and nothing else. If you already know the organization id,
which is the normal case for a server-side integration, skip it entirely.

## Derived clients

Both derivations are cheap: they share the HTTP core, the auth source and the
connection pool, and only rewrite one header.

```ts
// Same credentials, a different tenant.
const other = xg.forOrganization("6b3c...")

// Scope a batch of calls to one workspace without repeating the parameter.
const yard = xg.forWorkspace("9f21...")
const devices = await yard.devices.listAll()
```

`forWorkspace(undefined)` clears the default, which is how you widen a scoped
client back to the whole organization.

Per-call overrides exist too, and beat the client default:

```ts
await xg.devices.list({ workspaceId: "9f21..." })
```

## Timeouts and cold starts

The default `timeoutMs` is 30000, which is generous on purpose. Warm requests
answer in a few hundred milliseconds, but the **first call after a quiet period
is seconds**, not milliseconds. The production database is Aurora Serverless with
a floor of 0 ACU and a 30-minute auto-pause, so the first request after it has
gone to sleep waits for the cluster to resume; a cold Lambda sits on top of that.
Measured against production, a first call of 2 to 5 seconds is normal and one
that took longer would not be surprising.

Two endpoints are outliers even when warm: `GET /devices/{id}/sessions` and
`GET /devices/{id}/video-channels` have both been measured in the seconds.

Do not set an aggressive timeout to "fail fast". **Never set `timeoutMs` below
about 3000**: a 1-second deadline turns a normal resume into an error, and
retrying makes it worse rather than better.

## Cancellation

Every method that can take a while accepts a standard `AbortSignal`:

```ts
const ac = new AbortController()
setTimeout(() => ac.abort(), 5_000)

const history = await xg.telemetry.history(deviceId, {
  from: "2026-08-09T00:00:00Z",
  to: "2026-08-10T00:00:00Z",
  signal: ac.signal,
})
```

An aborted request throws a `XorgateError` with code `ABORTED`. A request that
hits `timeoutMs` throws code `TIMEOUT`. They are distinguishable because one is
your decision and the other is not.

## The escape hatch

`xg.request()` reaches anything the resource modules do not model yet: a new
endpoint, an undocumented query parameter, the Workflows surface. It applies
auth, tenancy headers, the timeout and error mapping, but it does **not** unwrap
the response envelope or normalize casing, so the type parameter is the raw wire
shape.

```ts
const raw = await xg.request<{ device_models: unknown[] }>(
  "GET",
  "/device-models",
)
```

The path is appended to the origin **and the version segment**, so pass
`/device-models`, not `/v1/device-models`.

If you find yourself using it for something the platform supports properly, that
is a gap in this SDK worth reporting.
