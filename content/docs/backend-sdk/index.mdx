`@xorgate/sdk` is the server-side JavaScript and TypeScript client for the
xorgate platform API. It is what your own backend uses to sync devices, read
telemetry history, manage workspaces and members, and pull recorded media.

## What it is

```ts
import { createClient } from "@xorgate/sdk"

const xg = createClient({
  auth: { apiKey: process.env.XORGATE_API_KEY! },
  organizationId: process.env.XORGATE_ORG_ID!,
})

const page = await xg.devices.list({ status: "online" })
console.log(page.items.length, "of", page.page.total, "online")
```

- **One client, resource modules.** `xg.devices`, `xg.workspaces`,
  `xg.telemetry`, `xg.media`, and so on, mirroring the API's resources.
- **Tenancy is configuration, not per-call boilerplate.** `organizationId` is
  required at construction and travels on every request.
- **camelCase everywhere.** The three snake_case envelope keys on the wire
  (`api_keys`, `api_key`/`plaintext_key`, `device_model`/`device_models`) are
  normalized by the SDK. So are the snake_case timestamps on `User` and
  `Organization`.
- **One error type.** Everything thrown is a `XorgateError` carrying the
  platform's `{ code, message, details }` envelope, including client-side
  validation failures.
- **One iteration convention.** `iterate()` exists on every collection, whether
  or not that endpoint paginates today.
- **Zero runtime dependencies.** Node 20+, and anything with `fetch`.

## Design principles

These are the rules the surface was derived from. They explain most of the
choices you will find surprising.

**Mirror the API, do not improve it.** Where the platform paginates, the SDK
paginates. Where it does not, the SDK returns a plain array rather than faking a
page. `deviceRegistrations.create()` returns 200 rather than 201 upstream, and
the SDK does not hide that; it just returns the object. A client library that
smooths over the API teaches you a shape that is not there when you drop down to
raw HTTP.

**One exception: casing.** The two snake_case envelopes mirror Postgres table
names and stay on the wire deliberately (see the
[API reference overview](/api-reference)). Presenting them unchanged would
push a database naming detail into every consumer, so this is the one place the
SDK translates.

**Do work the API cannot.** Two examples. `deviceModels.create()` validates
`ioCapabilities` client-side, because the API accepts any JSON object there but
provisioning parses it strictly, and a document that fails that parse gives the
device **zero video channels with no error anywhere**. And
`deviceRegistrations.waitForClaim()` exists because there are no webhooks, so
every "wait for this to finish" is a poll loop somebody would otherwise write
badly.

**Be honest in the types.** `Device.status` is machine-managed, so
`UpdateDeviceInput` does not include it. `MediaSession.segmentCount` is present
only on the list endpoint, so it is optional. `User.createdAt` is typed
`string | null`, because `GET /me` builds its `user` block from the request's
credential and carries no timestamp at all.

**Never invent an endpoint.** Every method maps to a real operation, except
four that say so where they are documented: `devices.getConfig()` (a view over
`GET /devices/{id}`), `telemetry.latestByMetric()` (a reshape of
`telemetry.latest()`), and the two helpers above. `devices.mergeConfig()` is the
fifth and the most opinionated: it is `patchConfig()` with a read in front,
because a partial config write that looks like a merge and is not is a foot-gun
aimed at customer hardware.
