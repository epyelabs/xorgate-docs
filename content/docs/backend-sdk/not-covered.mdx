---
title: "What this SDK does not cover"
description: "The live planes, the authoring half of workflows, the device claim, and an honest list of the platform gaps you will hit."
---

Two lists. The first is scope: things that exist and belong elsewhere. The
second is gaps: things that do not exist yet and that you will have to work
around.

## Out of scope by design

### Live telemetry

The 1 Hz feed does not go through this API. A client subscribes to AWS IoT Core
over MQTT-over-WebSocket, signed with SigV4, using temporary AWS credentials from
a Cognito identity pool, after calling `POST /live/access` once to attach
its IoT policy.

That call attaches the policy to **the caller's own Cognito identity**, which
makes it meaningless from a server, so the SDK has no method for it. Live
telemetry belongs to `@xorgate/react`.

What this SDK gives you instead: `telemetry.latest()` for the current value per
metric, and `telemetry.recent()` for the newest N samples. Polling `latest()`
every few seconds is a reasonable substitute for a dashboard that does not need
per-second updates, and it costs one request rather than a WebSocket.

### Live video

WebRTC, peer to peer from the device. `devices.videoChannels()` returns the
channel metadata a viewer needs, and that is the extent of this SDK's
involvement: video frames never traverse the API. The viewer lifecycle,
reconnection and credential refresh belong to `@xorgate/react`.

Recorded video is fully covered here. See
[Media](/backend-sdk/resources/media).

### The device claim and install script

`POST /device-registrations/{code}/claim` and `GET /get/{code}` are the install
script's private contract, called unauthenticated on the device itself, and the
claim returns X.509 private key material. They are excluded from the public API
reference and will never be SDK methods. Your side of that flow is
[Device registrations](/backend-sdk/resources/device-registrations).

### Workflows and AI, except the template reads

Three operations are covered:
[`xg.workflowTemplates`](/backend-sdk/resources/workflow-templates) lists
templates (filtered by tag), reads one back, and reads the organization's tag
vocabulary. They exist because an integration has to FIND the templates it owns
at run time without hard-coding an id, and tagging is how it does that. Those
three are in the [API reference](/api-reference/workflow-templates) too.

Everything else on that surface is not documented anywhere on this site and is
not in this SDK: creating a template, saving a draft, publishing or restoring a
version, device attachments and their triggers, runs, run steps, events, the
served catalog, the model registry, simulations, and per-organization
credentials. That half is still moving, and a template is authored by a person
in the web editor rather than by a consumer.

So `xg.search()` can return `workflow-template` and `workflow-instance` hits,
and only the template ones have a method to follow them with:
`xg.workflowTemplates.get(id)`.

`xg.request()` will reach the rest if you need it. There is no stability promise
attached.

The definition format, the node catalog and the engine that executes a template
are documented under [Workflows](/workflows); that is the stable part, and the
platform runs on that same engine.

### Device-side code

The agent that runs on the hardware is a separate program with its own CLI and
configuration, not something this SDK talks to. See
[Device SDK](/device-sdk).

## Platform gaps

These are real limitations of the platform today, not omissions in the SDK.
Every one of them is on the platform-readiness backlog.

### An API key cannot create an organization

`POST /organizations` needs a user, and a key has none, so a consumer cannot
onboard a customer as its own xorgate organization. Map customers onto
**workspaces** inside one organization instead, which a default `member` key can
create. Organizations are provisioned out of band. See
[Authentication](/backend-sdk/authentication).

### Webhooks cover presence and sessions, not everything

xorgate pushes device presence, recording sessions and workflow events as
signed [webhooks](/platform-concepts/webhooks) to an endpoint you register.
Everything else is still a poll: registration claims, config convergence and
agent updates have no event.

| You want to know             | Webhook                                                    | Otherwise poll                             | Signal                     |
| ---------------------------- | ---------------------------------------------------------- | ------------------------------------------ | -------------------------- |
| A device finished onboarding | none                                                       | `deviceRegistrations.waitForClaim(code)`   | `status` becomes `claimed` |
| A config change landed       | none                                                       | `devices.getConfig(id)`                    | `pending` becomes false    |
| A device came back online    | `device.online`                                            | `devices.get(id)`                          | `status`, `lastSeenAt`     |
| An agent update succeeded    | none                                                       | `devices.get(id)`                          | `agentVersion` changes     |
| New recorded media exists    | `media_session.started`, `media_session.ended`             | `media.sessions.list(id, { from: since })` | new or grown sessions      |
| A drive's telemetry is ready | `telemetry_session.completed`                              | `telemetry.sessions.list(id)`              | a closed session           |
| A device stopped reporting   | `device.offline` (`source: "sweeper"` for stale telemetry) | `telemetry.latest(id)`                     | `ts` stops advancing       |
| A workflow flagged something | `workflow.event`, from the `output.event` node's `webhook` | no public route; the console's run history | new events                 |

Webhooks are routed per device (presence and sessions) or per workflow node,
and go to a server you run, never to a browser. From `@xorgate/sdk` 0.9.0,
`xg.webhooks` and `xg.devices.webhooks` manage endpoints and routes, and
`verifyWebhookSignature` checks a delivery's signature.

For whatever you still poll, a fleet-wide sweep is one `devices.iterate()` per
interval. Keep the interval sane: there is no rate limiting to protect the
platform from a tight loop, and `GET /devices/{id}/sessions` in particular is
around 1090 ms per device.

### Cross-tenant reads look like missing rows

A resource in another organization answers `404`. You cannot distinguish "does
not exist" from "not yours". That is deliberate, and it means reconciliation code
must treat `NOT_FOUND` as "not visible to me" rather than "deleted".

### The first-party live grant is still one shared policy

`POST /live/access` attaches **one** browser IoT policy to the caller's Cognito
identity, so a member of any organization can subscribe to any device's telemetry
topic. That is the xorgate dashboard's own path, and narrowing it is open work.

It does not affect this SDK, which reads only org-scoped REST endpoints, and it
is **not** the path a third party uses: `POST /auth/live-credentials` vends
credentials confined to one tenant, and a sibling workspace's device is refused
on both planes by the credential itself. See
[Authentication](/backend-sdk/authentication).

### No idempotency keys

A timed-out write is genuinely ambiguous. The SDK does not retry writes for that
reason. See [Errors](/backend-sdk/errors).

### No request id in error bodies

`XorgateError.requestId` is the id the SDK generated and sent as `X-Request-ID`.
The API does not return one, so it correlates your own logs but cannot yet be
handed to someone reading the platform's.

### Not everything paginates

Six list endpoints return their whole collection (`xg.workflowTemplates.tags()`
is a seventh, but that one is a small vocabulary rather than a collection). That is fine at today's scale
and will not stay fine. Use `iterate()` rather than `list()` where you can, so
the change is free. See [Pagination](/backend-sdk/pagination).

### Roles cannot be changed

There is no membership update endpoint. Changing a role means remove then add.
See
[Users and organizations](/backend-sdk/resources/users-and-organizations).

### Deleting is final, and it is thorough

`devices.delete()` removes the rows and cascades, and since the destroy
mechanism (API 0.7) it also tears down the AWS side: the IoT thing and
certificate, the KVS signaling channels, the uploaded media and telemetry
objects, and the FK-less telemetry history. `workspaces.delete()` and
`organizations.delete()` do the same for every device under them. There is no
soft delete and no restore anywhere in the API, and no SDK method yet for
`DELETE /me` (closing the caller's own account) — that is a console operation
today; call the endpoint directly if you need it from code.
