The SDK takes exactly one `auth` value, and it is one of two shapes:

```ts
type XorgateAuth =
  | { apiKey: string }
  | { getToken: () => string | Promise<string> }
```

`{ apiKey }` is the mode for server-to-server callers. `{ getToken }` is the
first-party mode, carrying a Cognito ID token. Both authenticate against the
platform; they differ in what they can reach, not in whether they work.

## API keys

```ts
const xg = createClient({
  auth: { apiKey: process.env.XORGATE_API_KEY! },
  organizationId: process.env.XORGATE_ORG_ID!,
})
```

A key is a long-lived, organization-scoped credential minted with
[`POST /api-keys`](/docs/api-reference/api-keys/create-api-key) and returned
exactly once. This is the right shape for a backend: no interactive login, no
refresh cycle, no token expiry to schedule around.

A key is bound to one organization by the row it was minted from and acts with
its own `role`, defaulting to `member`: it can read everything and write
devices, workspaces and device registrations, but not memberships, keys or
organization settings, and never device models. Four operations refuse a key
outright because they are about a person (`GET /me`, `GET`/`POST
/organizations`, and the two live-access operations); the SDK exposes those on
`createBootstrapClient` and the live hooks, not here.

### How the SDK sends it

As a bearer credential on the existing header:

```http
Authorization: Bearer xg_A1b2C3d4...
```

Not `X-Api-Key`. Keys carry the `xg_` prefix, so the backend discriminates a key
from a JWT on the token itself without a second header, and the API's CORS
allowlist of request headers is exactly `Authorization`, `Content-Type`,
`X-Request-ID`, `X-Organization-Id` and `X-Workspace-Id`, so a new header would
have cost a CORS change plus a deploy. This was an SDK-side recommendation that
the backend then adopted.

`organizationId` stays required on the client even with a key, which is
redundant but harmless: the server takes the organization from the key row and
`403`s a header naming a different one, so a mismatch is loud rather than
silent.

<Callout title="Vending live access for your own clients">

Live telemetry and live video are streaming protocols the client speaks
directly, so they are entered with a signed connection rather than with a bearer
token.
[`POST /auth/live-credentials`](/docs/api-reference/auth/create-live-credentials)
is what signs it, and your key may call it. Pass the target `workspaceId` and
you get credentials confined to that one customer: they receive its devices'
telemetry, they can view its devices' video, and a sibling workspace's device is
refused. Hand the response to your frontend unread and give it to the SDK's
`getLiveCredentials` slot.

That is the PROXIED shape, and its point is that your browser touches no xorgate
endpoint at all. If you would rather your client called xorgate directly, mint a
session token instead (below) and let the SDK do the vending.

The two live-ACCESS operations still answer `401 USER_CREDENTIAL_REQUIRED` to a
key, and always will: they attach and detach an IoT policy on a Cognito
identity, which is the xorgate dashboard's own mechanism and not part of an
integration.

</Callout>

## Minting session tokens for your clients

The key stays on your server. When your own frontend or mobile app needs to talk
to xorgate, exchange the key for a short-lived **session token** and send that
instead:

```ts
// Your endpoint, guarded by your own auth.
app.post("/api/xorgate-token", requireMyOwnLogin, async (req, res) => {
  const session = await xg.auth.createSessionToken({
    // YOUR authorization decision. xorgate never learns who req.user is.
    workspaceId: await myDb.workspaceForUser(req.user.id),
    ttlSeconds: 900,
  })
  res.json(session) // { token: "xgs_…", expiresAt, workspaceId, role, live }
})
```

Three properties make this safe to hand out where a key would not be:

- **It expires.** 15 minutes by default, an hour at most.
- **It is never more privileged than the key.** It inherits the key's `role`,
  and the role in force is the lower of the token's and the key's current one.
- **It can be confined to one workspace**, and that confinement is enforced
  rather than advisory. A workspace-scoped token sees only that workspace's
  devices, gets `403 WORKSPACE_MISMATCH` for an `X-Workspace-Id` naming another,
  and `403 WORKSPACE_SCOPED` on organization-wide operations at any role.

Deleting the key with
[`DELETE /api-keys/{id}`](/docs/api-reference/api-keys/delete-api-key) destroys
every token it minted, immediately. That is the emergency stop; there is no
per-token revoke.

Full request and response shape:
[Auth](/docs/api-reference/auth).

<Callout title="A session token is a client credential, not a second backend one">
  Do not authenticate your own backend with a token it minted. It buys nothing
  over the key it came from, it expires under you, and it cannot mint its own
  replacement.
</Callout>

## Cognito ID tokens

```ts
const xg = createClient({
  auth: { getToken: async () => (await auth.currentSession()).getIdToken() },
  organizationId: orgId,
})
```

`getToken` is called **once per request**, and may be sync or async. The SDK does
not cache the result, on purpose: your Cognito library already caches and
refreshes, and only it knows when the token expires. A cache in the SDK would be
a second, worse one that hands out expired tokens.

Three things to know:

- It must be an **ID token**, not an access token. The platform verifies
  `tokenUse: 'id'`, and an access token fails with `401 UNAUTHORIZED` in a way
  the message does not explain.
- A `getToken` that throws propagates as a `XorgateError` with code
  `UNAUTHORIZED` and the original error as `cause`. Refresh failures surface as
  auth failures, which is what they are.
- The user row is created just-in-time on first successful verification, so
  there is no registration call to make first.

<Callout title="Fine for a first-party backend, awkward for a third party">
  An ID token is tied to an interactive login, so a headless service using this
  mode has to keep a service-account session alive. That is exactly the problem
  API keys solve. Use `{getToken}` only when you genuinely need the
  person-scoped operations or the live plane.
</Callout>

## Roles

Authentication answers who you are. Two separate role systems answer what you may
do, and they are easy to confuse.

| System          | Where it lives                                                     | Values                               | Gates                                                                                                                                                                                                       |
| --------------- | ------------------------------------------------------------------ | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Membership role | `memberships.role`, per organization, or `api_keys.role` for a key | `owner`, `admin`, `member`, `viewer` | Every read is open to all four. `viewer` can write nothing. Provisioning, API keys, memberships, organization writes, session deletes and the reboot / power-off / update commands need `owner` or `admin`. |
| Platform role   | `users.role`, global                                               | `user`, `admin`                      | Device-model catalog writes only. An API key and a session token are always `user`, so neither can ever write the catalog.                                                                                  |

A failure on either is `403`, distinguished by code: `INSUFFICIENT_ROLE` when you
are a member without enough role, `FORBIDDEN` when you are not a member of the
requested organization at all, `NO_ORGANIZATION` when you are a member of none.

A workspace-scoped session token adds a third dimension that no role satisfies:
`WORKSPACE_SCOPED` on an organization-wide operation, and `WORKSPACE_MISMATCH`
for an `X-Workspace-Id` that contradicts the token. Both are `403`.

The SDK marks role requirements in each method's documentation. It does not
check them client-side, because it cannot know your role without a `me()` call
and the answer can change between the check and the request.

## Storing credentials

The usual rules, listed because SDK examples get copied.

- Read keys and tokens from the environment or a secret manager. Never from
  source, and never from a file committed to a public repository.
- A plaintext key is shown once, at creation. Only its SHA-256 is stored, so a
  lost key is replaced, never recovered.
- An API key grants access to a whole organization at its role. There is no
  per-workspace or per-device key: **a session token is how you narrow to one
  workspace**, and it is the only xorgate credential that belongs in a browser
  or a mobile binary. Rotation is manual and overlapping: mint the
  new key, deploy it, then delete the old one with
  [`DELETE /api-keys/{id}`](/docs/api-reference/api-keys/delete-api-key).
  Expiry is opt-in per key, so set one on anything long-lived.
- `XorgateError` never includes the credential in its `message` or `url`.

## The live planes are a separate question

Live telemetry (MQTT over WebSocket) and live video (WebRTC) do not use this
API's credential at all. They need temporary AWS credentials from a Cognito
identity pool, which requires a Cognito identity that neither an API key nor a
session token has. The `live` block on a minted token carries the coordinates
(region and realtime endpoint) so a client never hardcodes them, but the
credential that opens a stream is separate work. See
[What this SDK does not cover](/docs/backend-sdk/not-covered).
