Everything here is a known limit, recorded as a decision rather than left as a
surprise. The engine's first plan deferred a specific list, and the platform's
workflow REST surface is still moving; both are stated plainly so you can
design around them.

## The platform workflow API is not documented

Workflow templates, their versions and publication, device attachments and
their triggers, runs, run steps, events, the served catalog, the model
registry, simulations and organization credentials all exist as REST resources
on the platform. **None of them are in the [API reference](/api-reference)**,
and neither the [Backend SDK](/backend-sdk) nor the
[Frontend SDK](/frontend-sdk) models them. `xg.search()` can return
`workflow-template` and `workflow-instance` hits, and `xg.request()` will reach
the endpoints, with no stability promise attached.

What this section documents instead is the part that is stable and runnable:
the definition format, the catalog, and the engine. A template exported from
the platform runs unchanged in the engine today.

## The platform integration

The engine is the one execution engine for workflows, the platform's own runs
included. Since `@xorgate/workflow-engine` 0.3.0 the platform's
attachment-triggered runs and editor simulations execute through this package:
its shell installs it as an ordinary npm dependency on both of its targets, a
Lambda function for telemetry-only graphs and a container image (with ffmpeg,
ONNX Runtime and `python3`) for graphs with media or code function nodes, and
calls `createEngine({ host })` exactly as [Using the engine as a
library](/workflows/library) shows. The catalog the editor fetches is the
package's, at the same `catalogVersion` (`08c8c39436928e5e`) `xwe` reports.

What that does not give you is a round trip from a local run: there is no
publishing of a locally authored template and no ingesting of a local run's
results. Templates move as JSON.

What makes the integration hold:

- the definition format, run manifest, `result.json` and catalog are frozen
  contracts, shared by the engine and the platform's storage and editor;
- the local artifact tree is the platform's storage key layout, so tooling
  written against one reads the other;
- the engine core is storage-free, and the platform's shell supplies the same
  seams the local shell supplies (sources, artifacts, secrets, progress) over
  its object storage, database, secret store and message topics.

A template that behaves differently on the platform than under `xwe` is a bug
on whichever side diverged from those contracts; the catalog hash is the first
thing to compare, and the two are equal by construction when the platform's
pinned engine version matches yours.

## Deferred engine features

These were explicitly kept out of the engine's first plan. Each is a door left
open, not a gap discovered late.

### No bundle or export format

There is no `.xwf` bundle, no `GET /workflow-templates/{id}/export`, and no
tethered sync of local results to the platform. You move templates and
fixtures by hand, as JSON and media files.

### No serve mode, schedules, or watch folders

`xwe run` is one process per run. There is no long-running daemon that accepts
work, and nothing that watches a directory or a clock.

### No live camera

The live-mode channel semantics (drop-oldest frames, latest wins) are in the
core, and the editor's webcam simulation is designed around them, but the
local host shell has no live source: no v4l2, no avfoundation, no MQTT ingest.
A `webcam` binding fails with "no live ingest support".

### Function nodes: since 0.2.0

`function.javascript` and `function.python`, user code run in a sandboxed
child process, shipped in 0.2.0 and are documented on
[Code function nodes](/workflows/functions). The container image is the
outer sandbox boundary, which is why it carries `python3`. What is still not
there is a `condition` output (a function cannot drive `output.event`
directly) and a way to feed a function from telemetry: a function consumes
`json`, so on a telemetry-only graph its producer is the connector or another
function.

### CPU only

`onnxruntime-node` ships CPU builds for Linux and macOS on x64 and arm64, and
no GPU execution provider for the Node binding. `model.depth` accepts
`backend: "gpu-endpoint"` in its schema and nothing implements it. The
`backend` seam exists so a GPU path costs nothing to add later; the
[performance](/workflows/performance) page says what CPU buys.

### No device-agent coexistence

The engine is not integrated with the device agent. The measured Compute
Module 5 run happened on a module with the agent live, which proves they can
share a host, not that anything coordinates them: no shared media bridge, no
scheduling around recording, no fleet distribution of templates.

### What is distributed, and what is not

The engine is published as `@xorgate/workflow-engine` 0.2.0 on npm, with the
`xwe` command inside it, and as the multi-arch image `ghcr.io/epyelabs/xwe`;
[Installing the engine](/workflows/installation),
[Using the engine as a library](/workflows/library),
[Models and the registry](/workflows/models) and
[Extending the catalog](/workflows/extending) describe those artifacts as
verified. The license is MIT, the same as the SDKs. There is no licensing or
metering of runs, and none is planned. Every documented feature is in the
published 0.2.0, code function nodes included; 0.3.0 adds only the exports the
platform's shell consumes.

## Bindings that only resolve on the platform

`telemetry_history` (device history from the platform database) and `webcam`
(the editor's live ingest) are part of the shared binding vocabulary, but the
local host shell has no database and no live plane, so they fail with a
message that names the alternative. On the platform, whose shell runs this
engine, both resolve: `telemetry_history` against the device's stored history
and `webcam` against the editor's live ingest topic.
