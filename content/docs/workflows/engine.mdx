`xorgate-workflow-engine` is the workflow execution engine, developed as its own
repository (`engines/xorgate-workflow-engine`). It runs a definition over local
files and writes the platform's artifact layout, with **no cloud dependency
at all**: the package depends on no cloud provider's SDK, and its smoke test
fails if one appears. That independence is the point. An engine that
needs nothing from its host can be handed to a laptop, a container, an edge
device, or the platform's own runners, and run the same template the same way
on each.

<Callout title="Published">
  `npm install -g @xorgate/workflow-engine` puts `xwe` on your path; `docker
  pull ghcr.io/epyelabs/xwe` gets the image with ffmpeg and ONNX Runtime inside.
  Both are version 0.2.0, built from the repository's `v0.2.0` tag. [Installing
  the engine](/workflows/installation) has every install route; this page is the
  repository itself, for running from a checkout and for reading the code.
</Callout>

## Where it runs

The engine is developed in isolation on purpose: a standalone codebase is
easier to test and iterate on, and the platform is used as a source of real
fixtures (published templates, session video, telemetry windows, registry
models) rather than as a runtime dependency. The platform then **consumes this
engine** as the npm package: since 0.3.0 its shell pins an exact version on
both of its execution targets, a Lambda function for telemetry-only graphs and
a container image (ffmpeg, ONNX Runtime, `python3`) for graphs with media or
code function nodes, so a workflow attached to a device, a scheduled run, and
a simulation from the editor all execute on exactly the code you can run with
`xwe`.

Everything about the engine's contracts is shaped by that arrangement:

- The artifact tree a run writes uses the platform's storage key layout under
  the run prefix, so a local run directory and a platform run are
  interchangeable for tooling.
- Source bindings are one shared vocabulary; the local shell resolves them as
  files, the platform's shell resolves them as storage objects, device history
  and live ingest.
- The catalog is one catalog, served to the editor and executed by the engine,
  with a content hash that tells you at a glance whether two hosts agree.

What the integration does not give you (a round trip from a local run) is
drawn on [What this does not cover](/workflows/not-covered#the-platform-integration).

## What is in the repository

| Directory      | What it is                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------ |
| `src/engine/`  | `runGraph`, the channels and stall detector, ffmpeg and ONNX plumbing, the manifest and result schemas |
| `src/catalog/` | The 28 node definitions and executors                                                                  |
| `src/models/`  | The model manifest schema (the registry layout)                                                        |
| `src/local/`   | The local host shell: file sources, the artifact writer, secrets, progress, video muxing               |
| `src/cli/`     | The `xwe` command                                                                                      |
| `fixtures/`    | Real templates, a real drive's video and telemetry, and `yolov8n`, for the golden tests                |

The engine core (`src/engine/`, `src/catalog/`) is storage-free by design.
Every source reads through a seam, every artifact leaves through a seam, and a
host supplies the seam implementations. `src/local/` is the host shell for
files on disk; the platform's shell supplies the same seams over its object
storage, secret store and message topics. The seams are the library's
integration contract, described under
[Using the engine as a library](/workflows/library#the-four-seams).

Two things about this layout are worth knowing when reading the source: the
fixtures directory keeps only the small files (templates, CSV, manifests) and
pulls the video and the model on demand, so that nothing in the repository
grows with the number of models; and the catalog is a set of **packs** built
into a catalog instance rather than one static list, so that nodes outside
the repository register the same way the core ones do. See
[Models and the registry](/workflows/models) and
[Extending the catalog](/workflows/extending).

## Requirements

- **Node 20 or newer.** The build ships ESM and CommonJS.
- **ffmpeg.** Every video node spawns it. Resolution order is `FFMPEG_PATH`,
  then `ffmpeg` on `PATH`, then the `ffmpeg-static` development dependency if
  installed. The docker image installs it from apt.
- **CPU only.** Inference runs through `onnxruntime-node`'s prebuilt CPU
  binding on Linux and macOS, x64 and arm64. There is no GPU path; see
  [Performance](/workflows/performance) for what CPU buys you.
- **Models on disk** for any `model.*` node other than the VLM, in the registry
  layout described under [Inputs and outputs](/workflows/run-artifacts#models):
  a `--models-dir` root, or the cache that `xwe models pull` fills.
- **A secret** only for the connector (except `osm`) and `model.vlm`.

`xwe doctor` prints each of these for the machine it runs on, with the fix
when one is missing; see
[Installing the engine](/workflows/installation#checking-a-machine-xwe-doctor).

## Running it

<Tabs items={["Docker", "Bare node"]}>

<Tab value="Docker">

Build from the checkout, then run with your working directory mounted at
`/work`. Relative template, input and output paths resolve there, and so does
the default model directory.

```bash
docker build -t xwe .
docker run --rm -v "$PWD":/work xwe \
  run fixtures/templates/overspeed.json \
  --input telemetry=fixtures/telemetry/window.csv --out out
```

A multi-architecture image (`linux/amd64` and `linux/arm64`) builds with
`docker buildx build --platform linux/amd64,linux/arm64 -t xwe .`. The
entrypoint is the CLI, so any `xwe` argument list works after the image name.

</Tab>

<Tab value="Bare node">

```bash
npm ci
npm run build
npx xwe run fixtures/templates/overspeed.json \
  --input telemetry=fixtures/telemetry/window.csv --out out
```

`dist/` is a build artifact, so a fresh checkout needs `npm run build` before
`npx xwe` resolves. On macOS there is typically no system ffmpeg; the
`ffmpeg-static` development dependency covers it with no further setup.

</Tab>

</Tabs>

The expected output of that first run, on any host:

```
[xwe] succeeded in 0.0s -> out/local-1787000000000/result.json
  ok      n1           150 samples (csv: gps.lat, gps.lon, gps.speed)
  ok      n2           derived 149 speed_kph values (speed_from_position)
  ok      n3           true on 149/149 samples (gt 10)
  ok      n4           emitted 1 event(s)
  events: 1
```

## Verifying an install

Two scripts, both offline:

```bash
npm run smoke   # imports runGraph, counts 28 catalog nodes, prints the catalog hash, asserts no cloud SDK packages
npm test        # builds, then runs the golden suite
```

The golden suite is the repository's regression gate. It drives the real CLI
over the shipped fixtures and asserts outcomes, not bytes: the overspeed
template must produce exactly one `overspeed` event at a pinned timestamp with
a pinned observed speed; the detection template must decode exactly 50 frames
and find 81 objects give or take a tolerance for floating-point variance across
hosts; the visualization template must emit an MP4 that decodes back to exactly
50 frames at 2 fps; and a missing input must exit 1 naming the failing node
while still writing `result.json`.

## Compatibility

The engine is a set of contracts with code behind them, and the package
version is about the contracts. The policy applies from 0.1.0. `docs/compatibility.md` in the repository is
the full table with the file each contract lives in; the short form:

| Contract            | Identity                                                                                                                                                    |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workflow definition | `schemaVersion: 2`; v1 graphs are upgraded on the way in                                                                                                    |
| Run manifest        | `manifestVersion: 2`                                                                                                                                        |
| `result.json`       | `resultVersion: 2`, `engineVersion: 2`; written last in the artifact tree                                                                                   |
| Catalog payload     | `schemaVersion: 2`; `catalogVersion` is the content hash of the node definitions, `92697a69913738c4` for the core catalog from 0.5.1; `packs[]` is additive |
| Model manifest      | v1; the `files` block is additive; `family` is an open string                                                                                               |
| Host seams          | `EngineSourceReader`, `EngineArtifactSink`, `EngineSecretReader`, `EngineProgressSink`, and `EngineHost.bind` over them                                     |
| Progress messages   | `status`, `step`, `event`, `record`, each stamped `at`; the same objects as NDJSON on stdout and as callbacks                                               |
| CLI                 | the commands, their flags, and the exit codes `0`, `1`, `2`                                                                                                 |
| Node packs          | `NodePack`, `createCatalog`, `corePacks`, the namespace rules                                                                                               |
| Environment         | `XWE_MODELS_DIR`, `XWE_MODELS_PULL`, `XWE_MODEL_REGISTRY`, `XORGATE_SECRET_<LOGICAL_NAME>`, `FFMPEG_PATH`                                                   |
| Node.js             | 20 or newer                                                                                                                                                 |

The version number follows semantic versioning over that table. A breaking
change to any contract is a major: a field removed or retyped, a seam method
renamed, a progress message type removed, an exit code reassigned, a core
node or port removed, a config schema narrowed so an existing template stops
validating. An additive change is a minor: a new optional field, a new
optional seam method, a new message type or field, a new command or flag, a
new core node. A new node moves the core `catalogVersion`, and the changelog
names the old and new hashes. A fix that changes what an executor produces on
the same input is a patch, and the changelog names the affected node types
under an "Executor behaviour" heading so a host can decide whether to
re-baseline.

Schema versions move only on majors, so a document written by an older
release keeps parsing on every newer release of the same major, and a
document written by a newer minor may carry fields an older release ignores.
The latitude semantic versioning grants a `0.x` package is not used: the
rules apply from the first release, and `1.0.0` is meant to change nothing but
the number.

Not contracts, and free to change in any release: the wording of log lines
and of step summaries (the [conformance kit](/workflows/library#proving-a-host-the-conformance-kit)
matches their leading counts, not their prose), the module layout under
`dist/` (deep imports are not supported), the exact bytes of frames and
videos, and detection counts within the documented tolerance.
`catalogVersion` is the drift detector, not a version number: two hosts with
the same hash execute the same node definitions.

## The fixtures

Real data, grabbed read-only from the development platform, with provenance
in `fixtures/README.md`. The two large files (the video and the model) are not
committed: `fixtures/fixtures.json` pins their checksums and
`npm run fixtures:pull` fetches them (`npm test` runs it first).

| Fixture                                  | What it is                                                                                                          |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `templates/overspeed.json`               | The published "Overspeed Detect" template. Telemetry only, no network, no model: the hermetic golden case.          |
| `templates/perimeter-person-detect.json` | Published: video, `yolov8n`, a person gate, an event.                                                               |
| `templates/perimeter-visualize.json`     | The same graph plus `output.visualization`, for annotated video.                                                    |
| `templates/overspeed-osm.json`           | Published: the connector on `osm`. Calls public Overpass at run time, so it is for manual testing, not the suite.   |
| `telemetry/window.csv`                   | 150 s of 1 Hz GPS from one highway drive, 74 to 118 km/h.                                                           |
| `video/drive.mp4`                        | 25 s of 720p h264 from the same drive and the same minutes, cut from one on-device session segment. Pulled.         |
| `models/detection/yolov8n/1/`            | `model.onnx` (12.85 MB) and its manifest, in the registry layout. Pulled; runs pass `--models-dir fixtures/models`. |

The video and telemetry are from the same vehicle at the same time, so graphs
that correlate the two behave as they would on a real session.
