<Callout type="warn" title="Design preview">
  The registry layout, the manifest and the local directory search on this page
  are how the engine works today. The public registry, `xwe models`, the cache,
  integrity fields and `--pull` are planned and not published yet.
</Callout>

Models are never part of the engine. The package does not contain one, the
container image does not bake one in, and the repository does not commit any.
A `model.*` node names a model and the host resolves it, from disk or from a
registry, in one fixed layout that is the same on the platform and on your
machine.

## The layout

```
<root>/<family>/<name>/<version>/manifest.json
<root>/<family>/<name>/<version>/model.onnx
```

Families are `detection`, `segmentation` and `depth`, matching the three ONNX
node types; `name` is what node config carries (`"model": "yolov8n"`);
`version` is a positive integer directory. The platform's registry is this
layout under a prefix in its object storage, the public registry is this
layout over HTTPS, and a directory on disk is this layout as folders. Tooling
written against one reads the others.

## Where a model comes from

The local host searches a chain of roots in order and takes the first hit,
highest version first within it:

| Root                              | Set by                                                                                                   | Default                     |
| --------------------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------- |
| explicit directories              | `--models-dir <dir>` (repeatable), `localHost({ modelDirs })`                                            | none                        |
| the cache                         | `XWE_MODELS_DIR`                                                                                         | `~/.xorgate/models`         |
| the registry, **only when asked** | `--pull`, `XWE_MODELS_PULL=1`, `localHost({ models: { pull: true } })`; `XWE_MODEL_REGISTRY` for the URL | `https://models.xorgate.io` |

A model that is in none of them fails the node's step with the roots it
searched and the command that would fix it:

```
xwe: run failed at node n3: model detection/yolov8n not found under ./models, ~/.xorgate/models
  (run `xwe models pull detection/yolov8n`, or pass --pull)
```

Pulling is explicit by default on purpose. A CI job or an edge device should
never start a download because a template named a model; it should have been
provisioned, and the error says how.

## `xwe models`

```bash
xwe models list                              # the registry index, marking what is cached
xwe models pull detection/yolov8n            # newest version into the cache
xwe models pull detection/yolov8n@1          # a specific version
xwe models path detection/yolov8n            # what a run would load, and from which root
```

`pull` downloads `manifest.json` and `model.onnx` into the cache root, verifies
the checksum the manifest declares, and refuses to keep a file that does not
match. `list` reads the registry's `index.json`, which is the same list the
platform's model picker shows. Everything works against any registry that
serves the layout, so a private mirror is one environment variable away:

```bash
XWE_MODEL_REGISTRY=https://models.example.internal xwe models pull detection/yolov8n
```

In the container, mount a volume at the cache path so pulls survive the
container (`-v xwe-models:/root/.xorgate/models`).

## Integrity

The manifest carries a checksum for each file next to it. The field is
additive to `manifestVersion: 1`: every manifest that exists today still
parses, and a manifest without it is pulled with a warning instead of a
verification.

```json
{
  "manifestVersion": 1,
  "family": "detection",
  "name": "yolov8n",
  "version": 1,
  "files": {
    "model.onnx": { "sha256": "…", "sizeBytes": 13468672 }
  }
}
```

The engine verifies on pull, not on every run. A model already on disk is
trusted the way any other local file is.

## Pinning a version

Node config names a model, and the highest version found wins. A template
that must not move pins the version in the same string:

```json
{ "config": { "model": "yolov8n@1" } }
```

The catalog's config schema is unchanged (the field is a string); the resolver
splits on `@`. A template without a pin runs the newest version wherever it
runs, which is the platform's behaviour too.

## Bringing your own model

A fine-tuned or entirely private model is a directory in the layout, not a
special case. The engine never checks where a model came from; it checks that
the manifest parses and that its `postprocess.kind` is one it implements.
This walkthrough takes a YOLOv8 detector fine-tuned on two classes,
`forklift` and `pallet`, from training output to a running template, first
with the CLI and then from code.

### The layout you are producing

```
models/
  detection/
    acme-forklift/
      1/
        manifest.json
        model.onnx
```

`models/` is any directory you choose to pass as a root. `detection` is the
family the `model.object_detection` node asks for. `acme-forklift` is the
name a template will carry. `1` is the version; a retrained model becomes
`2/` next to it and templates that do not pin a version pick it up.

<Steps>

<Step>

### Export to ONNX and write the manifest

The engine reads the model's geometry, normalization, class names and
post-processing parameters from the manifest, so the export step's job is to
produce both files consistently. The export tool that produces the
first-party models is planned to ship in the engine repository under
`tools/export/`, and it accepts your own weights:

```bash
python tools/export/export_yolo.py \
  --weights runs/train/forklift/weights/best.pt \
  --name acme-forklift --version 1 \
  --out ./models
```

It exports `best.pt` to `model.onnx` at the training image size, reads the
class names from the weights, and writes this manifest next to it:

```json
{
  "manifestVersion": 1,
  "family": "detection",
  "name": "acme-forklift",
  "version": 1,
  "label": "Forklift detector (site A, 2026-09)",
  "backend": "cpu-onnx",
  "input": {
    "width": 640,
    "height": 640,
    "layout": "nchw",
    "colorSpace": "rgb",
    "normalize": { "scale": 0.00392156862745098 },
    "letterbox": { "enabled": true, "padValue": 114 }
  },
  "classNames": ["forklift", "pallet"],
  "postprocess": { "kind": "yolov8", "nmsIouThreshold": 0.45 },
  "files": {
    "model.onnx": { "sha256": "9f2c…", "sizeBytes": 12212736 }
  }
}
```

If you export another way (Ultralytics' own `yolo export format=onnx`, or a
training framework's exporter), write this manifest by hand. The only fields
that change between a stock YOLOv8 and a fine-tune are `name`, `label`,
`classNames` and, if you trained at another size, `input.width` and
`input.height`. `classNames` must be in the training's class-index order,
because that is how the output tensor is decoded.

</Step>

<Step>

### Check the directory

```bash
xwe models check ./models/detection/acme-forklift/1
```

```
manifest   ok   detection/acme-forklift v1, yolov8, 2 classes, 640x640 nchw rgb
model      ok   model.onnx 11.6 MB, sha256 verified
session    ok   onnxruntime-node 1.19.2, input "images" [1,3,640,640]
output     ok   "output0" [1,6,8400] matches yolov8 with 2 classes (4 + 2)
```

The last line is the one that matters. A YOLOv8 head outputs
`4 + classNames.length` rows; a manifest that lists two classes for a model
trained on three fails here, with both numbers, instead of as a garbled
detection list halfway through a run. `check` also fills in `files.sha256`
and `sizeBytes` when the manifest lacks them, so a hand-written manifest
becomes registry-ready.

</Step>

<Step>

### Name it in a template

A template names the model in the detection node's config and, since the
class names are now yours, uses them in the nodes downstream:

```json
{
  "schemaVersion": 2,
  "nodes": [
    {
      "id": "src",
      "type": "source.video",
      "data": { "label": "Camera", "config": {} },
      "position": { "x": 0, "y": 0 }
    },
    {
      "id": "dec",
      "type": "video.decode_sample",
      "data": { "label": "2 fps", "config": { "fps": 2 } },
      "position": { "x": 200, "y": 0 }
    },
    {
      "id": "det",
      "type": "model.object_detection",
      "data": {
        "label": "Forklifts",
        "config": { "model": "acme-forklift", "minConfidence": 0.5 }
      },
      "position": { "x": 400, "y": 0 }
    },
    {
      "id": "gate",
      "type": "logic.detection_gate",
      "data": {
        "label": "Forklift in frame",
        "config": { "classes": ["forklift"], "minCount": 1 }
      },
      "position": { "x": 600, "y": 0 }
    },
    {
      "id": "evt",
      "type": "output.event",
      "data": {
        "label": "Forklift seen",
        "config": { "kind": "forklift_present" }
      },
      "position": { "x": 800, "y": 0 }
    }
  ],
  "edges": [
    { "id": "e1", "source": "src", "target": "dec" },
    { "id": "e2", "source": "dec", "target": "det" },
    { "id": "e3", "source": "det", "target": "gate" },
    { "id": "e4", "source": "gate", "target": "evt" }
  ]
}
```

`"model": "acme-forklift@1"` pins the version; without the pin the highest
version under any root wins.

</Step>

<Step>

### Run it

```bash
xwe validate forklift.json
xwe run forklift.json --input video=yard.mp4 --models-dir ./models --out out
```

```
[xwe] model detection/acme-forklift v1 <- models/detection/acme-forklift/1/model.onnx
[xwe] succeeded in 6.2s -> out/local-1789000000000/result.json
  ok      src          video yard.mp4 (video_local)
  ok      dec          50 frame(s) sampled at 2 fps from 1 video(s)
  ok      det          37 detection(s) over 50 frame(s) (acme-forklift v1, ~41 ms/frame)
  ok      gate         true on 22/50 detection frame(s)
  ok      evt          emitted 3 event(s)
  events: 3
```

The first line names the model and version the run loaded and the file it
came from, which is the thing to read when a run used a model you did not
expect. Without `--models-dir`, the cache (`~/.xorgate/models`) is searched,
so `cp -r models/detection/acme-forklift ~/.xorgate/models/detection/` makes
the model available to every run on the machine.

</Step>

### Sharing it: a private registry

A registry is a static file server in the layout with an `index.json` at
the root. Nothing else is required, so a team's registry can be a bucket, an
internal web server, or a directory served during a test:

```
registry/
  index.json
  detection/acme-forklift/1/manifest.json
  detection/acme-forklift/1/model.onnx
```

`index.json` is an array of the manifests, so `xwe models list` can show
what is available without walking directories:

```json
[
  {
    "family": "detection",
    "name": "acme-forklift",
    "version": 1,
    "label": "Forklift detector (site A, 2026-09)"
  }
]
```

Point pulls at it and everything on this page works against it:

```bash
export XWE_MODEL_REGISTRY=https://models.acme.internal
xwe models list
xwe models pull detection/acme-forklift
xwe run forklift.json --input video=yard.mp4 --pull
```

`pull` verifies the manifest's `files.sha256` after download, which is why
`check` fills it in.

### From code

The library resolves models exactly as the CLI does; the options are the same
words:

```ts
import { createEngine } from "@xorgate/workflow-engine"
import { localHost } from "@xorgate/workflow-engine/local"

const engine = createEngine({
  host: localHost({
    modelDirs: ["./models"],                          // searched first
    models: { registryUrl: "https://models.acme.internal", pull: true }, // then the cache, then this
    outDir: "./out",
  }),
})

const run = await engine.run({ template: "./forklift.json", inputs: { video: "./yard.mp4" } })
for (const step of run.result.steps) console.log(step.nodeId, step.status, step.output)
// det ok 37 detection(s) over 50 frame(s) (acme-forklift v1, ~41 ms/frame)
```

The check is available as a function too, for a build step or a test:

```ts
import { checkModelDir } from "@xorgate/workflow-engine/local"

const report = await checkModelDir("./models/detection/acme-forklift/1")
if (!report.ok) throw new Error(report.problems.join("\n"))
```

A host with its own storage does not use directories at all. Models reach
the engine through one seam method, and a host that keeps weights in a
bucket, a database or memory implements just that method. The engine caches
the session per model for the run, so the method is called once per model
per run:

```ts
import { runGraph } from "@xorgate/workflow-engine"
import { modelManifestSchema } from "@xorgate/workflow-engine"

const sources = {
  ...fileSources,
  async fetchModel({ family, name }) {
    const prefix = `models/${family}/${name}/${await latestVersion(family, name)}/`
    const manifest = modelManifestSchema.parse(JSON.parse(await bucket.text(prefix + "manifest.json")))
    const modelPath = await bucket.downloadToTemp(prefix + "model.onnx")  // ONNX Runtime opens a file path
    return { manifest, modelPath }
  },
}

const outcome = await runGraph(spec, { sources, artifacts, secrets, progress })
```

That is the platform's own arrangement: its shell implements `fetchModel`
over its object storage, and the engine does not know the difference.

### Limits

- **A model whose output layout matches no existing `postprocess.kind`**
  (`yolov8`, `yolov8-seg`, `depth-anything`) needs a decoder. That is either
  a contribution to the engine or a `model.*` node in a
  [pack](/workflows/extending) that carries its own decoding; the manifest's
  `kind` is the list of what exists.
- **A new family** (`classification`, say) comes with the pack that adds a
  node for it. The manifest's `family` is one of `detection`, `segmentation`
  and `depth` today because those are the three model nodes; it is planned
  to become an open string with the known values documented, so a pack can
  bring a family without an engine release.
- **Segmentation and depth fine-tunes** follow the same steps with
  `yolov8-seg` (a `maskThreshold` joins `postprocess`) and `depth-anything`
  (no class names, a single map output).
- **On the platform**, a private model is the same directory uploaded to the
  organization's own registry prefix. That upload path is a platform feature
  and is not part of the engine.

## The manifest

The manifest is the same document the platform's registry stores, and it is
what makes a model usable without code: input geometry, normalization, class
names and post-processing parameters are read from it, not hard-coded per
model.

| Field                                 | Meaning                                                                                                                                 |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `family`, `name`, `version`, `label?` | Identity. `label` is the human name pickers show.                                                                                       |
| `backend`                             | `cpu-onnx` is the only one implemented. `gpu-endpoint` is accepted by the schema and refused at run time.                               |
| `input`                               | `width`, `height`, `layout` (`nchw`), `colorSpace` (`rgb`), `normalize` (`scale`, `mean?`, `std?`), `letterbox` (`enabled`, `padValue`) |
| `classNames`                          | Class index to name, for detection and segmentation.                                                                                    |
| `postprocess`                         | `kind` (`yolov8`, `yolov8-seg`, `depth-anything`, `rtdetr`), `nmsIouThreshold`, `maskThreshold`                                         |
| `quantization?`                       | `fp32`, `fp16` or `int8`, informational.                                                                                                |
| `files?`                              | Checksums, above.                                                                                                                       |

The export pipeline that converts a model to ONNX is the only writer of
manifests on the platform side. A model you export yourself needs a manifest
in this shape and a `postprocess.kind` the engine implements; `rtdetr`
manifests parse but the node refuses them until its decoder lands.

## First-party models and their licenses

<Callout type="warn" title="Read the license before you ship">
  The engine is MIT licensed. The models are not the engine. Each carries its
  own license, and the two default detectors are AGPL-3.0, which has
  consequences for a proprietary product or a hosted service that uses them. The
  engine resolves whatever model a template names, so swapping in a model under
  a license you can live with is a template change, not an engine change.
</Callout>

| Model                     | Family         | Source                    | License                       | Status in the engine                       |
| ------------------------- | -------------- | ------------------------- | ----------------------------- | ------------------------------------------ |
| `yolov8n`                 | `detection`    | Ultralytics YOLOv8        | AGPL-3.0                      | the catalog default; the golden fixture    |
| `yolov8s`                 | `detection`    | Ultralytics YOLOv8        | AGPL-3.0                      | runs                                       |
| `yolov8n-seg`             | `segmentation` | Ultralytics YOLOv8        | AGPL-3.0                      | the catalog default                        |
| `depth-anything-v2-small` | `depth`        | Depth Anything V2 (small) | Apache-2.0                    | the catalog default                        |
| `rtdetr`                  | `detection`    | RT-DETR                   | Apache-2.0 (original release) | manifest accepted, decoder not implemented |

A permissively licensed default detector is on the roadmap. Changing a
catalog default changes the catalog hash and the meaning of every published
template that relies on the default, so it is a platform decision rather than
a quiet engine change.

## The platform registry and the public one

The platform keeps its registry under `models/` in its object storage, written
by the export pipeline, listed by `GET /model-registry`, and read by its own
engine shell through the same `fetchModel` seam the local host implements. The
public registry at `models.xorgate.io` is a mirror of the first-party subset
of that registry, in the same layout, with `index.json` at the root. Nothing
about a model differs between the two; the only difference is who can reach
them.
