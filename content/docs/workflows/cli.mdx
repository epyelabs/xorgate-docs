`xwe` is one dispatcher with four subcommands. It has no configuration file
and no daemon; every run is one process that reads a template, executes it,
and exits with a code you can act on.

```bash
xwe validate <template.json>
xwe run <template.json> --input <key>=<path> ... [options]
xwe run --manifest <manifest.json> [options]
xwe models list | pull <family>/<name>[@<version>] | path <family>/<name>[@<version>] | check <dir>
xwe doctor [--models-dir <dir>]...
xwe <command> ... --log-level silent|error|info|debug                      # any command
xwe function test <template.json> <nodeId> --event <event.json> [--version <n>]   # 0.2.0, on main
```

<Callout type="warn" title="Design preview">
  Everything on this page is shipped in 0.1.0 and verified against the published
  package, except `function test`, which is implemented on the engine's main
  branch for 0.2.0 with [code function nodes](/workflows/functions) and is not
  in a published package yet; its output below is measured from that branch.
</Callout>

## `validate`

Parses the template (bare definition or API snapshot), upgrades a v1 graph,
runs the same publish validation the platform's editor runs, and prints what a
run of it would need. Real output for the shipped detection template:

```
OK: 5 nodes, 4 edges (schemaVersion 2)
required inputs:
  --input video=<path>   source.video "Video Stream" (node n1)
required secrets: none
other requirements: video
```

On failure it lists every issue with its code and the node or edge it points
at, and exits 1:

```
INVALID: 1 issue(s)
  MISSING_INPUT [viz]: required input "frames" has no edge
```

"Required secrets" comes from the catalog's capability tokens, so a graph
with a `google_roads` connector reports `google-roads-api-key` here before you
find out at run time. "Other requirements" lists the remaining tokens: `video`
for a video source and one `metric:<name>` per telemetry signal the graph
expects.

## `run`

| Flag                   | Meaning                                                                                                                                                                                                                                                                                                                          |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `<template.json>`      | The template to run. Mutually exclusive with `--manifest`.                                                                                                                                                                                                                                                                       |
| `--manifest <file>`    | Run a prebuilt run manifest instead of building one from a template. See [Inputs and outputs](/workflows/run-artifacts#the-run-manifest).                                                                                                                                                                                        |
| `--input <key>=<path>` | Bind a source node to a file. Repeatable. Keys below.                                                                                                                                                                                                                                                                            |
| `--out <dir>`          | Artifact root, default `./out`. The run writes `<out>/<runId>/`.                                                                                                                                                                                                                                                                 |
| `--run-id <id>`        | The run id, default `local-<epoch ms>`. Also the output directory name.                                                                                                                                                                                                                                                          |
| `--models-dir <dir>`   | A model registry root. Repeatable; searched in order before the cache (`XWE_MODELS_DIR`, default `~/.xorgate/models`). The checkout's fixture model is one such root: `--models-dir fixtures/models`.                                                                                                                            |
| `--secrets <file>`     | A JSON object of `"<logical-name>": "<value>"`. Wins over the environment. A file that does not parse is reported by name only; a value never appears in any artifact or output line, and child processes never see it.                                                                                                          |
| `--progress json`      | Emit one JSON object per line on stdout as the run progresses.                                                                                                                                                                                                                                                                   |
| `--emit-video`         | After a successful run, mux each visualization node's frames into an MP4.                                                                                                                                                                                                                                                        |
| `--window <from>,<to>` | An ISO-8601 run window. Rarely needed: file bindings carry their own timestamps.                                                                                                                                                                                                                                                 |
| `--pull`               | Fetch a model the graph names from the registry into the cache when it is not on disk (`XWE_MODELS_PULL=1` does the same). See [Models](/workflows/models).                                                                                                                                                                      |
| `--pack <module>`      | Register a node pack before running: a package name or a path, resolved from the working directory the way `require` is; the module's `pack` or default export is the pack. Repeatable, also on `validate`. Prints `[xwe] pack <name> v<version> (<n> nodes) <- <file>` per pack. See [Extending](/workflows/extending).         |
| `--log-level <level>`  | On every command. `silent` prints nothing on stderr (the exit code and `result.json` carry the outcome); `error` prints failures only; `info`, the default, prints what this page shows; `debug` adds the engine's trace: the bindings, the graph order, one `[engine]` line per node with its timing. stdout is never affected. |

### Input keys

A key is either a **shorthand** for the node's type or a **node id**:

| Key         | Binds                               |
| ----------- | ----------------------------------- |
| `video`     | the graph's `source.video` node     |
| `telemetry` | the graph's `source.telemetry` node |
| `<nodeId>`  | that node, whatever its type        |

Shorthands only work while the graph has one node of that type; with two video
sources, `validate` reports their node ids as the keys instead. A key that
matches no bindable source, or a source left unbound, fails before anything
runs, with the expected keys in the message. The connector node is never
bound: it is fed by an edge.

The binding kind is chosen from the node type and the file extension: video
files become `video_local`; a `.csv` becomes `telemetry_csv`; a `.jsonl` becomes
`telemetry_materialized`. The formats are on
[Inputs and outputs](/workflows/run-artifacts#source-bindings).

### What a run prints

Diagnostics go to **stderr**, so stdout stays clean for `--progress json`. A
successful run ends with one line per step in execution order, the node's own
summary, and the event count:

```
[xwe] model detection/yolov8n v1 <- fixtures/models/detection/yolov8n/1/model.onnx
[engine] n2: decoded 50 frame(s) from fixtures/video/drive.mp4
[xwe] succeeded in 4.1s -> out/demo/result.json
  ok      n1           video fixtures/video/drive.mp4 (video_local)
  ok      n2           50 frame(s) sampled at 2 fps from 1 video(s)
  ok      n3           81 detection(s) over 50 frame(s) (yolov8n v1, ~36 ms/frame)
  ok      gate-m6      true on 0/50 detection frame(s)
  ok      n4           emitted 0 event(s)
  events: 0
```

A failed run names the node:

```
xwe: run failed at node n1: ENOENT: no such file or directory, open '.../missing.csv'
```

With `--log-level debug` the engine's own trace comes first, and with
`--log-level error` only the `xwe:` failure line is left (`silent` prints
nothing on stderr at all):

```
[engine] run demo: 4 node(s), bindings n1=telemetry_csv
[engine] run demo: artifacts -> out/demo
[engine] graph: 4 node(s), 3 edge(s), order n1 -> n2 -> n3 -> n4
[engine] n1: ok in 2 ms, 150 message(s)
[engine] n2: ok in 2 ms, 150 message(s)
[engine] n3: ok in 2 ms, 149 message(s)
[engine] n4: ok in 2 ms, 0 message(s)
[engine] run demo: succeeded in 4 ms
[xwe] succeeded in 0.0s -> out/demo/result.json
  ok      n1           150 samples (csv: gps.lat, gps.lon, gps.speed)
  ok      n2           derived 149 speed_kph values (speed_from_position)
  ok      n3           true on 149/149 samples (gt 10)
  ok      n4           emitted 1 event(s)
  events: 1
```

### The progress stream

With `--progress json`, stdout carries the engine's progress messages, one
object per line, each stamped with `at`. The message set is the engine's, not
the CLI's; a platform shell publishes the same messages over its own transport:

| `t`      | Fields                                                                   | When                                           |
| -------- | ------------------------------------------------------------------------ | ---------------------------------------------- |
| `status` | `status` (`running` \| `succeeded` \| `failed`), `error`, `failedNodeId` | once at start, once at the end                 |
| `step`   | `seq`, `nodeId`, `label`, `status`, `output`, `durationMs`               | as each node finishes                          |
| `event`  | `kind`, `occurredAt`, `confidence`, `payloadSummary`, `payload`          | as `output.event` fires                        |
| `record` | `nodeId`, `port`, `tag`, `ts`, `seq`, `payload`                          | for each `json`-channel message leaving a node |

`record` covers `json` ports only: connector lookups, VLM verdicts, and the
like. Detections travel on their own channel and are counted in the detection
node's step summary rather than streamed.

The message set is stable: the four types and the fields above are a
published contract, never removed or retyped within a major version, and only
ever added to (see [Compatibility](/workflows/engine#compatibility)). A secret
value read through the secrets seam never reaches a message: it is replaced
with `[redacted]` in `output`, `error` and every payload before the message
is emitted, on stdout and through `engine.run({ progress })` alike.

## `models`

Four subcommands over the [model registry](/workflows/models):

```bash
xwe models list                          # the registry index, marking what is cached locally
xwe models pull detection/yolov8n        # newest version into ~/.xorgate/models, checksum verified
xwe models pull detection/yolov8n@1      # a specific version
xwe models path detection/yolov8n        # what a run would load, and from which root
xwe models check ./models/detection/acme-forklift/1   # validate a model directory
```

`XWE_MODEL_REGISTRY` overrides the registry URL and `XWE_MODELS_DIR` the cache
root; `--models-dir` adds roots for `list` and `path`. `pull` exits 1 when a
checksum does not match and keeps nothing; `pull` of a version already in the
cache downloads nothing. `check` prints four lines (manifest, model, session,
output), fills in the manifest's checksum when it is missing (`--no-fill` to
only read), and exits 1 when any line fails; the lines are on
[Models](/workflows/models#check-the-directory). Measured against the public
registry with an empty cache:

```
$ xwe models list
registry https://models.xorgate.io (3 models)
  depth/depth-anything-v2-small@1  Depth Anything V2 Small  94.5 MB
  detection/yolov8n@1              yolov8n                  12.3 MB
  segmentation/yolov8n-seg@1       yolov8n-seg              13.2 MB
$ xwe models pull detection/yolov8n
pulled detection/yolov8n@1 -> ~/.xorgate/models/detection/yolov8n/1 (model.onnx 12.3 MB, sha256 verified)
$ xwe models path detection/yolov8n
/home/dev/.xorgate/models/detection/yolov8n/1/model.onnx
  detection/yolov8n v1, from the cache (~/.xorgate/models)
```

## `function test`

Runs one event through a [code function node](/workflows/functions) in the
same sandboxed runtime a run would use, with the code the template holds, and
prints the result, the log lines and the handler's duration. On the engine's
main branch for 0.2.0, not in a published package yet.

```bash
xwe function test forklift-summary.json fn --event event.json
```

```
ok      fn           function.javascript  $LATEST  0 ms
result: {"frameSeq":3,"count":1,"widestPx":212,"confidence":0.81}
logs: none
```

A handler that throws prints the error and the frames inside its own code,
and exits 1; a dropped event prints `result: null (dropped)`; log lines are
listed under `logs:`. `--version <n>` runs a published snapshot instead of
the working copy, and the report's third column says `v2` instead of
`$LATEST`. Exit 2 when the template, the node id (the message lists the
node ids), the event file or the version is wrong and nothing ran, and when
`python3` is not on `PATH` for a Python node. The event file is
`{ "tag"?, "ts"?, "seq"?, "payload" }`; only `payload` is required.

## `doctor`

Prints the node version, the ffmpeg it would use, whether the
ONNX Runtime binding and the VLM provider client are installed, the `python3`
that `function.python` nodes would use (from 0.2.0), the model roots and
what they contain, whether the registry is reachable, and the catalog hash
with any packs. Exits non-zero when something a run needs is missing, with the
fix on the same line. The output is on
[Installing the engine](/workflows/installation#checking-a-machine-xwe-doctor).

## Exit codes

| Code | Meaning                                                                                                                                                         |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`  | The run succeeded, or the template validated.                                                                                                                   |
| `1`  | The run failed (a node threw, or the deadline hit). `result.json` is still written, with `status: "failed"` and the node id. `validate` also exits 1 on issues. |
| `2`  | Usage or configuration: an unbindable input key, a template that does not parse, a missing file argument. Nothing was run.                                      |

The distinction between 1 and 2 is the useful one for scripting: 2 means the
invocation was wrong, 1 means the graph was. The three codes are stable: a
code is never reassigned within a major version, and `--log-level` changes
what is printed, never the code (see
[Compatibility](/workflows/engine#compatibility)).
