A workflow is a directed graph. Source nodes feed telemetry or video into
processing nodes (decoders, models, filters, logic) that end in outputs: events,
captured records, and annotated frames. A **template** is one such graph saved
as JSON, and a **run** is one execution of it over concrete inputs.

Templates are authored in the web application's editor. They are executed by
**`xorgate-workflow-engine`**, a standalone execution engine with a
command-line shell, `xwe`, that runs a template over local files on a laptop,
in a docker container, or on a Raspberry Pi 5 class device today. It is the
same engine everywhere: the platform's own workflow runs execute on it too,
consumed as the npm package by the platform's shell, so a template behaves
identically wherever it runs.

## The shape of a workflow

The smallest useful graph: GPS telemetry in, ground speed derived from
position, a threshold, an event. This is a real published template, and it is
the engine's golden test.

```json
{
  "schemaVersion": 2,
  "nodes": [
    {
      "id": "n1",
      "type": "source.telemetry",
      "data": {
        "label": "GPS",
        "config": { "metrics": ["gps.lat", "gps.lon", "gps.speed"] }
      },
      "position": { "x": 40, "y": 200 }
    },
    {
      "id": "n2",
      "type": "telemetry.derivative",
      "data": {
        "label": "Speed from GPS",
        "config": { "mode": "speed_from_position", "outputSignal": "speed_kph" }
      },
      "position": { "x": 300, "y": 200 }
    },
    {
      "id": "n3",
      "type": "logic.threshold",
      "data": {
        "label": "Speed Limit Check",
        "config": { "signal": "speed_kph", "operator": "gt", "value": 10 }
      },
      "position": { "x": 580, "y": 200 }
    },
    {
      "id": "n4",
      "type": "output.event",
      "data": {
        "label": "Overspeed",
        "config": { "kind": "overspeed", "attachClip": true }
      },
      "position": { "x": 860, "y": 200 }
    }
  ],
  "edges": [
    { "id": "e1", "source": "n1", "target": "n2" },
    { "id": "e2", "source": "n2", "target": "n3" },
    { "id": "e3", "source": "n3", "target": "n4" }
  ]
}
```

Every node's executor starts at once and the edges are bounded in-process
channels, so a source never reads faster than its slowest consumer. A node that
throws fails its step, every node downstream of it is skipped, independent
branches run to completion, and the run is marked failed with the first failing
node's id. Those semantics belong to the engine, not to where it runs.

## One engine, several hosts

The engine takes a **run manifest** (a definition plus source bindings) and
produces an **artifact tree** (`result.json`, events, records, frames). Hosts
differ only in where the bindings point and where the tree lands.

|            | Your machine, a container, a device         | The platform                                                                      |
| ---------- | ------------------------------------------- | --------------------------------------------------------------------------------- |
| Started by | `xwe run`                                   | a device attachment trigger, a schedule, or a simulation from the editor          |
| Inputs     | local files: video, CSV or JSONL telemetry  | device telemetry history, uploaded video, on-device session segments, live ingest |
| Outputs    | `out/<runId>/` on disk                      | object storage under `workflows/v2/runs/<runId>/`, then rows in the database      |
| Models     | a local mirror of the model registry layout | the model registry                                                                |
| Secrets    | environment variables or a JSON file        | per-organization credentials, then platform credentials                           |

The engine reaches those hosts as one npm package, `@xorgate/workflow-engine`,
that carries both `xwe` and a library entry point, and as one multi-arch
container image; [Installing the engine](/workflows/installation) is how to
get either, and [Using the engine as a library](/workflows/library) is what
embedding it in your own service looks like.

The local artifact tree uses the platform's storage key layout, the binding
kinds are shared, and the catalog is one catalog. That is deliberate: the
platform consumes the engine as a package, and nothing about a template, a
manifest or a result changes between a local run and a platform run. Four
things are frozen contracts for that reason: the
definition format (`schemaVersion: 2`), the run manifest, the `result.json`
shape, and the catalog node definitions.
