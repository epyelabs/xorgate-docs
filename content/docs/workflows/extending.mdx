The 26 nodes in the [catalog](/workflows/catalog) are ordinary modules: a
declarative definition and an executor, validated once when the catalog is
built. A node you write is the same thing, in your own package, and the
engine treats it exactly like a core node once it is registered. This is where
a catalog of hundreds of nodes lives: not in the engine's repository, but in
packs owned by whoever needs them. The example pack this page builds lives in
the engine repository under `examples/packs/acme-scale/`, and the output
below is measured with it.

## A node

```ts
import { z } from "zod"
import { defineNode, requireInput, telemetrySamples } from "@xorgate/workflow-engine"
import type { EngineInChannel, EngineRunCtx } from "@xorgate/workflow-engine"

const configSchema = z.object({
  signal: z.string().min(1).describe("Signal to scale"),
  factor: z.number().default(1).describe("Multiplier"),
})

export const def = defineNode({
  type: "acme.scale",
  version: 1,
  group: "telemetry",
  label: "Scale",
  description: "Multiplies one signal by a constant.",
  ui: { icon: "move-diagonal" },
  inputs: [{ id: "telemetry", label: "Telemetry", channel: "telemetry", cardinality: "one", required: true }],
  outputs: [{ id: "telemetry", label: "Telemetry", channel: "telemetry", cardinality: "many", required: false }],
  config: configSchema,
  requires: [],
  runtime: { target: "any" },
})

export const executor = async function* (inputs: EngineInChannel[], config: unknown, ctx: EngineRunCtx) {
  const cfg = configSchema.parse(config)
  let count = 0
  for await (const sample of telemetrySamples(requireInput(inputs, "telemetry"))) {
    const signals = { ...sample.signals }
    if (cfg.signal in signals) signals[cfg.signal] *= cfg.factor
    count += 1
    yield { ch: "telemetry" as const, ts: sample.ts, payload: { signals } }
  }
  ctx.setSummary(`scaled ${count} samples (${cfg.signal} × ${cfg.factor})`)
}
```

What the definition promises:

| Field               | Rule                                                                                                                                                            |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type`              | `namespace.name`, lowercase. The namespace is yours; `source`, `video`, `telemetry`, `model`, `logic`, `output`, `connector` and `function` belong to the core. |
| `group`             | One of `source`, `video`, `telemetry`, `model`, `logic`, `output`, `function` (empty until code function nodes ship). It places the node in the editor palette. |
| `inputs`, `outputs` | Ports with a [channel](/workflows/definitions#channels), a cardinality and `required`. A `json` output must declare its `tag`.                                  |
| `config`            | A zod schema. It is parsed at run time, unknown keys are rejected, and it is serialized to JSON Schema for the editor's config form.                            |
| `requires`          | Capability tokens (`secret:<name>`, `metric:<name>`, `video`) so `validate` can say what a graph needs before it runs.                                          |
| `runtime`           | `target: "any"` runs wherever the engine runs; `"media"` says the node needs ffmpeg or ONNX Runtime. `modelRef.family` for model nodes.                         |

What the executor promises: it is an async generator; it reads its inputs
through bounded channels and therefore applies backpressure by awaiting; it
yields messages on a channel with a timestamp; it throws to fail its step; and
it reports through `ctx` (`setSummary`, `log`, `emitEvent`, `captureRecord`)
rather than through side effects. A node that needs a file, a model, a secret
or HTTP asks `ctx.sources`, `ctx.secrets` and `ctx.http` for them, which is
what keeps it runnable on every host.

## A pack

A pack is a versioned list of nodes:

```ts
import type { NodePack } from "@xorgate/workflow-engine"
import * as scale from "./nodes/scale"
import * as thermalGate from "./nodes/thermal-gate"

export const pack: NodePack = {
  name: "@acme/xwe-nodes-thermal",
  version: "1.2.0",
  nodes: [scale, thermalGate],
}
```

Publish it as an npm package whose default export (or a named `pack` export)
is the pack. It depends on `@xorgate/workflow-engine` as a peer, so there is
one engine in the process. Either module format works: the `xwe` command is
CommonJS and loads an ES module pack through `require` (Node 20.19 and 22.12
or later) or a dynamic `import` on older versions, and the library does the
same in either direction. The core catalog is itself seven packs, one per
namespace (`corePacks`: `core/source`, `core/connector`, `core/video`,
`core/telemetry`, `core/model`, `core/logic`, `core/output`), which is what
lets a host compose the engine without the pieces it cannot run:
`createCatalog(corePacks.filter((p) => p.name !== "core/model"))` is the
engine without ONNX Runtime.

## Loading packs

```ts
import { createEngine, createCatalog, corePacks } from "@xorgate/workflow-engine"
import { pack as thermal } from "@acme/xwe-nodes-thermal"

const engine = createEngine({
  host,
  catalog: createCatalog([...corePacks, thermal]),
})
```

`createEngine({ packs: [thermal] })` is the shorthand for "core plus these".
The CLI takes the same thing as a module specifier, resolved from the working
directory, repeatable:

```bash
xwe run graph.json --pack @acme/xwe-nodes-thermal --pack ./local-pack.js --input telemetry=window.csv
xwe validate graph.json --pack @acme/xwe-nodes-thermal
```

Each pack loaded prints one line on stderr, then the command runs as usual.
With the repository's example pack, over a copy of the overspeed template
that scales the derived speed by 0.05 before the threshold:

```
$ xwe run examples/packs/acme-scale/overspeed-scaled.json --pack ./examples/packs/acme-scale \
    --input telemetry=fixtures/telemetry/window.csv --out out --run-id scaled
[xwe] pack @acme/xwe-nodes-scale v1.0.0 (1 node) <- ./examples/packs/acme-scale/index.js
[xwe] succeeded in 0.0s -> out/scaled/result.json
  ok      n1           150 samples (csv: gps.lat, gps.lon, gps.speed)
  ok      n2           derived 149 speed_kph values (speed_from_position)
  ok      n2b          scaled 150 samples (speed_kph × 0.05)
  ok      n3           true on 0/149 samples (gt 10)
  ok      n4           emitted 0 event(s)
  events: 0
```

Without the pack the same template does not validate, and `validate` names
the namespace it looks like the node belongs to:

```
$ xwe validate examples/packs/acme-scale/overspeed-scaled.json
INVALID: 2 issue(s)
  UNKNOWN_NODE_TYPE [n2b]: Unknown node type "acme.scale": namespace "acme" is not in the core catalog; register its pack (--pack <module>, or createEngine({ packs }))
  MISSING_INPUT [n3]: Threshold input "Telemetry" must be connected
```

`run` treats that as a usage error (exit code 2, nothing runs). A `--pack`
that does not resolve, a module that exports no pack, or a pack that fails
to build (below) exit 2 as well, with the reason on stderr.

Building a catalog validates every definition the way the core is validated:
a malformed definition, a duplicate `type`, a duplicate port id within one
direction, or a `json` output without a tag throws at build time with the
offending node named, before any run. A pack cannot replace a core node, and
a pack cannot change a core node's defaults: a second definition of a type
that already exists is the duplicate error, not an override. A pack node in
a core namespace is refused for the same reason, and registering one pack
twice is an error rather than a silent no-op:

```
Duplicate catalog node type "acme.scale" (in pack "@acme/xwe-nodes-scale" and pack "y"); a pack cannot replace or override a node
Pack "x": node type "telemetry.scale" uses the core namespace "telemetry"; a pack picks its own namespace (reserved: source, video, telemetry, model, logic, output, connector, function)
createCatalog: pack "@acme/xwe-nodes-scale" is registered twice (positions 8 and 9)
```

## What `catalogVersion` means with packs

The serialized catalog payload's `catalogVersion` is a content hash of every
node definition the host registered, sorted by group and label. With no packs
it is the core hash the [catalog page](/workflows/catalog) quotes, and two
hosts that print the same value run the same nodes with the same defaults.
With packs the value changes, by design, and the payload says why. Measured
with the example pack registered next to the core
(`buildCatalogPayload(createCatalog([...corePacks, pack]))`, `nodes` elided):

```json
{
  "catalogVersion": "5c3e079fc2e7f9e8",
  "schemaVersion": 2,
  "aliases": {},
  "nodes": [],
  "packs": [
    { "name": "core", "version": "0.1.0-dev", "hash": "e481243f5ffe4678" },
    {
      "name": "@acme/xwe-nodes-scale",
      "version": "1.0.0",
      "hash": "1b1102fe3076cd96"
    }
  ]
}
```

A pack's `hash` is the `catalogVersion` a catalog holding only that pack
would have, so the `core` entry equals the core hash whenever every core pack
is registered, whatever else is (the seven core packs collapse into that one
entry; a host that dropped `core/model` reports a different core hash). With
no packs registered the payload is exactly what it was before packs existed
plus a one-entry `packs` list, and `catalogVersion` is still
`e481243f5ffe4678`.

`packs` is additive to the payload; a consumer that only knows
`catalogVersion` keeps working. A consumer that reads `packs` can say "the
core matches, this host also has extras", which is the question that matters
when a template authored against one host runs on another: a template that
uses only core nodes runs anywhere the core hash matches, and a template that
uses a pack's node needs that pack, at a compatible version, on the host that
runs it. `validate` reports an unknown node type with the pack namespace it
looks like it belongs to, as shown above.

## The other kind of extension

A pack is trusted code loaded into the process. Code you would rather not
trust, or code a template author writes in the editor without a repository,
is a [code function node](/workflows/functions): user JavaScript or Python
stored inside the template and run by the engine in a sandboxed child
process. The two are siblings, and the function page ends with a table of
when to use which.

## What a pack cannot do

- Add a channel. The six channels are the engine's; a pack picks from them.
- Add a binding kind that the host does not resolve. A source node in a pack
  can declare a new `kind`, but only a host that implements it can run it.
- Reach outside `ctx`. There is no sandbox around a pack: a pack is code you
  chose to load into your process, with your process's permissions, the same
  as any npm dependency. Untrusted user code is what
  [code function nodes](/workflows/functions) are for.
