`xorgate-workflow-engine` ships as one npm package, **`@xorgate/workflow-engine`**,
that contains both the library and the `xwe` command, and as one container
image, **`ghcr.io/epyelabs/xwe`**, that contains the command with ffmpeg and
ONNX Runtime already installed. Which one you install depends on how you want
to run templates, not on what the templates do: every mode runs the same
engine over the same catalog.

| You want to                                     | Install                                   | Then                                                      |
| ----------------------------------------------- | ----------------------------------------- | --------------------------------------------------------- |
| run templates over files from a shell or CI     | `npm install -g @xorgate/workflow-engine` | `xwe run ...`                                             |
| try it once without installing anything         | nothing                                   | `npx @xorgate/workflow-engine run ...`                    |
| run templates from your own code                | `npm install @xorgate/workflow-engine`    | `import { createEngine } from "@xorgate/workflow-engine"` |
| run on a machine you do not want to put node on | `docker pull ghcr.io/epyelabs/xwe`        | `docker run ghcr.io/epyelabs/xwe run ...`                 |

The package targets Node 20 or newer, ships ESM and CJS with its own
TypeScript types, and is MIT licensed. A project install puts `xwe` in
`node_modules/.bin`, so `npx xwe` works inside the project; a global install
(`npm install -g @xorgate/workflow-engine`) puts it on your `PATH`.

### What an install pulls down

The engine itself is small. What makes an install large is ONNX Runtime, whose
npm package carries prebuilt native bindings for every platform it supports.
The engine therefore declares its two heavy dependencies as **optional**:

| Dependency                             | Needed by                                                     | Declared as | Loaded                               |
| -------------------------------------- | ------------------------------------------------------------- | ----------- | ------------------------------------ |
| `onnxruntime-node`                     | `model.object_detection`, `model.segmentation`, `model.depth` | optional    | at run time, by the first model node |
| the VLM provider client                | `model.vlm`                                                   | optional    | at run time, by the VLM node         |
| `zod`, `jpeg-js`, `zod-to-json-schema` | everything                                                    | required    | at import                            |

A plain `npm install` includes the optional dependencies, so the CLI runs
every node out of the box. `npm install --omit=optional` gives a lean install
for hosts that only run telemetry and logic graphs; a model node on such a host
fails its step with a message naming the missing package, and nothing else is
affected. The catalog, validation and the serialized catalog payload never
touch either package, which is why importing the library is cheap on every
host.

The numbers below were measured for 0.1.0 by the package's own tarball check
(`npm run verify:tarball`: pack, install into a fresh project, run), on macOS
arm64 with npm 11, and confirmed against the published tarball. They are
re-measured for every release.

| Artifact                                   | Measured                                                                                                                                                                     |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| npm tarball (`dist`, README, LICENSE only) | 185 kB packed, 1.2 MB unpacked, 282 files                                                                                                                                    |
| `node_modules` after `--omit=optional`     | 4.8 MB                                                                                                                                                                       |
| `node_modules` after a default install     | 295 MB, of which ONNX Runtime 283 MB (every platform) and the VLM client 6 MB                                                                                                |
| container image, per architecture          | ONNX Runtime trimmed to the image's own binding: 940 MB on arm64 (1.31 GB before the trim), 1.03 GB on amd64 (1.78 GB before); ffmpeg and its libraries are most of the rest |

The tarball never contains fixtures, models, video, or the source tree; the
same check asserts it on every run.

### ffmpeg

Every video node spawns `ffmpeg`, and it is never an npm dependency of the
package. Resolution order is `FFMPEG_PATH`, then `ffmpeg` on `PATH`. Install it
from your platform:

```bash
brew install ffmpeg          # macOS
sudo apt install ffmpeg      # Debian, Ubuntu, Raspberry Pi OS
```

The container image has it already. Telemetry-only graphs never need it.

## The container image

```bash
docker run --rm -v "$PWD":/work ghcr.io/epyelabs/xwe \
  run templates/overspeed.json \
  --input telemetry=telemetry/window.csv --out out
```

The image is multi-architecture (`linux/amd64`, `linux/arm64`), so the same
tag runs on a laptop, a server, and a Raspberry Pi 5 class device. The
entrypoint is `xwe`, any argument list works after the image name, and your
working directory mounted at `/work` is where relative template, input, model
and output paths resolve. Tags follow the package version (`0.1.0`) with
`latest` tracking the newest release.

Models are not baked into the image. Mount a directory in the
[registry layout](/workflows/models) or let the image pull into a mounted
cache:

```bash
docker run --rm -v "$PWD":/work -v xwe-models:/root/.xorgate/models \
  ghcr.io/epyelabs/xwe models pull detection/yolov8n
```

## Checking a machine: `xwe doctor`

`xwe doctor` reports everything a run depends on and exits non-zero when a
required piece is missing. From the 0.1.0 image, after one `models pull` into
a mounted cache:

```
xwe 0.1.0 (node 20.20.2, linux arm64)
  ffmpeg            /usr/bin/ffmpeg (5.1.9-0+deb12u1)
  onnxruntime-node  1.29.0, cpu binding loaded
  vlm providers     1 client installed
  models            ~/.xorgate/models (1 cached: detection/yolov8n@1)
  registry          https://models.xorgate.io (index: 3 models)
  catalog           26 nodes, core e481243f5ffe4678, no packs
```

Each line names the fix when something is absent (`ffmpeg: not found; set
FFMPEG_PATH or install it`), which is the first thing to run when a model or
video node fails on a new machine. From 0.2.0 a `python3` line follows
`vlm providers` (`/usr/bin/python3 (3.11.2)` in the image) for
[`function.python`](/workflows/functions) nodes; like the registry line it
never fails the check. When more than one model root is in the
search chain (`--models-dir`, the cache), each root gets its own line under
`models`. The `registry` line reads the registry's `index.json`
(`XWE_MODEL_REGISTRY`, default the public registry) and reports how many
models it lists, or why it could not be read (`unreachable: ENOTFOUND` on a
machine without network access). It never fails the
check: a run needs the registry only when it pulls.

## Requirements, in one place

- Node 20 or newer, for the package. The image brings its own.
- ffmpeg on the machine, for video nodes.
- CPU only. ONNX Runtime's prebuilt CPU binding covers Linux and macOS on x64
  and arm64; there is no GPU path. [Performance](/workflows/performance) says
  what that buys.
- Models on disk or pulled from a registry, for `model.*` nodes other than the
  VLM. See [Models and the registry](/workflows/models).
- A secret only for `connector.third_party` (except `osm`) and `model.vlm`. See
  [Inputs and outputs](/workflows/run-artifacts#secrets).
