A [pack](/workflows/extending) is code you compile, publish and load into the
process, and it is trusted the way any dependency is. A **code function** is
the other kind of extension: a few lines of JavaScript or Python stored inside
a node of the template, and run by the engine in a sandboxed child process
wherever the template runs. Packs are for node authors; functions are for
template authors who need one transformation the catalog does not have.

## The two node types

| Type                  | Group      | Ports                                               | Target | Configuration                                                                                                                   |
| --------------------- | ---------- | --------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `function.javascript` | `function` | in `event:json` (any tag), out `result:json/result` | `any`  | `handler` (`"handler"`), `timeoutMs` (3000, 100 to 30000), `memoryMb` (256, 128 to 2048), `code`, `versions`, `deployedVersion` |
| `function.python`     | `function` | the same                                            | `any`  | the same                                                                                                                        |

A function consumes `json` messages of any tag and emits `json/result`. In
the current catalog that means it can sit downstream of a detector
(`json/detections`), a depth or segmentation model, the VLM's analysis
(`json/vlm`), the connector (`json/speed_limit`) or another function, and
its result can feed `output.data_capture` (which accepts any `json`) or
another function. Frames, telemetry and conditions stay on their own channels
and are handled by catalog nodes.

## The handler

One function per event. Whatever it returns is emitted; `null`, `undefined`
or `None` drops the event.

```js
async function handler(event, context) {
  context.log("got", event.tag, "at", event.ts)
  return { ...event.payload, seenAt: new Date(event.ts).toISOString() }
}
```

```python
def handler(event, context):
    context.log("got", event["tag"], "at", event["ts"])
    return {**event["payload"], "seen": True}
```

| Name                              | Contents                                                                                                                                                                            |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `event.tag`                       | The tag the producer declared: `detections`, `vlm`, `speed_limit`, `result`, and so on.                                                                                             |
| `event.ts`                        | Epoch milliseconds of the message.                                                                                                                                                  |
| `event.seq`                       | The producer's per-node sequence number.                                                                                                                                            |
| `event.payload`                   | The record itself. For `detections`: `{ ts, frameSeq, boxes: [{ cls, confidence, xyxy }] }`.                                                                                        |
| `context.log(...args)`            | Appends one log line to the invocation (`console.log` and `print()` do the same). Lines reach the run as `record` progress messages tagged `log`, and the step summary counts them. |
| `context.nodeId`, `context.runId` | For correlating logs.                                                                                                                                                               |
| `context.functionVersion`         | `"$LATEST"` or the deployed version number that is running.                                                                                                                         |
| `context.remainingTimeMs()`       | Time left before `timeoutMs` ends the invocation.                                                                                                                                   |
| return value                      | Emitted as the `payload` of a `json/result` message with the event's `ts`.                                                                                                          |

A thrown error, an uncaught exception, or a timeout fails the invocation,
which fails the node's step and skips everything downstream, exactly like
any other node. The error, the frames inside your code and the invocation's
log lines are in the step's output:

```
invocation 1 failed: TypeError: Cannot read properties of undefined (reading 'filter')
    at handler (index.js:3:40)
logs:
  about to fail on frame 0
```

A function with several producers wired to `event` handles their messages
in arrival order (not merged by timestamp), so a producer that goes quiet
never stalls the others.

## Worked example: count forklifts per frame

The detection graph on the [models page](/workflows/models#bringing-your-own-model)
emits one `detections` record per frame with every box. Suppose you want a
compact per-frame record instead: how many forklifts, and the widest one.
That is a function between the detector and a capture node.

```
source.video -> video.decode_sample -> model.object_detection -> function.javascript -> output.data_capture
```

The handler:

```js
async function handler(event, context) {
  const forklifts = event.payload.boxes.filter((b) => b.cls === "forklift")
  if (forklifts.length === 0) return null // nothing to record for this frame
  const widest = forklifts.reduce((a, b) => (width(b) > width(a) ? b : a))
  return {
    frameSeq: event.payload.frameSeq,
    count: forklifts.length,
    widestPx: Math.round(width(widest)),
    confidence: widest.confidence,
  }
}

function width(box) {
  const [x1, , x2] = box.xyxy
  return x2 - x1
}
```

The template stores the code in the node's config. `code` is one JSON
string, so the editor writes it with escaped newlines; the rest of the node
is ordinary:

```json
{
  "id": "fn",
  "type": "function.javascript",
  "data": {
    "label": "Forklift summary",
    "config": {
      "handler": "handler",
      "timeoutMs": 1000,
      "memoryMb": 128,
      "code": "async function handler(event, context) {\n  const forklifts = event.payload.boxes.filter((b) => b.cls === \"forklift\")\n  …\n}",
      "versions": [],
      "deployedVersion": null
    }
  },
  "position": { "x": 600, "y": 0 }
}
```

with edges `det -> fn` and `fn -> cap`, where `cap` is an
`output.data_capture` node. Validation accepts the edge from the detector
because the function's input is untagged, and the edge into the capture node
because its input is untagged too.

Run it:

```bash
xwe run forklift-summary.json --input video=yard.mp4 --models-dir ./models --out out
```

```
[xwe] model detection/acme-forklift v1 <- models/detection/acme-forklift/1/model.onnx
[xwe] succeeded in 1.7s -> out/local-1789000000000/result.json
  ok      src          video yard.mp4 (video_local)
  ok      dec          50 frame(s) sampled at 2 fps from 1 video(s)
  ok      det          81 detection(s) over 50 frame(s) (acme-forklift v1, ~30 ms/frame)
  ok      fn           50 invocation(s), 33 result(s), 17 dropped ($LATEST, javascript, ~0 ms)
  ok      cap          captured 33 record(s)
  events: 0
```

(the counts are from the engine's golden footage with `"car"` in place of
`"forklift"`; `~0 ms` is the handler's own time per invocation, under a
millisecond here). `out/local-1789000000000/outputs/cap/records.jsonl`
holds one line per frame that had a forklift, in the capture node's
`{ ts, tag, record }` shape, with the event's `ts` and the `result` tag:

```json
{"ts":1788658741055,"tag":"result","record":{"frameSeq":0,"count":1,"widestPx":196,"confidence":0.7959}}
{"ts":1788658741555,"tag":"result","record":{"frameSeq":1,"count":2,"widestPx":124,"confidence":0.7451}}
```

## Worked example: the same thing in Python

```python
def handler(event, context):
    forklifts = [b for b in event["payload"]["boxes"] if b["cls"] == "forklift"]
    if not forklifts:
        return None
    widest = max(forklifts, key=lambda b: b["xyxy"][2] - b["xyxy"][0])
    return {
        "frameSeq": event["payload"]["frameSeq"],
        "count": len(forklifts),
        "widestPx": round(widest["xyxy"][2] - widest["xyxy"][0]),
        "confidence": widest["confidence"],
    }
```

The node is `function.python` with the same config keys, and the step
summary says `python`. The standard library is available (`json`, `math`,
`statistics`, `datetime`, `re`); packages are not, and neither are the
modules that reach files, processes or the network (`os`, `pathlib`,
`subprocess`, `socket`, `asyncio`, `sys`, and their relatives), which raise
`PermissionError` on import. `round()` rounds half to even, so `widestPx`
can differ from the JavaScript version by one on a `.5` width; the engine's
golden suite runs both over the same footage and checks exactly that.

## Worked example: chaining functions

Functions compose because a result is a `json` message like any other. A
second function downstream of the first sees `event.tag === "result"` and
the first function's return value as `event.payload`:

```js
// fn2: keep a running maximum across frames and emit only when it grows
let best = 0
async function handler(event, context) {
  if (event.payload.count <= best) return null
  best = event.payload.count
  context.log("new maximum", best, "at frame", event.payload.frameSeq)
  return { frameSeq: event.payload.frameSeq, maxCount: best }
}
```

Module-level state like `best` lives as long as the node's process, which is
the run: functions are stateful within a run and start fresh on the next.
That is enough for running maxima, debouncing and deduplication, and it is
the reason a function gets one process per run rather than one per event.
Over the golden footage the chain above prints

```
  ok      fn           50 invocation(s), 33 result(s), 17 dropped ($LATEST, javascript, ~0 ms)
  ok      fn2          33 invocation(s), 5 result(s), 28 dropped, 5 log line(s) ($LATEST, javascript, ~0 ms)
```

and with `--progress json` each `context.log` call is one line of the stream:

```json
{
  "at": "2026-09-06T01:00:39.490Z",
  "t": "record",
  "nodeId": "fn2",
  "port": "log",
  "tag": "log",
  "ts": 1788656438677,
  "seq": 0,
  "payload": { "line": "new maximum 1 at frame 0", "invocation": 1 }
}
```

## Worked example: the whole thing from code

Everything above, driven from your own program instead of the shell. The
handler lives in its own file so it can be edited and linted like any other
source; the program puts its text into the node's config, validates the
template, tests the function on one event, runs the template, and reads the
records back.

```ts
import { readFile } from "node:fs/promises"
import { createEngine, validateDefinition } from "@xorgate/workflow-engine"
import { localHost } from "@xorgate/workflow-engine/local"

// 1. The template, with the handler's source placed into the function node.
//    `code` is an ordinary string in the node's config, so keeping the handler
//    in a file and reading it in is the natural way to author it from code.
const template = JSON.parse(await readFile("./forklift-summary.json", "utf8"))
const fn = template.nodes.find((n) => n.id === "fn")
fn.data.config.code = await readFile("./functions/forklift-summary.js", "utf8")

// 2. Validate before anything runs: the function node is checked like any
//    other (config against its schema, edges against its ports).
const validation = validateDefinition(template)
if (!validation.ok) {
  for (const issue of validation.issues) console.error(issue.code, issue.nodeId ?? "", issue.message)
  process.exit(2)
}

// 3. One engine, one host. The function runtime is part of the engine; the
//    host only supplies files, models, secrets and where artifacts go.
const engine = createEngine({
  host: localHost({ modelDirs: ["./models"], outDir: "./out" }),
})

// 4. Test the function alone, on one detections event, before spending a
//    run on it. Same sandboxed runtime, same code the run would use.
const test = await engine.testFunction({
  template,
  nodeId: "fn",
  event: {
    tag: "detections",
    ts: 1786578991867,
    payload: {
      ts: 1786578991867,
      frameSeq: 3,
      boxes: [{ cls: "forklift", confidence: 0.81, xyxy: [120, 200, 332, 410] }],
    },
  },
})
if (!test.ok) throw new Error(`handler failed: ${test.error}`)
console.log("test result", test.result) // { frameSeq: 3, count: 1, widestPx: 212, confidence: 0.81 }

// 5. Run the template. Function log lines arrive as `record` progress
//    messages tagged `log`, as the run proceeds.
const run = await engine.run({
  template,
  inputs: { video: "./yard.mp4" },
  progress: (m) => {
    if (m.t === "record" && m.tag === "log") console.log(`[${m.nodeId}]`, m.payload.line)
    if (m.t === "step") console.log(m.status, m.nodeId, m.output)
  },
})

// 6. Read the results: from memory, or from the artifact tree on disk.
if (run.result.status !== "succeeded") {
  throw new Error(`run failed at ${run.result.failedNodeId}: ${run.result.error}`)
}
const records = run.outcome.captures["cap"] // the capture node's records, in memory: { ts, tag, record }
console.log(records.length, "frames with a forklift; widest:", Math.max(...records.map((r) => r.record.widestPx)))
console.log("on disk:", `${run.runDir}/outputs/cap/records.jsonl`)
```

What it prints:

```
test result { frameSeq: 3, count: 1, widestPx: 212, confidence: 0.81 }
ok src video ./yard.mp4 (video_local)
ok dec 50 frame(s) sampled at 2 fps from 1 video(s)
ok det 81 detection(s) over 50 frame(s) (acme-forklift v1, ~30 ms/frame)
ok fn 50 invocation(s), 33 result(s), 17 dropped ($LATEST, javascript, ~0 ms)
ok cap captured 33 record(s)
33 frames with a forklift; widest: 297
on disk: out/local-1789000000000/outputs/cap/records.jsonl
```

`engine.testFunction` also resolves for a handler that throws (`ok: false`,
the error and its trace in `error`, the log lines in `logs`) and rejects
with `XweUsageError` (`exitCode: 2`) when the node id, the version or the
event is wrong and nothing ran; the result carries `nodeId`, `type`,
`language` and `runtime` (`node 20.20.2`, `python 3.11.2`) next to the
documented fields.

The same program with `function.python` changes one line: the file it reads
is `forklift-summary.py`. Nothing about the engine, the host or the run
changes, because the runtime is chosen by the node type.

Two things this program does not do, on purpose. It does not `eval` the
handler itself: the engine's child-process runtime is the only place the
code runs, in the test and in the run alike. And it does not need the
platform: no account, no network, no credentials, which is the point of
running the engine as a library.

## Testing a function locally

`xwe function test` runs one event through the node in the same sandboxed
runtime a run would use, with the code the template holds:

```bash
cat > event.json <<'EOF2'
{
  "tag": "detections",
  "ts": 1786578991867,
  "payload": {
    "ts": 1786578991867,
    "frameSeq": 3,
    "boxes": [
      { "cls": "forklift", "confidence": 0.81, "xyxy": [120, 200, 332, 410] },
      { "cls": "pallet", "confidence": 0.77, "xyxy": [400, 380, 520, 440] }
    ]
  }
}
EOF2
xwe function test forklift-summary.json fn --event event.json
```

```
ok      fn           function.javascript  $LATEST  0 ms
result: {"frameSeq":3,"count":1,"widestPx":212,"confidence":0.81}
logs: none
```

A handler that throws shows the trace and exits 1 (here on an event without
`boxes`):

```
failed  fn           function.javascript  $LATEST  0 ms
error: TypeError: Cannot read properties of undefined (reading 'filter')
    at handler (index.js:2:41)
logs: none
```

The Python node reports `at handler (handler.py:2)` the same way. A dropped
event prints `result: null (dropped)`; log lines are listed under `logs:`.
`--version 2` tests a published snapshot instead of the working copy. Exit
code 2 means the node id (the message lists the template's node ids), a
file or the version was wrong and nothing ran. From code it is
`engine.testFunction`, resolving to
`{ ok, result?, error?, logs, durationMs, functionVersion }`, as the worked
example above shows. The template in these examples, in both languages, and
the event are in the engine repository under `examples/functions/`.

## Versions

The node's configuration holds a working copy and a list of published
snapshots, which is how the editor lets you keep editing while a known-good
version runs:

| Field             | Meaning                                                                                     |
| ----------------- | ------------------------------------------------------------------------------------------- |
| `code`            | The working copy, `$LATEST`.                                                                |
| `versions`        | Published snapshots, newest first: `{ version, code, handler, publishedAt, description? }`. |
| `deployedVersion` | The snapshot that runs, or `null` for the working copy.                                     |

The engine runs `deployedVersion` when it is set and present in `versions`,
and the working copy otherwise. One rule on every host: a template exported
with `deployedVersion: 2` runs version 2 under `xwe` too, and the step
summary says `v2` instead of `$LATEST`. A template edited by hand can leave
`versions` empty and `deployedVersion` null; the working copy runs.

## How the engine runs a function

Untrusted code never runs in the engine's process. Each function node
instance gets **one child process per run**, started when the first event
arrives and reused for every event after it, speaking one JSON object per
line over stdio:

| Boundary      | JavaScript                                                                                                                                                                          | Python                                                                                                                                |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Runtime       | the `node` the engine runs on, with Node's permission model enabled; the only grant is a read on the runner file itself (no file system, no child processes, no workers, no addons) | `python3 -I -S` from `PATH` (isolated: no site-packages, no environment variables); the image includes it and `xwe doctor` reports it |
| Module access | none: no `require`, no `import()`, no `eval` or `Function`, no `process`; the language's built-ins, timers, `console` and `structuredClone`, in a context of their own              | the standard library minus the modules that reach files, processes or the network; `open()` refuses; no `pip` packages                |
| Time          | `timeoutMs` per invocation; on expiry the process is killed and the step fails                                                                                                      | the same                                                                                                                              |
| Memory        | `memoryMb` as the heap limit (`--max-old-space-size`)                                                                                                                               | `memoryMb` as an address-space limit (`RLIMIT_AS`, enforced on Linux; not on macOS)                                                   |
| Network       | none: `fetch` and every module refuse with `ERR_ACCESS_DENIED`                                                                                                                      | none: `socket`, `asyncio`, `http`, `urllib` and their relatives raise `PermissionError` on import                                     |
| Filesystem    | none                                                                                                                                                                                | none: `open()`, `os`, `pathlib`, `shutil`, `tempfile` refuse                                                                          |
| Environment   | an allowlist: `PATH`, `HOME`, locale, `TZ` and the temp directory; no `XORGATE_SECRET_*`, no secrets file, no `NODE_OPTIONS`; the handler has no `process` at all                   | the same allowlist                                                                                                                    |

The container image is the intended outer boundary for hosts that run
templates from people they do not trust; the per-process limits above are the
inner one. The JavaScript wall is enforced by the runtime (the permission
model and the context); the Python guards are at the import layer, and an
interpreter is not a security boundary on its own. A function that needs the
network, a package, a model or a secret is a sign that it should be a pack or
a connector node instead. `xwe doctor` names the `python3` a machine would
use; without one, a `function.python` step fails naming it and
`function test` exits 2.

## Functions or packs

| Question                       | Code function                      | Node pack                              |
| ------------------------------ | ---------------------------------- | -------------------------------------- |
| Who writes it                  | the template author                | a developer, in a repository           |
| Where the code lives           | inside the template                | in an npm package the host loads       |
| Trust                          | untrusted: sandboxed child process | trusted: runs in the engine's process  |
| Dependencies                   | none                               | anything npm has                       |
| Channels                       | `json` in, `json` out              | any channel, any port shape            |
| Needs a model, a secret, HTTP  | no                                 | through `ctx`, like a core node        |
| Runs on a host that lacks it   | anywhere `node` or `python3` runs  | only where the pack is installed       |
| Appears in the catalog payload | as the two fixed types             | as its own nodes, with the pack's hash |

When a function grows a dependency, a second port, or a need for a secret,
it has become a pack. The handler contract is designed so the move is a copy:
a pack executor that wraps the same `handler(event, context)` is a few lines.
A `condition` output, so a function can drive `output.event` directly, is
the obvious next step and is not in the first version; today that path is a
function feeding a capture node, or a pack.
